# Web 安全：XSS 与 CSRF

## TL;DR

**XSS 是「把恶意脚本注入到你的页面里执行」，防御核心是输入输出转义 + CSP + HttpOnly；CSRF 是「在别人的网站上冒用你的登录态发请求」，防御核心是 SameSite Cookie + Token 校验 + 同源检测**。一句话区分：XSS 偷数据，CSRF 冒身份。

---

## 1. XSS：跨站脚本攻击

攻击者让恶意 JS 在受害者浏览的页面上执行，从而窃取 Cookie/Token、伪造操作、篡改页面。按注入途径分三类：

| 类型 | 途径 | 例子 |
|---|---|---|
| 存储型（最危险） | 恶意内容入库，所有访问者中招 | 评论区发 `<script>` 偷 Cookie |
| 反射型 | 恶意代码在 URL 参数里，服务端拼进响应 | 诱导点击带 payload 的链接 |
| DOM 型 | 纯前端：JS 把不可信数据插入 DOM | `innerHTML = location.hash` |

### 防御组合拳

1. **输出转义**（核心）：把用户内容渲染进 HTML 前转义 `< > " ' &`；框架默认插值（React JSX、Vue 模板）已做，**危险出口**是 `dangerouslySetInnerHTML`、`v-html`、原生 `innerHTML`——面试要能点名；
2. **输入校验**：白名单格式校验（长度、字符集），富文本用成熟库（DOMPurify）按标签白名单过滤；
3. **CSP**（内容安全策略）：响应头 `Content-Security-Policy: script-src 'self'` 限制脚本来源，禁内联脚本——即使注入成功也执行不了，是兜底防线；
4. **HttpOnly Cookie**：JS 读不到，XSS 偷不走登录态（配合 Secure、SameSite）；
5. 谨慎使用 `eval`、`new Function`、`javascript:` 协议 URL。

---

## 2. CSRF：跨站请求伪造

利用「浏览器请求会自动携带目标站 Cookie」：受害者已登录 A 站，访问恶意 B 站时，B 页面向 A 发起请求（img、自动提交表单），A 的服务器看到合法 Cookie 就执行了操作。

三个特征（判断题常考）：攻击**发起在第三方网站**；攻击者**冒用而拿不到** Cookie；请求是「合法用户发出」的，服务器难以分辨。

攻击形态：GET 型（`<img src="https://a.com/transfer?to=hacker">`）、POST 型（自动提交的隐藏表单）、诱导点击的链接型。

### 防御组合拳

1. **SameSite Cookie**（当代第一道防线，详见下节）：Lax 起步，敏感站 Strict；
2. **CSRF Token**：服务器发随机 Token（存 Session），页面表单/请求头携带，服务端校验——第三方网站拿不到 Token；缺点是每个页面每个接口都要接入，工程量大；
3. **双重 Cookie 校验**：登录后种一个随机值 Cookie（不设 HttpOnly），前端请求时读出来放进自定义请求头，服务端比对 Cookie 与头是否一致——第三方站发请求带得上 Cookie 但**读不到它、加不了自定义头**。优点是无 Session、可统一拦截实施；前提是无 XSS 且全站 HTTPS；
4. **同源检测**：服务端校验 Origin/Referer 头（浏览器不允许 JS 篡改）；
5. 敏感操作二次确认：验证码、支付密码——本质是「只有真人在真页面才能提供的凭证」。

**为什么 XSS 会让 CSRF 防御全线失守**：Token 也好、双重 Cookie 也好，防的是「第三方站拿不到凭证」；一旦本站被 XSS，攻击脚本就在「本站上下文」里，什么都读得到——所以先防 XSS。

---

## 3. SameSite：Cookie 的跨站开关

`Set-Cookie: sid=xxx; SameSite=Lax`：

| 值 | 行为 |
|---|---|
| `Strict` | 跨站请求一律不带 Cookie（从别站点链接跳过来也丢登录态，体验差） |
| `Lax`（**Chrome 默认**） | 跨站不带，但**顶级导航的 GET**（点链接跳转）例外 |
| `None` | 跨站也带，**必须同时 Secure**（仅 HTTPS） |

Lax 默认化让「img/表单自动发请求」类经典 CSRF 基本失效，但不能只靠它：老浏览器、`None` 场景（真需要第三方嵌入的业务）、以及 Lax 放行的 GET 导航（所以**永远别用 GET 做写操作**）。

## 面试问答

### Q: XSS 有哪几类？怎么防御？

满分答案：存储型（恶意内容入库、影响所有访问者）、反射型（payload 在 URL、服务端拼回）、DOM 型（前端自己把不可信数据插入 DOM）。防御分层：输出转义是根本，框架默认插值安全但 v-html/dangerouslySetInnerHTML/innerHTML 是危险出口，富文本用 DOMPurify 白名单；CSP 限制脚本来源做兜底；HttpOnly 保住 Cookie。一句原则：永远不信任用户输入，在「输出到执行环境」的那一刻做处理。

### Q: CSRF 的攻击原理？怎么防御？

满分答案：利用浏览器自动携带 Cookie——用户登录 A 站后访问恶意站，恶意站以 img/自动表单向 A 发请求，A 见 Cookie 合法即执行。防御：SameSite=Lax/Strict 掐断第三方携带；CSRF Token 或双重 Cookie 校验（第三方读不到 Cookie、加不了自定义头）；服务端校验 Origin/Referer；敏感操作加验证码。写操作禁用 GET，因为 Lax 会放行顶级 GET 导航。

### Q: XSS 和 CSRF 的区别与联系？

满分答案：XSS 是代码注入，恶意脚本在目标站上下文执行，能直接窃取数据；CSRF 是请求伪造，发生在第三方站，只能冒用身份执行操作、拿不到数据。联系：CSRF 的各种 Token 类防御的前提是「凭证第三方不可读」，一旦存在 XSS，脚本已在本站上下文，所有 CSRF 防御随之失效——所以 XSS 的优先级更高。

### Q: SameSite 三个值的区别？默认是什么？

满分答案：Strict 跨站一律不带 Cookie，安全但从外链跳入会丢登录态；Lax 跨站不带、仅放行顶级导航 GET（链接跳转），是 Chrome 的默认值；None 跨站也带但强制要求 Secure。工程含义：Lax 默认化已废掉大部分传统 CSRF，需要第三方嵌入（iframe 支付、跨站 SSO）的 Cookie 才显式设 None + Secure，并配合其他 CSRF 防御。
