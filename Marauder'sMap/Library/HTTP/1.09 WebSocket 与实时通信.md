# WebSocket 与实时通信

## TL;DR

**WebSocket 是基于 TCP 的全双工协议：由一次 HTTP 「协议升级」握手（101 Switching Protocols）建立，之后双方随时互发帧，没有请求-响应的束缚**。选型脉络：单向推送选 SSE，双向实时选 WebSocket，兼容兜底才轮到轮询。

---

## 1. 为什么 HTTP 做不了实时

HTTP 是请求-响应模型，**服务器无法主动开口**。历史演进就是「怎么让服务器能推」：

| 方案 | 原理 | 缺点 |
|---|---|---|
| 短轮询 | 定时发请求问「有新的吗」 | 大量无效请求、延迟=轮询间隔 |
| 长轮询 | 服务器 hold 住请求直到有数据/超时，返回后立刻再连 | 实时性尚可，但每条消息一次完整 HTTP 往返、服务端挂起消耗连接 |
| SSE | 一个长连 HTTP 流，服务器持续 `text/event-stream` 推送 | **只能服务器→客户端单向**、纯文本 |
| WebSocket | 独立协议，全双工帧通信 | 需要服务端支持、有状态连接的运维成本 |

SSE 加分点：基于普通 HTTP（代理/网关友好）、自带断线重连和事件 ID 续传——**AI 对话的流式输出就是典型 SSE 场景**；只需要「推」时它比 WebSocket 更省事。

## 2. 握手：一次 HTTP 升级

```text
GET /chat HTTP/1.1
Host: example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: <客户端随机 base64>
Sec-WebSocket-Version: 13
Origin: https://example.com

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: <对 Key 拼固定 GUID 后 SHA-1 再 base64>
```

三个理解点：

1. 借 HTTP 握手是为了**复用 80/443 端口和基础设施**，穿透代理防火墙；101 之后这条 TCP 连接上跑的就是 WebSocket 帧，不再是 HTTP；
2. `Sec-WebSocket-Key/Accept` **不是加密**，只是确认「对端真的懂 WebSocket 协议」、防止普通 HTTP 服务器被误当 WS 服务器；
3. **WebSocket 不受同源策略限制**——所以服务端必须自己校验 `Origin` 头，否则会被跨站 WebSocket 劫持。

URL 用 `ws://` / `wss://`（TLS 版，生产必须 wss，HTTPS 页面里也只允许 wss）。

## 3. 使用与工程要点

```js
const ws = new WebSocket('wss://example.com/chat');
ws.onopen = () => ws.send(JSON.stringify({ type: 'hello' }));
ws.onmessage = (e) => handle(JSON.parse(e.data));   // 文本或二进制（Blob/ArrayBuffer）
ws.onclose = (e) => scheduleReconnect(e.code);      // 1000 正常关闭
ws.onerror = () => {/* 错误细节有限，主要靠 close code */};
```

生产必答的三件配套（裸 WebSocket 不可上线）：

- **心跳保活**：定时 ping/pong（应用层自定义消息即可），检测死连接——中间设备会静默掐掉长时间无数据的 TCP；
- **断线重连**：指数退避 + 抖动，重连后**补拉离线消息**（服务端按消息序号/时间戳支持增量拉取）；
- **消息协议设计**：自定义 `{ type, seq, payload }` 信封，处理有序性与去重。

现成方案：Socket.IO（自动降级长轮询、房间、重连开箱即用，但私有协议、两端都要用它）；纯推送场景直接用云厂商推送通道或 SSE。

多标签页共享一条连接（省连接数）：用 `SharedWorker` 持有 WebSocket，各页面经 port 通信；或 BroadcastChannel 由主标签页转发。

## 面试问答

### Q: WebSocket 和 HTTP 的关系与区别？

满分答案：WebSocket 是独立的应用层协议，只是「借」HTTP 完成握手——客户端发带 Upgrade: websocket 的 GET，服务端回 101 Switching Protocols 后，这条 TCP 连接就切换为全双工的帧通信，之后与 HTTP 无关。区别：HTTP 请求-响应、无状态、服务器不能主动发；WebSocket 持久连接、双向、低开销（帧头几字节，无重复头部）。借 HTTP 握手的动机是复用 80/443 和现有网络基础设施。

### Q: 轮询、长轮询、SSE、WebSocket 怎么选？

满分答案：按方向和实时性——只需服务器单向推（通知、行情、AI 流式回答）用 SSE：普通 HTTP、自带重连续传、实现最轻；需要双向高频交互（聊天、协同编辑、游戏）用 WebSocket；轮询只作老环境兜底：短轮询实现最简但空耗流量、延迟高，长轮询实时性好些但每条消息一次完整往返。成熟做法是 Socket.IO 这类库自动降级。

### Q: WebSocket 如何保证连接可用？断了怎么办？

满分答案：三板斧——应用层心跳（定时 ping/pong，超时即判死，防中间设备静默断连）；指数退避重连（加随机抖动防雪崩），重连成功后按本地记录的最后消息序号向服务端增量补拉，保证不丢消息；消息信封带 seq 做去重与排序。再提一句连接层：页面切后台、网络切换都要监听处理，移动端尤其重要。

### Q: WebSocket 有同源限制吗？安全上要注意什么？

满分答案：没有——任何页面都能向任意 ws 地址发起连接，所以安全责任在服务端：握手时校验 Origin 头防跨站 WebSocket 劫持，连接建立后先走鉴权（token 放握手 URL 参数或首条消息），生产一律 wss 加密。Sec-WebSocket-Key 只是协议确认机制，不承担鉴权或加密职能——这是常见误解，说清很加分。
