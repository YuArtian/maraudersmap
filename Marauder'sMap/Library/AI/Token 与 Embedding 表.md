# Token 与 Embedding 表

> 文字进入大模型前的两次翻译：字节 →（查词表）→ token →（查 embedding 表）→ 向量

## TL;DR

- 模型不认识"字"，只认识 **token**：词表像一盒乐高，常见词整块、生僻词拆碎、256 个字节 token 兜底——**编码层面不存在"不认识"**
- **256 个字节兜底是穷举、不是抽样**：一个字节只有 2⁸ = 256 种可能，且字节全集恒定不变（字符全集每年在涨），所以这 256 行买的是永久保险
- **Embedding 表 = 词表行数 × 维度的巨大数字表格**，是模型参数的一部分，存在权重文件里，训练学出来的
- 每家模型的词表和 embedding 表都不同 → **不同模型的向量互不通用**（RAG 换 embedding 模型必须整库重灌）
- **token 数 ≠ 字数**：常见字一块搞定，生僻字退化成 2~3 个字节 token，同一句话里混着来
- **词表大小（32000）是超参数，本质是"用参数换序列长度"**：调大 → 切分更整块、token 数更少、注意力 O(n²) 省，但 embedding 表和输出头的参数线性暴涨
- **32000 种 token ≠ 只能表达 32000 种东西**：token 是序列（组合爆炸），且含义由上下文重塑——**离散有限的入口，连续无限的内部表示**
- 完整链条：字符 →(UTF-8)→ 字节 →(分词器)→ token →(查表)→ 向量（序列长度 × 维度的矩阵）→(注意力层)→ …

## 1. 分词器与词表：一盒乐高积木

词表（vocabulary）里的一行不是一个"词"，而是一个 **token（词元）**——可以是完整的词、词的碎片，最小到单个字节：

```text
常见词   → 有整块积木:  "the"、"我" 各占一行，1 个 token 搞定
次常见词 → 拆成几块:    "internationalization"
                       → "intern" + "ational" + "ization"（3 个 token）
生造词   → 拆得更碎:    "blorptastic"
                       → "bl" + "orp" + "tast" + "ic"（4 个 token）
```

分词器（tokenizer）的策略：**尽量用大块，不够就用小块**。

### 字节兜底：永远拼得出来

词表专门留 256 行对应所有字节值（0~255），长相就是 `<0x00>` ~ `<0xFF>`。任何字符终归是几个字节（见 [[1.05 字符编码]]），最坏情况退化到按字节切：

```text
"我" UTF-8 = E6 88 91 → 词表里有专属行 → 1 个 token
"藜" UTF-8 = E8 97 9C → 没有专属行   → <0xE8> <0x97> <0x9C> 3 个 token
```

**为什么 256 行就够？因为一个字节只有 256 种可能——这是穷举，不是抽样。** 字节 = 8 个 bit，每个 bit 两态 → 2⁸ = 256 种组合，从 `00000000` 到 `11111111`，**不存在第 257 种字节**。

和"穷举字符"对比一下就知道这个设计有多划算：

| | 全集有多大 | 会变吗 | 词表能穷举吗 |
|---|---|---|---|
| **字符** | Unicode 已收录 14 万+ | **会**，每年新增新字、新 emoji | ❌ 永远追不上 |
| **字节** | **恒定 256** | **不会**，2⁸ 是数学事实 | ✅ 花 256 行买永久保险 |

所以"编码层面不存在不认识"是一条封闭的推理链，不是经验规律：

```text
任何文本 →(UTF-8)→ 一串字节
每个字节必然是 0~255 之一      ← 2⁸ 穷尽了，没有别的可能
词表里 0~255 各有一行          ← 256 行全占坑
∴ 任何文本必然切得出来，无例外
```

附带的好处：连非法 UTF-8 序列、乱码、甚至任意二进制数据都能 tokenize——分词器根本不需要判断输入是否合法。

### 不是每个字节都变成一个 token

最容易误读的一点：**词表为 256 个字节值各留一行 ≠ 输入里每个字节各切一个 token**。分词器贪心取最长匹配，只在匹配不到时才退化到逐字节：

```text
字节流:  E6 88 91 | E7 88 B1 | E5 90 83 | E8 97 9C | E9 BA A6      共 15 字节
         └─ 我 ─┘  └─ 爱 ─┘  └─ 吃 ─┘  └─ 藜 ─┘  └─ 麦 ─┘

切成:      [我]       [爱]       [吃]   [<0xE8>][<0x97>][<0x9C>]  [麦]
            1          1          1     └──── 3 个 token ────┘     1     共 7 个
```

「我」的 3 个字节被**一个** token 整块吞掉（词表里有「我」这一行）；「藜」的 3 个字节**各自**成为一个 token（词表里没有「藜」）。5 个字在 UTF-8 层面都是 3 字节、待遇完全平等，差别只在词表里有没有专属行。

字节级 token 和普通 token **结构上待遇完全相同**：各占词表一行、各有 embedding 行、各变向量。差别只在语义——`<0xE8>` 这个字节本身没有任何含义（它只是 UTF-8 三字节模板的首字节而已），「藜」的意思得靠注意力层从上下文重新拼出来，**类比人逐字母拼读生词 quinoa，结合上下文猜出是种吃的**。

### 两种实现流派

字节 token 在不同模型的文档里长相不一样，因为有两条技术路线：

| 流派 | 做法 | 字节 token 长相 |
|---|---|---|
| LLaMA / SentencePiece | 词表主体是字符和子词，**额外**挂 256 个字节 token 作 fallback | `<0xE8>` |
| GPT-2 / GPT-4（byte-level BPE） | **整个词表建在字节之上**，所有 token 本质都是字节序列 | 映射成可打印字符，显示像乱码 `ä`、`£` |

结果一样（256 个字节全覆盖、永不 UNK），只是前者"打补丁"、后者"从地基起就用字节"。本文用 LLaMA-2 举例，属第一种。

## 2. 词表大小：32000 是怎么定的

**32000 是超参数——训练分词器时人拍下来的，不是算出来的**（见 [[模型里的四类数字]]）。而 embedding 表**必须**是 32000 行这件事是被动的、没有选择：词表有多少行，embedding 表就得有多少行，**一一对应**——多一行是死代码，少一行就有 token 查不到表。

### 为什么词表越大，切分反而越整块

这一点反直觉（"条目更多不该切得更碎吗"），但看 BPE 训练分词器的实际过程就很直白：

```text
起点（词表 = 256）
  只有 256 个字节 token，任何文本只能逐字节切 —— 这是最碎的极限

合并 #1     语料里最高频的相邻对 "t"+"h"  → 新增一行 "th"，词表 257
合并 #2     "th"+"e"                     → 新增一行 "the"，词表 258
合并 #3     "in"+"g"                     → 新增一行 "ing"，词表 259
   ⋮
合并 #31741                               → 词表 32000
```

**每一次合并都是"把两个 token 粘成一个更长的，占掉词表新的一行"。** 所以：

> **词表大小 = BPE 允许的合并次数预算。** 预算越大 → 合并做得越多 → 表里的块越长 → 切出来越整块。

关键在于：**最碎的那 256 个 token 是起点、开局就送满了**。词表变大，多出来的行只能装**更长**的块——没有比单字节更碎的东西可装。更强的论证：同一次 BPE 训练出的词表是**嵌套**的，词表 32000 包含词表 256 的全部条目，所以大词表能做的切分包含小词表能做的全部，**只会更整块，不可能更碎**，这是单调的。

同一句话在不同词表下：

```text
词表    256（纯字节）  "我爱吃藜麦" → 15 个 token   逐字节，最碎
词表  32000            → 7 个 token   我/爱/吃/<0xE8>/<0x97>/<0x9C>/麦
词表 128000            → 5 个 token   「藜」也挤进表里了，各占一块
```

也就是说，**词表大小和"整块程度"不是两个独立的东西，是同一件事的两种说法**——词表就是合并结果的账本，账本越厚说明粘得越多。

### 权衡：为什么不无限调大

| | 词表调大 | 词表调小 |
|---|---|---|
| 序列长度 | 短 → 注意力 **O(n²)** 省得多 | 长 → 开销平方级涨 |
| 上下文窗口 | 同样窗口装更多实际内容 | 被碎 token 吃掉 |
| 生成速度 | 一步吐一个 token，步数更少 | 步数多 |
| **参数量** | **线性暴涨** | 省 |
| 每步输出 | 全词表算 logits + softmax，更贵 | 便宜 |
| 训练质量 | 长尾 token 出现太少，向量学不好 | 每个 token 都被充分训练 |

参数量是最硬的约束，因为词表大小**同时**乘进两个大矩阵——`model.embed_tokens`（32000 × 4096）和 `lm_head`（4096 × 32000），LLaMA-2 这两个不共享权重：

```text
词表     32000 → 两矩阵合计   2.62 亿  占 7B 总参数  3.89%
词表    128256 → 两矩阵合计  10.51 亿  占            15.59%
词表    151936 → 两矩阵合计  12.45 亿  占            18.47%
词表    256000 → 两矩阵合计  20.97 亿  占            31.12%
```

**词表拉到 25.6 万，光查表就吃掉三分之一的参数预算**——而这些参数只做查表、不参与任何推理计算，性价比远低于花在注意力和前馈层上。

为什么恰好是 32000 这个整数：一半是圆整好记（SentencePiece 训练时 `vocab_size` 直接填），一半是**对齐友好**——`32000 = 256 × 125`，能被 64 / 128 / 256 整除，GPU 上矩阵维度对齐到 2 的幂的倍数，kernel 效率明显更高。

### 32000 行里装了什么

```text
id 0 ~ 2        3 个特殊 token（<unk>、<s>、</s>）
id 3 ~ 258      256 个字节 token（<0x00> ~ <0xFF>）    ← 兜底层，只占 0.8%
id 259 ~ 31999  31741 个子词，BPE 从语料里合并学出来的
```

**256 行买永久保险，31741 行拿来提效率**——兜底层的成本几乎可以忽略，剩下的空间全用在"让常见内容切得更整块"上。

### 业界取值与趋势

| 模型 | 词表 |
|---|---|
| GPT-2 | 50257 |
| **LLaMA-1 / 2、Mistral 7B** | **32000** |
| LLaMA-3 | 128256（128000 个 BPE token + 256 个保留特殊 token） |
| Qwen2 | 151936 |
| Gemma | 256000 |

**趋势是明显变大的**，主推力就是多语言 token 效率：32000 的词表以英文为主，中文大量退化到字节级。LLaMA-3 跳到 128256 做的正是"多花 8 亿参数，换中文 token 数腰斩"这笔交易——对中文用户很值，对纯英文场景是浪费。

所以 **32000 不是什么最优解，是 2023 年初 + 英文为主 + 7B 规模这三个前提下的合理取值**。前提一变，数字就跟着变。

## 3. 只有 32000 个不同的 token，够用吗

是的，就 32000 个，一个不多，而且**训练完就冻结**。模型这辈子见到的、输出的，永远只是这 32000 个之一（输出层每一步做的就是在这 32000 个上算概率、挑一个）。

但「只有 32000 种 token」和「只能表达 32000 种东西」差得极远：

**第一层：token 是序列，不是单选。**

```text
  1 个 token 的序列 → 3.2 × 10⁴   种
  2 个              → 1.0 × 10⁹   种（10 亿）
  3 个              → 3.3 × 10¹³  种（32 万亿）
  7 个（"我爱吃藜麦"）→ 3.4 × 10³¹  种
100 个              → 约 10⁴⁵⁰    种
```

英文只有 **26 个字母**，却能写出人类所有英文著作。**有限的字母表 + 任意长的序列 = 无限的表达力**，这是文字系统的常态，不是妥协。32000 比 26 大三个数量级。

**第二层（更关键）：token 的种类是固定的，token 的含义不是。**

```text
入口（查 embedding 表）  「苹果」→ 永远是第 5678 行那个固定向量
                          ↓ 过第 1 层注意力
第 1 层之后               "吃苹果"里的苹果  ≠  "苹果公司"里的苹果
                          ↓ 再过 31 层
最终                      两个向量已天差地别
```

**32000 是"入口的种类数"，不是"模型内部状态的种类数"。** 内部流动的是 4096 维连续向量，可能的取值是天文数字量级。上下文重塑含义的机制见 [[Transformer]]。

准确的说法是：**离散有限的入口，连续无限的内部表示。** 32000 只约束了"能从哪些格子进门"。

### 词表冻结的两个后果

**一、新词永远拿不到专属 token。** 训练之后出现的新品牌名、新流行语，词表里不会有它们的行，会被拆成已有 token 的组合。模型照样能处理（字节兜底保证了这一点），只是**更费 token、语义更依赖上下文拼凑**——和「藜」的处境完全一样。这也是词表冻结不算致命问题的原因。

**二、token id 跨模型完全不通用。** id `5678` 在 LLaMA-2 里是某个东西，在 GPT-4 的词表里是**毫无关系的另一个东西**。推论：

- 换模型必须换分词器，`tokenizer.model` 和权重文件必须来自同一个模型
- 用 A 模型的分词器数出的 token 数，不能用来估 B 模型的费用和上下文占用
- 「这段文本多少 token」必须先问「哪个模型」——和「中文几个字节」必须先问「哪种编码」是同一类陷阱

### 分词的现实影响

- API 按 token 计费、上下文窗口按 token 算长度——模型眼里的世界就是按积木块切的
- 中文模型（Qwen、DeepSeek 等）把词表扩到十几万行，给常用汉字配整块积木，就是上面那笔"参数换序列长度"的交易

## 4. Embedding 表是什么

一张真实存在的**二维数字表格**：每行一个 token，每列是向量的一个格子。

```text
              第1列   第2列   第3列  ...  第4096列
token "我"     0.12   -0.83   0.45  ...   0.07
token "你"     0.15   -0.79   0.41  ...   0.11
token <0xE8>  -0.52    0.33   1.20  ...  -0.64
...
```

以 LLaMA-2 7B 为例：32000 行 × 4096 列 ≈ **1.3 亿个数字**（fp16 约 260MB，只占 14GB 模型的 2%，大头是注意力和前馈层的权重）。

**"查表" = 取出第 N 行**，没有任何计算。它是模型的第一层，文字进模型的第一站。

### 存在哪、谁生成的

- 存在**模型权重文件**里（`.safetensors` / `.gguf`），和 W_Q、前馈层权重打包在一起；运行时加载进显存
- **没有人编写它**：训练前是随机数，跟着"猜下一个词"的亿万次练习被梯度下降调出来（见 [[大模型如何训练]]）——是训练的产物，像肌肉是健身的产物

### 大家的表一样吗？完全不一样

| 差异层 | 说明 |
|---|---|
| 行数 | 各家分词器不同：LLaMA-2 32000 行，GPT-4 约 10 万行 |
| 列数（维度） | 768 / 4096 / 12288，各家自选 |
| 数值 | 训练数据、初始随机数都不同，练出来必然不同 |

有意思的是**相对关系会重现**："猫"和"狗"在每家的表里都互相靠近——好比两次城市规划，饭店都挨着商圈建，只是门牌号不同。

**推论（RAG 铁律）**：不同模型的向量是两个互不相通的坐标系，点积毫无意义 → 换 embedding 模型必须整库重灌（[[Vector Database]] 建库要指定维度的根源）。

## 5. 词级 embedding vs 句级 embedding

容易混淆的两个东西：

```text
词级: embedding 表查一行 → 一个 token 的向量（纯查表，无计算）
句级: 整句话送进完整模型（通常是 BERT 后代），词向量经过层层注意力
      互相融合 → 汇总成一个代表全句语义的向量
```

[[Embedding Service]] 提供的"文字进、向量出"是句级服务——查表只是它流水线的第一步。

## 6. 完整链条

用一整句话走一遍：**"我爱吃藜麦"**。

### 第一步：字符 → 字节（UTF-8）

```text
我  U+6211  →  E6 88 91
爱  U+7231  →  E7 88 B1
吃  U+5403  →  E5 90 83
藜  U+85DC  →  E8 97 9C
麦  U+9EA6  →  E9 BA A6
```

这一层与模型无关，是通用的字符编码（见 [[1.05 字符编码]]）。

### 第二步：字节 → token（分词器查词表）

分词器的策略是**尽量用大块，不够就用小块**，所以同一句话里不同的字待遇不同：

```text
"我"  →  常用字，词表里有专属行     →  1 个 token
"爱"  →  常用字，有专属行           →  1 个 token
"吃"  →  常用字，有专属行           →  1 个 token
"藜"  →  生僻字，词表里没有         →  退化到字节级：<0xE8> <0x97> <0x9C>  3 个 token
"麦"  →  常用字，有专属行           →  1 个 token

────────────────────────────────────────────────
5 个汉字  →  7 个 token
```

**这是单字例子看不出来的最重要一点：token 数不等于字数。** 常见词一块搞定，生僻字被拆成几块，两者混在同一个序列里，待遇完全平等。

真实的分词器还会在开头补一个特殊 token（如 `<s>` / `<BOS>`）标记序列起点，这里为清晰起见略去。

英文同理，只是切的是词根词缀而非字节：

```text
"tokenization"  →  "token" + "ization"       2 个 token
"cat"           →  "cat"                     1 个 token
"blorptastic"   →  "bl"+"orp"+"tast"+"ic"    4 个 token
```

这也是 API 按 token 计费、上下文窗口按 token 计长度的直接后果——**同样内容，中文往往比英文费 token**（LLaMA 系词表以英文为主，汉字大量退化到字节级）。

### 第三步：token → 向量（查 embedding 表）

7 个 token 各查一行，得到 7 个 4096 维向量，堆起来就是一个矩阵：

```text
token 序列              查表取出的行（各 4096 维）
────────────────────────────────────────────────
[我]         →  [ 0.12, -0.83,  0.45, ... ,  0.07]
[爱]         →  [-0.31,  0.55, -0.02, ... ,  0.88]
[吃]         →  [ 0.64,  0.19, -0.77, ... , -0.23]
[<0xE8>]     →  [-0.52,  0.33,  1.20, ... , -0.64]
[<0x97>]     →  [ 0.08, -0.41,  0.16, ... ,  0.92]
[<0x9C>]     →  [-0.19,  0.72, -0.35, ... ,  0.11]
[麦]         →  [ 0.47, -0.06,  0.83, ... , -0.50]

数据形状：7 × 4096  =  序列长度 × 维度
```

**行数随句子长短变，列数永远固定**（见 [[向量与点积]] 关于维度的规矩）。千字文就是一千多行 × 4096 列。

### 第四步：进入注意力层

这个 7×4096 的矩阵整体送进第一层，token 之间开始互相"看"对方（[[Transformer]]）。`<0xE8><0x97><0x9C>` 这三个字节 token 单看毫无意义，但它们夹在"吃"和"麦"中间，注意力层能从上下文推出这是某种可吃的东西——**类比人逐字母拼读生词 quinoa，结合上下文猜出是种粮食**。

### 一图总览

```text
"我爱吃藜麦"
   ↓ UTF-8 编码                    ← 与模型无关的通用编码
E6 88 91 | E7 88 B1 | ... 共 15 字节
   ↓ 分词器查词表（贪心匹配大块）      ← 每家模型的词表都不同
7 个 token（5 个字 → 7 个 token）
   ↓ 查 embedding 表（取行，零计算）  ← 模型参数的一部分
7 × 4096 的矩阵
   ↓ 32 层注意力 + 前馈              ← 真正的计算从这里开始
7 × 4096 的矩阵（含义已被上下文重塑）
   ↓ 取最后一个位置 × 输出矩阵 + Softmax
32000 维概率分布 → 采样出下一个 token
```

三层查表 + 一路矩阵运算——这就是文字进入神经网络并变回文字的全部路径。本文详述的是前两步；**后面每一步（位置编码、32 层里发生了什么、输出头、采样、自回归循环）的完整展开见 [[AI/Map|AI 知识地图]]**，整体图景见 [[大语言模型]]。

## 附：LLaMA 是什么

Meta（Facebook）出的大语言模型系列，**L**arge **La**nguage Model **M**eta **AI**，拼出来正好是"llama（大羊驼）"，读作"拉玛"。特殊地位在于**开放权重**——可以下载到自己机器上跑和微调，是开源社区的地基（llama.cpp 及各种微调模型都源于此）。本文用 LLaMA-2 举例因为它的参数配置（32000 词表、4096 维）经典好记。
