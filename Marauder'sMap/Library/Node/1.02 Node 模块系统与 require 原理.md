# Node 模块系统与 require 原理

## TL;DR

**require 四步：路径解析 → 查缓存 → 读文件 → 用包装函数执行**。Node 把每个文件包进 `function(exports, require, module, __filename, __dirname)` 执行——模块作用域、exports 与 module.exports 的关系、CJS 的一切「魔法」都从这个函数来。三类模块的查找顺序：核心模块 > 路径模块 > node_modules 逐级向上。

> CJS 与 ESM 的语义差异、互操作与循环依赖见 [[1.01 JS 模块化演进：CommonJS 与 ESM]]；exports 解析字段见 [[1.02 package.json 与依赖管理]]。

---

## 1. 三类模块与查找算法

**核心模块**（fs/http/path，编译进二进制，`node:fs` 前缀可显式指定）→ **文件模块**（`./`、`../`、绝对路径开头）→ **第三方模块**（裸名字：从当前目录 node_modules 逐级**向上**找到根）。

文件模块的补全顺序：精确文件 → 补 `.js/.json/.node` 后缀 → 当目录处理（读 package.json 的 main/exports → 兜底 index.js）。「require('lodash') 发生了什么」按这条链答即可；补一句现代变化：**package.json 的 exports 字段一旦声明，深层路径就被封装锁死**。

## 2. require 的执行原理（手写级）

```js
// 极简 require 骨架
function myRequire(id) {
  const filename = resolve(id);                 // ① 解析成绝对路径
  if (cache[filename]) return cache[filename].exports;   // ② 缓存命中直接返回

  const module = { exports: {} };
  cache[filename] = module;                     // ③ 先入缓存（循环依赖返回半成品的原因）

  const code = fs.readFileSync(filename, 'utf8');
  const wrapper = new Function(                 // ④ 包装函数（真实实现用 vm 模块编译）
    'exports', 'require', 'module', '__filename', '__dirname',
    code,
  );
  wrapper(module.exports, myRequire, module, filename, dirname(filename));
  return module.exports;                        // ⑤ 返回的永远是 module.exports
}
```

包装函数解释了五件事：模块内变量不污染全局（函数作用域）；`exports` 只是 `module.exports` 的形参别名（`exports = x` 断开引用导出失效）；`__dirname/__filename` 不是全局变量而是参数；`require` 可以被局部覆盖；顶层 `this === module.exports`。

**缓存**：以绝对路径为 key，模块代码只执行一次，后续 require 拿同一个 exports 对象——单例模式的天然实现；「先入缓存再执行」使循环依赖拿到「已执行部分」而不死循环。清缓存（测试场景）：`delete require.cache[path]`。

## 3. Node 里的 ESM 现状（更新到当下）

- 启用：`.mjs` 后缀或 package.json `"type": "module"`；
- ESM 里没有 `__dirname/require`——用 `import.meta.url`（配 `fileURLToPath`）与 `createRequire`；**Node 20.11+ 直接有 `import.meta.dirname`**；
- 互操作：ESM 可以 import CJS（default 拿整个 exports）；CJS require ESM 长期被禁，**Node 22 起支持同步 require(ESM)**（模块无顶层 await 时）——新旧结论都要说；
- 库的双格式发布与 exports 条件分发见 [[1.02 package.json 与依赖管理]]。

## 面试问答

### Q: require 一个模块时发生了什么？

满分答案：四步——路径解析：核心模块直接返回；相对/绝对路径按「精确文件→补后缀→目录的 package.json main/exports→index」补全；裸模块名沿 node_modules 逐级向上找。查缓存：以绝对路径为 key，命中直接返回 exports。加载执行：读文件、包进 (exports, require, module, __filename, __dirname) 五参包装函数运行。返回 module.exports。缓存先于执行写入，这是循环依赖能拿到部分导出的机制。

### Q: 为什么模块里的变量不会污染全局？__dirname 是全局变量吗？

满分答案：因为模块代码被塞进包装函数执行，顶层变量都是函数局部变量；__dirname、__filename、require、module、exports 都是这个函数的参数而非全局变量——这也解释了 exports 与 module.exports 的引用关系和「顶层 this 是 module.exports」。ESM 里没有这套包装，对应能力用 import.meta.url / import.meta.dirname（Node 20.11+）。

### Q: require 的缓存机制有什么作用和影响？

满分答案：模块首次加载后以绝对路径缓存 module 对象，之后 require 都返回同一 exports——代码只执行一次，天然单例（数据库连接、配置对象靠它共享）。影响：模块级可变状态会被所有引用方共享；测试要隔离时需 delete require.cache 或用 jest 的模块注册表；「先缓存后执行」让循环依赖返回半成品而非死循环，但可能读到 undefined 导出。
