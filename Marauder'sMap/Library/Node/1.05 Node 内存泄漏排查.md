# Node 内存泄漏排查

## TL;DR

**判定：堆内存曲线只涨不落（GC 后基线持续抬高）就是泄漏**。方法论四步：监控发现（RSS/heapUsed 告警）→ 压测复现（loadtest 放大）→ **堆快照对比**（两次 snapshot 按 Retained Size 找可疑对象、顺 Retainers 链定位持有者）→ 修复验证。Node 特色病灶：全局缓存无上限、EventEmitter 监听器累加、闭包挂全局、未关闭的连接与定时器。

> GC 与可达性判定见 [[2.06 垃圾回收机制]]，闭包泄漏机制见 [[1.03 执行上下文、调用栈与闭包]]。

---

## 1. 判定与指标

看三个数：`process.memoryUsage()` 的 **rss**（进程总内存）、**heapUsed/heapTotal**（V8 堆）、external（Buffer 等堆外）。健康曲线是「锯齿」（涨→GC 回落）；**锯齿的谷底持续抬升**才是泄漏——一时的高峰可能只是缓存或 GC 未触发。压力放大手法：`loadtest -c 100 -t 20 <url>` 边压边观察，几分钟看不出的慢泄漏立刻现形。堆逼近上限（老生代默认约 4GB，`--max-old-space-size` 可调）时 GC 频率暴涨 → CPU 飙升 → OOM 崩溃，这是「泄漏拖垮服务」的完整链条。

---

## 2. 定位：堆快照对比法（核心手艺）

1. 取快照：`node --inspect` + Chrome DevTools Memory 面板；或代码内 `v8.writeHeapSnapshot()`／heapdump 包（生产在告警时自动 dump）；
2. **操作前后各拍一次**（如压测前后），用 Comparison 视图看**新增对象**：按 Retained Size 排序，找「数量异常增长」的构造器（某业务类 ×10 万个、闭包 ×N）；
3. 点开可疑对象看 **Retainers（引用链）**：从 GC root 到它的路径上，「谁抓着不放」一目了然——修复点就在链条上离业务最近的一环；
4. 修复后再压测，确认谷底不再抬升。

线上配套：接 APM/性能平台做堆内存占比告警（如超上限 80% 提醒），告警时自动抓快照——「泄漏发生在凌晨」也有现场可查。

## 3. Node 高发病灶清单（配经典案例）

| 病灶 | 形态 | 修复 |
|---|---|---|
| **全局/模块级缓存无上限** | `const cache = {}` 只进不出（模块缓存单例放大了它，见 [[1.02 Node 模块系统与 require 原理]]） | LRU 上限（lru-cache）、TTL、或外置 Redis |
| **EventEmitter 监听器累加** | 每个请求给**全局** client 加一次 `on('error')`——26KB×流量 → OOM（真实案例形态）；Node 会警告 MaxListenersExceeded | 监听器注册移到初始化阶段一次完成；或 once；退出时 removeListener |
| 闭包被长寿对象引用 | 回调闭包挂在全局 map/队列里 | 用完删除；WeakMap 让引用不阻回收 |
| 定时器/未清理订阅 | setInterval 没 clear，回调连着大上下文 | 生命周期结束统一清理 |
| 连接未释放 | DB/HTTP keep-alive 连接池泄漏、流没有 destroy | 池化管理、错误路径也要释放（finally） |

「每请求都往全局对象注册事件」是**最典型的 Node 泄漏**——单元测试测不出（一次请求无感），流量一放大就 OOM；教训是：**凡是全局单例，写入必须有界**。

## 4. 面试叙事模板

「先讲判定（GC 后基线抬升）→ 再讲工具链（memoryUsage 指标、--inspect 快照、对比视图、Retainers）→ 给一个真实感案例（全局 emitter 累加监听）→ 收尾预防（全局写入有界、监听器初始化时注册、压测纳入上线流程、平台化告警自动 dump）」——方法论 + 案例 + 预防三段齐，比背清单高一档。

## 面试问答

### Q: 怎么判断和排查 Node 服务的内存泄漏？

满分答案：判定看 heapUsed 曲线——健康是锯齿形，GC 后谷底持续抬升才是泄漏。排查四步：监控指标告警（堆占上限比例）；压测放大复现；--inspect 或 heapdump 在操作前后取两次堆快照，Comparison 视图按 Retained Size 找异常增长的对象，沿 Retainers 引用链定位持有者；修复后回归压测。生产要平台化：告警触发自动 dump，保住案发现场。

### Q: 见过哪些典型的 Node 内存泄漏？

满分答案：最经典是「每请求向全局 EventEmitter 注册监听」——全局 client 在请求处理函数里 on('error')，每次请求叠一个闭包，流量一上来 OOM，Node 的 MaxListenersExceeded 警告就是它的前兆；其余高发：模块级缓存无上限只进不出、setInterval 未清理、闭包被全局队列长期持有、连接池/流未释放。共同修法：全局写入必须有界（LRU/TTL）、注册类操作移到初始化阶段、生命周期终点对称清理。

### Q: Node 进程内存有上限吗？怎么调整？

满分答案：V8 老生代堆默认上限约 4GB（64 位，版本有差异），用 --max-old-space-size=8192 调整；Buffer 属于堆外内存不受此限但计入 RSS。注意调大上限只是缓解不是治疗——泄漏照样会到顶，而且堆越大单次 Mark-Sweep 停顿越久；容器环境还要让上限与容器内存配额匹配，否则先被 OOMKilled。
