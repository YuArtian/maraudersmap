# 应用间通信与落地实践

## TL;DR

**通信三板斧：props 注入（主传子）、initGlobalState 全局状态（发布订阅，官方内置）、自建事件总线/共享 store（重通信场景）**。落地踩坑清单是这个主题的面试重头戏：跨域头、publicPath 404、路由 base、UMD 配置、内存释放——每个坑都能反向讲出一条原理。

---

## 1. 通信方案分层

| 方案 | 机制 | 适用 |
|---|---|---|
| **props 注入** | 主应用在注册/挂载时传入数据与回调 | 初始化配置、登录态下发——单向、简单 |
| **initGlobalState**（qiankun 内置） | 发布订阅：setGlobalState / onGlobalStateChange，经 props 交给子应用 | 少量共享状态（用户信息、主题）；业务边界清晰、通信不频繁的场景 |
| 自建 EventBus | 挂在主应用 window 的发布订阅单例（机制见 [[3.04 发布订阅与观察者模式]]） | 跨应用事件通知；注意卸载解绑 |
| 共享状态库 | 主应用建 store（Redux/Pinia 实例）props 下发；或独立的状态微模块 | 重度共享——但要警惕：**通信太重往往说明应用拆分边界错了** |
| URL/storage | 路由参数、localStorage + storage 事件 | 松耦合的低频同步 |

答题收尾句：**「通信量是拆分质量的试金石——频繁双向通信的两个『微应用』多半应该是一个应用」**。

---

## 2. 落地踩坑清单（每条都带原理）

1. **跨域**：qiankun 用 fetch 拉子应用资源（HTML entry 机制，见 [[1.02 qiankun 核心原理]]）——子应用服务必须回 `Access-Control-Allow-Origin` 等头，OPTIONS 预检回 204（原理见 [[1.06 同源策略与跨域]]）；
2. **资源 404**：子应用异步 chunk 按相对路径去了主应用域名——入口顶部注入 `__webpack_public_path__ = window.__INJECTED_PUBLIC_PATH_BY_QIANKUN__`（配套 eslint globals 声明防报错）；
3. **路由冲突**：子应用 History 路由要按激活路径设置 base——`window.__POWERED_BY_QIANKUN__` 判断运行环境；本地独立开发时 devServer 配 `historyApiFallback: true` 防刷新 404（同 [[2.03 Nginx 配置精要]] 的 try_files 逻辑）；
4. **拿不到生命周期**：UMD 没配（library/libraryTarget）或 jsonpFunction 撞名——见 qiankun 原理篇的构建三件套；
5. **内存不释放**：Vue2 子应用 unmount 后实例引用残留（经典 issue）——unmount 里 `instance.$destroy()` 并清空容器 innerHTML；本质是 [[1.05 Node 内存泄漏排查]] 同款的「引用未断」，前端侧用 Memory 面板验证切换前后堆曲线；
6. **Shadow DOM 相关**：开启严格样式隔离后 body 样式失效、e.target 变成 shadowRoot——见 [[1.04 CSS 隔离机制]]；
7. **Vite 子应用报 import 语法错**：eval 执行非 module 脚本不允许 import——沙箱与 ESM 的根本矛盾（见 [[1.03 JS 沙箱机制]]），vite-plugin-qiankun 可绕但官方不推荐，认真上 Vite 考虑无界。

## 3. 实践架构描述模板（讲项目用）

「主应用负责：登录态与权限、全局布局导航、应用注册表与路由分发、全局状态与埋点 SDK；子应用约定：导出生命周期、UMD 构建、独立仓库独立 CI（或 Monorepo 分包，见 [[1.04 Monorepo 与工作区]]）、可独立运行便于开发调试；公共依赖用 externals/Module Federation 共享减重复。」——按「主应用职责 / 子应用约定 / 公共层」三段描述自己的项目最清晰。

## 面试问答

### Q: 微前端应用间怎么通信？

满分答案：分层答——主到子用 props 注入（初始配置、登录态、回调）；全局共享用 qiankun 内置 initGlobalState，本质是发布订阅，setGlobalState 修改、onGlobalStateChange 订阅、卸载时 off；更重的场景自建事件总线或主应用下发共享 store。收尾亮观点：通信应该保持低频小量，双向频繁通信通常说明应用边界划分有问题，宁可合并或重划。

### Q: qiankun 落地遇到过什么问题？

满分答案：挑三四个带原理讲——fetch 加载子应用带来的跨域配置（CORS 头 + 预检 204）；异步 chunk 404 靠运行时注入 publicPath 解决（webpack 动态 publicPath 机制）；子应用路由要按激活路径设 base、用 __POWERED_BY_QIANKUN__ 区分环境；Vue2 子应用卸载不彻底导致内存泄漏，unmount 里手动 destroy 并清容器。每个坑都指向一条底层机制（CORS、JSONP 分包、路由、GC），比罗列现象高一档。

### Q: 为什么 qiankun 对 Vite 支持不好？怎么办？

满分答案：两层矛盾——import-html-entry 需以文本获取并 eval 执行脚本，而 Vite 产物是原生 ESM：import/export 不允许出现在 eval 的普通脚本里，且 ESM 顶层作用域无法被 with 包裹、Proxy 沙箱失去注入点。社区插件（vite-plugin-qiankun）通过改造注入可用但牺牲沙箱；根本解是换隔离原语——无界用同域 iframe 执行 JS 天然隔离，对 Vite 友好；长期看浏览器 ShadowRealm 提案才是标准答案。
