# JS 沙箱机制

## TL;DR

**沙箱要解决的是「子应用改了全局，卸载时还得干净地还回去」**。三代方案：**快照沙箱**（挂载时拍 window 快照、卸载时 diff 还原——单实例、全量遍历慢）→ **Legacy 沙箱**（Proxy 记录变更、还是直接改 window——省遍历仍单实例）→ **Proxy 沙箱**（fakeWindow + Proxy，写进假窗口、读时逃逸到真 window——**多实例并存**的最终形态）。

> Proxy 与 Reflect 的机制基础见 [[1.08 Proxy 与 Reflect]]。

---

## 1. 问题定义

子应用运行会污染全局：挂 window 变量、改原生方法、加定时器与事件监听。切换应用时必须**恢复现场**，否则 A 应用的残留影响 B 应用（同名全局变量、泄漏的 interval）。沙箱 = 给子应用一个「可写不可污染」的全局环境 + 卸载时的副作用清理。

---

## 2. 三代沙箱

**① 快照沙箱（SnapshotSandbox）**——不支持 Proxy 的降级方案：

```js
// 挂载：遍历 window 存快照；卸载：再遍历一次，diff 出子应用的修改
activate()  { this.snapshot = {}; for (const k in window) this.snapshot[k] = window[k]; /* 恢复上次的 modify */ }
deactivate() { for (const k in window) if (window[k] !== this.snapshot[k]) { this.modify[k] = window[k]; window[k] = this.snapshot[k]; } }
```

缺点：两次全量遍历 window（慢）；**直接操作真 window → 同一时刻只能有一个子应用**（单实例）。

**② Legacy 沙箱**：用 Proxy 拦截 set，把「新增/修改了哪些属性」记在小账本上，免去全量遍历——但写入仍落在真 window，**依旧单实例**。

**③ Proxy 沙箱（标准答案，重点讲）**：

```js
class ProxySandbox {
  constructor() {
    const fakeWindow = {};                      // 每个子应用一个假窗口
    this.proxy = new Proxy(fakeWindow, {
      set(target, key, value) {
        target[key] = value;                    // ★ 写：只进 fakeWindow，真 window 零污染
        return true;
      },
      get(target, key) {
        if (key === 'window' || key === 'self') return this.proxy;  // 防逃逸
        return key in target
          ? target[key]                          // 读：先查自己的修改
          : rebind(window[key]);                 // 查不到逃逸到真 window（函数需 bind(window)，防 Illegal invocation）
      },
      has() { return true; },                    // 配合 with 语句的作用域判定
    });
  }
}

// 子应用代码的执行方式：用 with + 严格闭包把 window 换成 proxy
const code = `;(function(window, self, globalThis){ with(window) { ${appJs} } }).bind(proxy)(proxy, proxy, proxy);`;
eval(code);
```

三个精髓：**写读分离**——写只落假窗口（卸载即弃，天然还原），读逃逸到真 window（用得上宿主的一切）；**多实例**——每个子应用各有 fakeWindow，互不可见，可同屏共存；**with + 参数替换**——子应用代码里裸写的 `window.x`/`x` 全被导流到 proxy（`has` 恒真让 with 兜住所有变量查找）。

细节判分点：从真 window 读到的**原生函数要 bind(window)**（`fakeWindow.alert()` 直接调用会 Illegal invocation——this 指向错了，呼应 [[1.04 this 与 call、apply、bind]]）。

## 3. 副作用清理（沙箱的另一半）

全局变量之外还有「动作型污染」，qiankun 逐一打补丁（patch）：

| 副作用 | 处理 |
|---|---|
| setTimeout/setInterval | 记录 id，unmount 时统一 clear |
| addEventListener | 记录 (target, type, fn)，卸载统一 remove |
| 动态插入的 style/script | 劫持 appendChild，卸载时移除节点 |
| history/定位类全局事件 | 同样记录-回放 |

心智模型：**沙箱管「状态还原」，patch 管「行为撤销」**，两者合起来才是完整的隔离。

**ESM 的困境**（现状题）：Proxy 沙箱依赖「用 with/eval 改写执行上下文」，而**原生 ES Module 的顶层作用域无法被 with 包裹**——这就是 qiankun 对 Vite 子应用支持吃力的根源；出路是 iframe 型沙箱（无界，见 [[1.01 微前端概览与选型]]）或浏览器原生提案（ShadowRealm）。

## 面试问答

### Q: qiankun 的 JS 沙箱是怎么实现的？

满分答案：三代演进——快照沙箱在挂载/卸载时全量遍历 window 拍快照与 diff 还原，兼容老浏览器但慢且单实例；Legacy 沙箱用 Proxy 记账省掉遍历，但写入仍污染真 window；Proxy 沙箱给每个子应用建 fakeWindow 并用 Proxy 包装：set 只写假窗口、get 先查假窗口再逃逸真 window（原生函数要 bind 回 window），子应用代码用 with(proxy) + eval 执行使全局访问全部导流——真 window 零污染、天然多实例。配套还有定时器、事件、动态样式的 patch 记录与卸载回放。

### Q: 为什么 Proxy 沙箱能支持多实例而快照沙箱不能？

满分答案：快照/Legacy 沙箱的写入都发生在唯一的真 window 上，两个子应用同时活跃必然互相覆盖，只能在切换时序列化地还原-恢复；Proxy 沙箱把写操作重定向到每个应用私有的 fakeWindow，读操作按「自己 → 真 window」的链查找，各应用的修改互不可见——同屏多个微应用（主页聚合仪表盘场景）因此可行。本质是「共享基座 + 私有写层」，思想同写时复制。

### Q: 沙箱方案对 Vite/ESM 子应用为什么支持不好？

满分答案：Proxy 沙箱的生效前提是能用 with 包裹子应用代码、把全局变量查找导流到代理——这要求以文本形式拿到 JS 并 eval；原生 ESM 由浏览器直接加载执行，顶层作用域封闭，无法注入 with 上下文，import 语句也不能出现在 eval 里。所以 Vite 子应用要么退化打包格式，要么换隔离原语：无界用同域 iframe 跑 JS（原生硬隔离），标准层面的长期答案是 ShadowRealm 提案。
