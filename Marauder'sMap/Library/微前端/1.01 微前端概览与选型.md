# 微前端概览与选型

## TL;DR

**微前端的核心价值是「技术栈无关」：多团队各自独立开发、独立部署，在浏览器里聚合成一个产品**。iframe 天然隔离但有四宗罪（UI 不同步、通信难、性能差、URL 不同步），所以才有 qiankun（HTML entry + JS 沙箱）、无界 wujie（iframe 执行 JS + Shadow DOM 渲染）、Module Federation（构建层共享模块）三条技术路线。

---

## 1. 什么问题值得上微前端

三个真实动机：**巨石应用解体**（单仓构建十几分钟、发布互相排队）；**跨团队自治**（各团队独立技术栈、独立发布节奏）；**遗留系统渐进迁移**（老 AngularJS/jQuery 应用与新 Vue/React 共存过渡）。

一句要说的反话（工程判断加分）：**同团队、同技术栈、无独立部署需求就别上微前端**——沙箱、通信、样式隔离的复杂度是实打实的税；Monorepo + 良好模块边界（见 [[1.04 Monorepo 与工作区]]）往往是更便宜的解。

---

## 2. 为什么不直接用 iframe

隔离是完美的，但四宗罪（qiankun 作者的经典论述）：

1. **UI 不同步**：DOM 硬隔离——子应用里的「全局居中弹窗」只能在 iframe 区域内居中，遮罩盖不满全屏；
2. **通信困难**：全局上下文完全隔离，只能 postMessage 序列化通信；cookie/storage 跨域场景更麻烦；
3. **性能差**：每次加载子应用都是完整的浏览器上下文重建，慢且内存高；
4. URL 不同步：iframe 内路由变化不反映到地址栏，刷新即丢状态（可解但别扭）。

但 iframe 并未出局——**无界的聪明处正是「只用 iframe 跑 JS，不用它渲染」**，取其隔离弃其 UI 之罪（见下）。

---

## 3. 三条技术路线对比

| | qiankun | 无界 wujie | Module Federation |
|---|---|---|---|
| 加载方式 | **HTML entry**：拉取子应用 HTML 解析出资源执行 | iframe 加载执行 JS + **Shadow DOM** 渲染 UI | **构建期声明共享**，运行时按需拉远程模块 |
| JS 隔离 | 自实现沙箱（Proxy，见 [[1.03 JS 沙箱机制]]） | **原生 iframe 隔离**（同域 iframe） | 无沙箱（同一上下文，靠规范） |
| CSS 隔离 | 劫持/前缀方案（见 [[1.04 CSS 隔离机制]]） | **原生 Shadow DOM** | 无 |
| 技术栈无关 | ✔ | ✔ | 半（需同为 webpack 系构建，共享依赖版本需协调） |
| Vite 子应用 | 原生 ESM 支持费劲（沙箱难改写 ESM） | ✔ 支持 | vite 有社区插件 |
| 特色 | 生态最成熟、基于 single-spa | 保活、预执行（requestIdleCallback 分片跑 JS 的 fiber 模式）、DOM 操作由 proxy 代理回 shadowRoot | **共享粒度是模块**而非应用：适合共享组件/工具而非整页聚合 |

无界的架构一句话：**JS 在同域 iframe 里执行（天然隔离 + 保活），DOM 渲染在主文档的 Web Component + Shadow DOM 里（天然样式隔离 + 弹窗可全屏），中间用 proxy 把 iframe 里的 document 操作转发到 shadowRoot**——用两个原生能力各取所长，代价是实现精巧、心智更绕。

选型口径：主流聚合场景 qiankun（生态、文档、可搜索的坑最多）；要保活/Vite/隔离更强选无界；「共享的是模块不是页面」（跨应用复用组件库、公共逻辑）选 Module Federation——它其实不是同一层的东西，常与前两者组合使用。

## 面试问答

### Q: 什么是微前端？解决什么问题？什么时候不该用？

满分答案：把多个可独立开发、独立部署的前端应用在运行时聚合成一个产品的架构风格，核心价值是技术栈无关与团队自治——解决巨石应用构建发布互相拖累、多团队协作冲突、遗留系统渐进迁移三类问题。反面判断同样重要：同团队同栈无独立部署诉求时，沙箱与通信的复杂度得不偿失，Monorepo 加模块边界是更简单的解。

### Q: 为什么不用 iframe 做微前端？

满分答案：iframe 隔离完美但代价大——DOM 不共享导致子应用弹窗无法全屏居中（UI 不同步）；全局上下文隔离使通信只剩 postMessage、cookie 处理麻烦；每次加载都重建完整浏览器上下文，性能和内存差；URL 不同步刷新丢状态。补一笔反转：无界方案保留 iframe 只做 JS 执行容器、DOM 渲染搬回主文档 Shadow DOM，说明 iframe 的问题在「拿它渲染 UI」而非隔离本身。

### Q: qiankun、无界、Module Federation 怎么选？

满分答案：qiankun——HTML entry 加自研沙箱，生态最成熟，适合标准的多应用聚合，短板是 Vite/ESM 支持吃力、沙箱是模拟的；无界——iframe 跑 JS 天然隔离、Shadow DOM 渲染天然样式隔离，支持保活与预执行、对 Vite 友好，实现更精巧；Module Federation 是构建层方案，共享粒度是模块，无沙箱，适合跨应用共享组件与逻辑，常与前两者互补而非互斥。按「聚合页面还是共享模块、要不要保活、构建工具是什么」三问定选型。
