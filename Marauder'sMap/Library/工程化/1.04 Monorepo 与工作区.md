# Monorepo 与工作区

## TL;DR

**Monorepo = 多个相关项目放进一个仓库统一管理：依赖一处声明、内部包直接引用、跨包改动一次提交**。地基是包管理器的 workspace（内部包用符号链接互连 + `workspace:*` 协议），规模化后再叠加任务编排层（Turborepo/Nx 的拓扑调度与增量缓存）。

---

## 1. 为什么要 Monorepo

MultiRepo 的痛：公共代码复用靠发包，「改组件 → 发版 → 各项目升级」链路漫长；版本对齐困难（A 项目用 utils@1、B 用 utils@3）；跨项目改动要开多个 PR 难以原子化；构建与规范各自为政。

Monorepo 的收益对应四条：**复用零成本**（内部包直接 import，改动即时生效）、**依赖统一治理**（一份 lock，版本收敛可检索所有使用方）、**原子提交**（跨包改动 + 用例在一个 PR 里）、**工程设施共享**（一套 lint/构建/CI 模板）。

代价也要会说：仓库体积与拉取时间（缓解：git sparse-checkout 稀疏检出、shallow clone）、权限边界粗（git 天然按仓库授权）、CI 不做增量的话全量构建爆炸——所以**工具链是 Monorepo 成败的关键**。

---

## 2. workspace 机制（以 pnpm 为例）

```yaml
# pnpm-workspace.yaml
packages:
  - 'packages/*'
  - 'apps/*'
```

```json
// apps/web/package.json
"dependencies": {
  "@proj/ui": "workspace:*"      // workspace 协议：链接本仓库内的包
}
```

机制三要点：

1. **符号链接互连**：`@proj/ui` 在 web 的 node_modules 里是指向 `packages/ui` 源码目录的软链——改 ui 无需发版，web 立刻可见（配合 pnpm 的链接结构，见 [[1.03 npm、yarn 与 pnpm]]）；
2. **`workspace:*` 协议**：强制解析到仓库内版本，杜绝「不小心装了线上旧版」；**发布时**由 pnpm 自动替换为真实版本号；
3. 依赖提升与隔离仍由包管理器保证；公共 devDependencies（typescript、eslint）装在根，业务依赖装在各包。

常用命令形态：`pnpm --filter @proj/ui build`（指定包）、`--filter ...@proj/ui`（它和依赖它的全部）——filter 语法是日常操作核心。npm/yarn 的 workspaces 字段同理但功能较薄。

## 3. 任务编排层：Turborepo / Nx

包多了之后「按依赖顺序构建 + 只构建受影响的」成为刚需：

- **拓扑调度**：`build` 依赖 `^build`（先构建上游依赖包），并行度自动最大化；
- **增量缓存**：以「输入文件 + 命令 + 环境」哈希为 key 缓存任务产物，命中即秒过；**远程缓存**让 CI 与同事间共享缓存命中；
- **受影响范围（affected）**：对比 git diff 只跑受影响包的构建与测试——Monorepo CI 不爆炸的关键。

选型口径：Turborepo 轻、配置少、够用为止；Nx 重、带代码生成与依赖图可视化，适合超大规模。版本发布配 **Changesets**（PR 里声明变更 → 自动算版本、生成 changelog、串行发包）。

## 4. 目录形态参考

```text
repo/
├─ apps/          # 应用（web、admin、docs）
├─ packages/      # 共享库（ui、utils、config、tsconfig）
├─ pnpm-workspace.yaml
├─ turbo.json     # 任务管线
└─ package.json   # 根：脚本 + 公共 devDeps
```

## 面试问答

### Q: Monorepo 解决了什么问题？有什么代价？

满分答案：解决 MultiRepo 的四痛——公共代码复用要走「发版-升级」长链路、多项目依赖版本发散、跨项目改动无法原子提交、工程设施重复建设。Monorepo 内部包直接链接引用、一份 lock 统一治理、一个 PR 完成跨包变更、共享一套规范与 CI。代价：仓库膨胀（sparse-checkout/浅克隆缓解）、权限粒度粗、CI 必须配增量方案否则全量构建不可接受——所以它是「仓库形态 + 工具链」的整套实践，不只是把代码堆一起。

### Q: pnpm workspace 是怎么工作的？workspace:* 是什么？

满分答案：pnpm-workspace.yaml 声明包位置；安装时内部包之间用符号链接互连，@proj/ui 在使用方的 node_modules 里直接指向源码目录，修改即时生效无需发版。workspace:* 是协议前缀，强制解析仓库内版本、防止误装远程旧版，发布时 pnpm 自动替换成真实 semver。日常用 --filter 圈定操作范围（单包、含上下游）。根放公共 devDeps，各包放自己的业务依赖。

### Q: Turborepo/Nx 在 Monorepo 里扮演什么角色？

满分答案：包管理器解决「装依赖和连包」，它们解决「跑任务」——按包依赖图做拓扑排序与最大并行（build 依赖 ^build）；以输入哈希做增量缓存，本地与远程共享，未变更的包直接命中跳过；affected 机制按 git diff 只构建测试受影响的包。这三件事让几十个包的 CI 时间保持在分钟级。发布侧交给 Changesets 做版本推导与 changelog。
