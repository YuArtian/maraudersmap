# Tree Shaking 与按需引入

## TL;DR

**Tree Shaking = 基于 ESM 静态结构，标记未被使用的导出并在压缩阶段删除**。三个前提缺一不可：ESM 语法（CJS 不行）、生产模式（usedExports 标记 + Terser 删除）、**没有副作用干扰**——package.json 的 `sideEffects` 就是你向 webpack 承诺「这些文件删了没事」的契约。

---

## 1. 原理：为什么只有 ESM 能摇

CJS 的 require 是运行时函数调用，导出对象可以动态增删——**不执行就不知道用了什么**；ESM 的 import/export 必须在顶层、静态可分析（见 [[1.01 JS 模块化演进：CommonJS 与 ESM]]），编译期就能画出「谁导出了什么、谁用了什么」的精确图。

webpack 的两步协作：

1. **标记**（webpack，`optimization.usedExports`）：分析后给未使用的导出打注释 `/* unused harmony export */`，代码还在；
2. **删除**（Terser 压缩阶段）：DCE（死代码消除）把未引用的函数体真正剔掉。

所以：开发模式看不到效果是正常的（mode: production 才全链路开启）；`babel-loader` 必须**关掉模块转换**（preset-env 的 `modules: false`，现代默认如此）——ESM 先被转成 CJS 的话，Tree Shaking 直接失明。

---

## 2. sideEffects：最容易翻车的一环

「用没用到」之外还有一问：**删掉它有没有副作用**？`import './polyfill.js'`、`import 'antd/dist/reset.css'` 这类「只引入不取值」的语句，模块的价值全在执行的副作用里。

package.json 的 `sideEffects` 是**包作者的声明**：

```json
{ "sideEffects": false }            // 我的所有文件都无副作用，随便摇
{ "sideEffects": ["*.css", "./src/polyfill.js"] }   // 除这些外随便摇
```

经典事故：库声明了 `sideEffects: false`，使用者 `import 'lib/style.css'` 在生产构建里被整条摇掉——**样式丢了，而且开发模式一切正常，上线才炸**（tree shaking 只在 production 生效）。所以发库带 CSS 的必须把样式文件列进 sideEffects。

`/*#__PURE__*/` 注释是函数调用级别的补充声明：标记「这个调用无副作用，返回值没人用就可删」，构建工具产物里常见。

---

## 3. 按需引入实战（lodash 是标准考题）

```js
import _ from 'lodash';           // ✗ 整包 70KB+：lodash 是 CJS，摇不动
import debounce from 'lodash/debounce';   // ✓ 路径直达，只打这一个
import { debounce } from 'lodash-es';     // ✓ ES 模块版，天然可摇（推荐）
```

四种手段按机制分类：

| 手段 | 机制 |
|---|---|
| 换 ESM 版（lodash-es） | 让 Tree Shaking 生效 |
| 路径引入（lodash/debounce） | 绕过入口，物理上只引一个文件 |
| babel-plugin-lodash / babel-plugin-import | 编译期把命名导入**改写**成路径引入（antd 老版本按需加载同思路） |
| 现代组件库的 exports + ESM | 无需插件，import { Button } 直接可摇 |

配套认知：**能被摇的库自己要「摇友好」**——发 ESM 产物、无顶层副作用、正确声明 sideEffects；这也是 lodash-es、date-fns 逐渐替代旧包的原因。

---

## 4. 验证与排查

- 产物分析：BundleAnalyzerPlugin 看某个库是整包还是片段进来了；
- 排查不生效的常见原因清单：**Babel 把 ESM 转成了 CJS**、导入的库只有 CJS 产物、sideEffects 未声明导致 webpack 保守保留、代码里存在「取整个命名空间再动态访问」（`import * as utils` 后 `utils[key]`）——动态访问让静态分析放弃；
- Rollup/Vite（生产用 Rollup）的 Tree Shaking 更激进，机制相同（见 [[2.06 Webpack、Vite 与 Rollup 对比选型]]）。

## 面试问答

### Q: Tree Shaking 的原理？为什么 CommonJS 不行？

满分答案：依赖 ESM 的编译期静态结构——import/export 顶层声明、不可动态拼接，构建器无需执行代码即可标记每个导出是否被使用（webpack 的 usedExports），再由 Terser 在压缩阶段做死代码删除。CJS 的 require 是运行时调用、exports 可动态修改，静态分析无法保证安全删除。补充链路细节：Babel 需保持 ESM 不转 CJS，效果只在 production 模式完整呈现。

### Q: sideEffects 是干什么的？配置错了会怎样？

满分答案：package.json 里包作者对副作用的声明——false 表示所有模块删除无害，数组列出必须保留的文件（典型是 *.css 和 polyfill）。它解决「import 'xxx' 只为副作用」的语句会不会被误删的问题。配置错的经典事故：库声明 false 但用户引它的 CSS，生产构建把样式摇没，且开发模式正常、上线才暴露。函数级的对应物是 /*#__PURE__*/ 注释。

### Q: lodash 怎么按需引入？

满分答案：优先用 lodash-es 配合命名导入，ESM 天然可摇；或路径直达 import lodash/debounce 物理隔离；存量代码用 babel-plugin-lodash 在编译期自动改写成路径引入。原理归因：lodash 主包是 CJS 摇不动，所以手段要么换 ESM、要么绕过入口、要么编译期改写。延伸：选型时偏好「摇友好」的库（ESM 产物 + sideEffects 声明正确），date-fns 替代 moment 是同一逻辑。

### Q: 怎么确认 Tree Shaking 生效了？不生效怎么查？

满分答案：BundleAnalyzerPlugin 看产物里目标库的体积与内容，或搜产物里未使用导出的函数名。不生效按链路排查：Babel/TS 是否把 ESM 编译成 CJS（preset-env modules: false、tsconfig module 设 ESNext）；库是否只有 CJS 产物；sideEffects 是否缺失导致保守保留；代码是否存在 import * 后动态取属性这类打断静态分析的写法；是否在 development 模式下看效果（只标记不删除）。
