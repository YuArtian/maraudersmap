# Babel 与编译体系

## TL;DR

**Babel 三段式：parse（源码→AST）→ transform（插件遍历改写 AST）→ generate（AST→新源码）**。语法降级靠插件，**API 缺失靠 polyfill**——preset-env 读 browserslist 决定「转多少、补多少」。CSS 侧的对应物是 PostCSS（autoprefixer、px 转换同一套 AST 思路）。

---

## 1. 三段式流水线

```mermaid
flowchart LR
    A["源码"] -- "@babel/parser<br/>词法+语法分析" --> B["AST<br/>(ESTree 规范的 JSON 树)"]
    B -- "@babel/traverse<br/>访问者模式遍历<br/>插件在此改写节点" --> C[新 AST]
    C -- "@babel/generator<br/>打印 + sourcemap" --> D[目标代码]
```

- **parse**：词法分析切 token、语法分析建树（与 [[V8 引擎与 JIT 编译]] 的前端一致，只是产物用途不同）；
- **transform**：核心在**访问者模式**——插件声明「我关心哪种节点」（`ArrowFunctionExpression`、`OptionalMemberExpression`…），traverse 深度优先走到对应节点时回调，插件用 @babel/types 增删改节点；
- **generate**：把新 AST 序列化回代码，同步生成 sourcemap。

**Babel 本身只是平台**：不装插件时输出 ≈ 输入。所有能力都是插件——语法转换插件、JSX 编译（见 [[1.01 JSX、React Element 与 $$typeof]]）、按需引入改写（babel-plugin-import，见 [[2.03 Tree Shaking 与按需引入]]）。preset 是插件套餐：preset-env / preset-react / preset-typescript（TS 走「直接删类型」路线，不做类型检查）。

写一个极简插件感受一下：

```js
// 把 console.log 调用移除
module.exports = () => ({
  visitor: {
    CallExpression(path) {
      if (path.get('callee').matchesPattern('console.log')) path.remove();
    },
  },
});
```

## 2. 语法 vs API：降级的两条腿（最重要的辨析）

- **语法降级**：箭头函数、可选链、class——编译期就能改写成旧语法，**插件解决，不增加运行时**；
- **API 补齐**：Promise、Array.prototype.includes、globalThis——旧环境**根本没有这个东西**，改写语法救不了，必须注入 **polyfill**（core-js 实现）。

`@babel/preset-env` 把两件事统一调度：读 **browserslist**（`.browserslistrc` / package.json 的 browserslist 字段）目标环境 → 查兼容性数据表 → 只启用目标缺失的转换插件 + 按 `useBuiltIns` 策略注入 polyfill：

| useBuiltIns | 行为 |
|---|---|
| `false` | 不管 polyfill（默认） |
| `entry` | 入口 import core-js，按目标环境展开全量所需 |
| `usage` | **按代码实际用到的 API 注入**，体积最优 |

库作者的正确姿势：`@babel/plugin-transform-runtime` + corejs 选项——polyfill 以模块导入方式隔离，**不污染全局**（应用可以污染全局，库不行）；顺带复用 helpers 减少重复注入。

**browserslist 是编译体系的总开关**：preset-env、autoprefixer、Vite 的 legacy 插件都读它——收紧目标浏览器 = 更少转译 + 更少 polyfill = 更小产物（呼应 [[2.04 代码分割与构建优化实战]]）。

现状补充：纯转译已多被 **SWC/esbuild** 替代（快一个数量级），但 Babel 仍是**自定义 AST 改写**（codemod、DSL、框架编译宏）的首选平台——「Babel 会不会被淘汰」的答案是分层的。

## 3. CSS 侧：PostCSS 同构思想

PostCSS = CSS 界的 Babel：CSS → AST → 插件改写 → 输出。常用插件：

- **autoprefixer**：按 browserslist 补厂商前缀；
- **postcss-pxtorem / px2rem**：构建期把 px 按根字号换算成 rem——移动端适配「设计稿 750px、rem 布局」流水线的一环（运行时配合动态设置 html font-size）；现代替代是直接写 vw 或 clamp()；
- cssnano（压缩）、postcss-preset-env（未来语法降级）。

答题连线：「JS 的语法/兼容问题 Babel 管，CSS 的对应问题 PostCSS 管，两者共享 browserslist 目标声明」——体系感一句话拉满。

## 面试问答

### Q: Babel 的工作原理？

满分答案：三段式——parser 做词法语法分析生成 ESTree 规范的 AST；traverse 以访问者模式深度优先遍历，插件注册对关心节点类型的回调、用 babel-types 改写树；generator 把新 AST 打印成代码并产 sourcemap。Babel 核心只是管道，一切转换来自插件，preset 是插件集合。可现场举例：移除 console 的插件就是在 CallExpression 节点上匹配 callee 并 remove。

### Q: polyfill 和语法转换的区别？preset-env 怎么配？

满分答案：语法问题（箭头函数、可选链）编译期改写即可、零运行时成本；API 问题（Promise、includes）是环境缺实现，必须注入 core-js polyfill。preset-env 读 browserslist 目标，按需启用转换插件；polyfill 策略用 useBuiltIns——usage 按实际使用注入最省体积，entry 按目标全量展开。区分身份：应用可全局污染式注入；库要用 transform-runtime 的隔离方案避免污染使用方全局，并复用 helpers。

### Q: browserslist 在工程里扮演什么角色？

满分答案：整个编译体系的统一目标声明——Babel preset-env 据它决定转译和 polyfill 范围，autoprefixer 据它补 CSS 前缀，Vite legacy 据它划分现代/传统产物。价值在单点控制：调整一行目标配置（如放弃 IE），JS 转译量、polyfill 体积、CSS 前缀同步收缩，是产物瘦身时最容易被忽略的开关。

### Q: 移动端 px 转 rem 是怎么实现的？

满分答案：构建期 PostCSS 插件（postcss-pxtorem）在 CSS AST 上按「设计稿基准 ÷ 根字号」把 px 声明改写成 rem；运行时配合脚本按屏宽动态设置 html 的 font-size，实现等比缩放。要点：转换发生在编译期、对源码无侵入，可配忽略清单（边框 1px 类）。补充现状：viewport 单位（vw/clamp）方案已可不依赖 JS，新项目常直接用 postcss-px-to-viewport 或原生写法。
