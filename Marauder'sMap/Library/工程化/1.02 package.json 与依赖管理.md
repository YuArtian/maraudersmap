# package.json 与依赖管理

## TL;DR

**package.json 描述「这个包是什么、入口在哪、依赖谁」，lock 文件把「语义化版本范围」冻结成「精确版本 + 完整依赖树」——两者配合才有可复现的安装**。依赖三兄弟按「谁用、何时用」区分：dependencies 运行要、devDependencies 开发要、peerDependencies 要求宿主提供。

> 版本号语义（`^ ~` 与 major.minor.patch）见 [[语义版本控制 SemVer]]；`npm i` 与 `npm ci` 的行为差异见 [[npm i & npm ci]]。

---

## 1. 关键字段速查

**身份与入口**：

| 字段 | 作用 |
|---|---|
| `name` / `version` | 包身份；发布必需 |
| `main` | CJS 入口（默认 index.js） |
| `module` | ESM 入口（bundler 约定，非官方标准） |
| `types` | TS 类型声明入口 |
| `browser` | 浏览器环境替代入口 |
| **`exports`** | **现代标准**：细粒度导出映射 + 条件分发（import/require/types），一旦声明就**封锁未列出的深层路径** |
| `type` | `"module"` 时 .js 按 ESM 解析（见 [[1.01 JS 模块化演进：CommonJS 与 ESM]]） |

```json
"exports": {
  ".": {
    "types": "./dist/index.d.ts",
    "import": "./dist/index.mjs",
    "require": "./dist/index.cjs"
  },
  "./utils": "./dist/utils.mjs"
}
```

**scripts 与钩子**：`pre`/`post` 前缀自动串联（`prebuild` → `build` → `postbuild`）；`preinstall` 常见用法——`npx only-allow pnpm` 锁定包管理器；`prepare` 在 install 后执行，husky 的安装点（见 [[3.03 Git 钩子与工程规范]]）。相关字段 `packageManager` + corepack 可锁定包管理器版本。

**其他常问**：`files`（发布白名单）、`sideEffects`（Tree Shaking 提示，见 [[2.03 Tree Shaking 与按需引入]]）、`engines`（Node 版本要求）、`workspaces`（见 [[1.04 Monorepo 与工作区]]）。

## 2. 依赖三兄弟 + 两个偏门

| 字段 | 语义 | 安装行为 |
|---|---|---|
| `dependencies` | 运行时需要 | 被依赖时**级联安装** |
| `devDependencies` | 只在开发构建时需要（构建器、测试、lint） | 作为依赖被安装时**不装** |
| `peerDependencies` | **要求宿主提供**，自己不带 | npm 7+ 自动安装并做冲突校验；pnpm 只校验不代装 |
| `optionalDependencies` | 装失败也不中断 | 可选原生模块常用 |
| `bundledDependencies` | 打进发布包 | 极少用 |

**peerDependencies 的真实用途**（高频）：插件类库声明「我需要和宿主共用同一个 React」——若把 react 写进 dependencies，宿主可能出现**两份 React 实例**（hooks 直接报错）。`peerDependenciesMeta: { xxx: { optional: true } }` 声明可选 peer，宿主没装也不警告。

应用（不发布的业务项目）里 dep/devDep 的区分对产物**没有实际影响**（打包器按 import 收集），但仍应按语义维护——CI 裁剪、审计与心智一致性。

## 3. lock 文件：可复现安装的基石

package.json 里写的是**范围**（`^18.2.0`），不同时间安装可能得到不同小版本；lock 文件（package-lock.json / pnpm-lock.yaml / yarn.lock）记录**整棵依赖树的精确版本 + 下载地址 + integrity 哈希**（内容校验 + 缓存命中）。

规则三条：**lock 必须提交**到仓库；CI 用 `npm ci`（严格按 lock 安装，lock 与 package.json 不一致直接报错，还更快）；升级依赖用显式命令（`npm update` / 改版本重装）产生 lock diff 走 code review。integrity 校验（sha512）同时防供应链篡改。

---

## 4. 版本管理：npm version 与发布节奏

`npm version patch|minor|major` 自动改版本号 + 打 git tag；预发布链路：

```text
1.2.3 → premajor → 2.0.0-0 → prerelease → 2.0.0-1 → major → 2.0.0
```

规律一句话：**pre\* 升位并挂预发布号，prerelease 只累加预发布号，正式 major/minor/patch 在有预发布号时「转正」而不再升位**。配合 dist-tag（`npm publish --tag beta`）让用户显式安装测试版。语义细节见 [[语义版本控制 SemVer]]。

## 面试问答

### Q: dependencies、devDependencies、peerDependencies 的区别？

满分答案：dependencies 是运行时依赖，包被安装时级联安装；devDependencies 只服务于开发与构建，作为依赖被引用时不会安装；peerDependencies 声明「宿主必须提供」的共享依赖，典型是插件要求与宿主共用同一个 React/Vue 实例，避免双实例问题——npm 7+ 会自动安装并校验版本冲突，可选 peer 用 peerDependenciesMeta 标记。补充：业务应用里 dep/devDep 对打包产物无实际影响（按 import 收集），但按语义维护利于审计。

### Q: package-lock.json 有什么用？要提交吗？

满分答案：把 package.json 的版本范围冻结为整棵依赖树的精确版本、来源 URL 和 integrity 哈希，保证任何人任何时间安装结果一致，integrity 还能校验内容防篡改。必须提交；CI 里配 npm ci——删掉 node_modules 严格按 lock 装，不一致即失败。依赖升级应显式进行并让 lock 变更过 review，而不是靠重装「碰运气」。

### Q: main、module、exports 字段的关系？

满分答案：main 是传统 CJS 入口；module 是社区约定的 ESM 入口（打包器认，Node 不认）；exports 是现代官方标准——支持子路径映射和条件导出（import/require/types/browser 分发不同文件），且具有封装性：声明后未列出的内部路径外部无法 require。优先级上支持 exports 的工具先看它。库作者双格式发包就靠 exports 按条件分发 ESM 与 CJS 产物。

### Q: npm version 的 major/minor/patch 和 pre 系列怎么用？

满分答案：正式版三连对应 SemVer 三位——破坏性变更 major、向后兼容新功能 minor、bug 修复 patch，命令自动改号并打 tag。预发布：premajor/preminor/prepatch 升位并加 -0 预发布号，prerelease 只递增预发布号，最后跑对应正式命令「转正」（2.0.0-1 → 2.0.0 不再升位）。发布配 --tag beta 挂 dist-tag，避免测试版被默认 latest 拉到。
