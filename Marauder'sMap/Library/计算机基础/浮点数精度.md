# 浮点数精度与 IEEE 754

## TL;DR

**电脑用二进制存小数,像 32.3 这种数根本存不准,只能存一个最接近的近似值;单精度盒子小、误差大到看得见,双精度盒子大、误差小到被显示规则藏住。**

- 32.3 转成二进制是无限循环小数(像十进制的 1/3),任何有限位数都存不下 → 只能四舍五入到最近的可表示值。
- 单精度(float32)= 32 位盒子,双精度(float64)= 64 位盒子;盒子分成「符号 + 指数 + 尾数」三段,**尾数位决定精度**(单 23 位 ≈ 7 位十进制,双 52 位 ≈ 15–16 位)。
- 两个都比 32.3 小一丁点:单精度差在第 7 位(看得见),双精度差在第 16 位(看不见)。
- 平时显示正常是因为「最短可还原」显示规则把误差藏了;一旦单精度值被加宽成双精度,藏不住了,长串就冒出来。
- 实战教训:体成分/金额这类值别用 float32 存;前端不该靠四舍五入给后端兜底,该在落库/计算层定死精度。

---

## 1. 为什么 32.3 存不准

电脑存小数用二进制(base-2)。`32.3` 换算成二进制是:

```text
32.3 = 100000.01001100110011001100110011...
                 └──── 0011 无限循环,除不尽 ────┘
```

就像十进制里 `1/3 = 0.3333…` 永远写不完一样,`32.3` 在二进制下也是无限循环小数。盒子只有固定位数,装不下无限串,**只能存一个最接近的近似值**。这一条单精度、双精度都逃不掉——区别只是近似得有多准。

> 经验法则:一个小数能不能用二进制精确表示,看它能不能写成「分母是 2 的幂」的分数。0.5(=1/2)、0.25(=1/4)可以;0.1、0.3、0.2 都不行。

---

## 2. 单精度 23 位、双精度 52 位是怎么来的

数字的盒子大小是硬件定死的:**单精度 32 位、双精度 64 位**(内存按 2 的幂组织)。IEEE 754 标准把每个盒子切成三段:

```text
单精度 (32 位):
[ 符号 1 ][   指数 8   ][        尾数 23        ]
  1  +  8  +  23  =  32

双精度 (64 位):
[ 符号 1 ][    指数 11    ][              尾数 52              ]
  1  +  11  +  52  =  64
```

| 段 | 作用 | 多给一点会怎样 |
|---|---|---|
| 符号位 | 正还是负 | 1 位就够 |
| 指数位 | 决定能表示多大/多小(**范围**) | 越多 → 数量级范围越大 |
| 尾数位 | 决定有几位有效数字(**精度**) | 越多 → 越精确 |

所以 **23 和 52 不是随便定的,是盒子总位数减掉符号位和指数位后剩下的**。盒子总大小固定,指数和尾数互相抢格子;双精度盒子翻倍多出的 32 格,大头给尾数(精度 23→52)、小头给指数(范围 8→11)。

**有效精度还要 +1**:规范化后整数部分永远是 `1.xxx`,这个开头的 `1` 不用存(隐含位),所以:

| | 尾数位 | 实际有效位 | ≈ 十进制有效数字 |
|---|---|---|---|
| 单精度 | 23 | 24 | ~7 位 |
| 双精度 | 52 | 53 | ~15–16 位 |

---

## 3. 怎么算出「实际存进去的值」—— 三步

以 `32.3` 为例:

**第 1 步:转二进制、规范化**

```text
32.3 = 1.00000100110011001100110011001100… × 2⁵
         └──────── 尾数,要塞进固定位数的盒子 ────────┘
```

**第 2 步:按盒子位数砍断 + 四舍五入**(看砍掉的下一位决定进位还是舍去)

```text
单精度只留 23 位:
1.00000100110011001100110 | 0110011…   ← 砍掉部分以 0 开头 → 舍 (round down)
                          ↑第23位       → 结果比 32.3 小一点
```

双精度留 52 位,砍在更靠后的地方,同样四舍五入。

**第 3 步:把砍好的二进制乘回 2⁵、转回十进制** = 真实存进去的值:

| | 实际存进去的精确值 | 离 32.3 差多少 |
|---|---|---|
| 单精度 | 32.**2999992**37060546875 | −0.00000076(第 **7** 位) |
| 双精度 | 32.**29999999999999**71578… | −0.0000000000000028(第 **16** 位) |

盒子越大 → 砍得越靠后 → 误差越小。**两个都比 32.3 小,只是单精度小得「看得见」。**

> 32 附近,相邻两个单精度数之间的最小间隔(ULP)≈ 3.8×10⁻⁶(约百万分之四)。32.3 卡在两个刻度中间,被迫挪到最近的那一格。

## 4. 为什么单精度露馅、双精度还显示 32.3

关键:电脑显示浮点时**不会把全部数字念出来,只念「能唯一还原回这个值的最短小数」**(shortest round-trip)。

| 存的值 | 离 32.3 | 最短可还原写法 | 屏幕显示 |
|---|---|---|---|
| 双精度 `32.299999999999997…` | 极近(第 16 位才差) | `32.3` | **32.3** |
| 单精度 `32.299999237060546875` | 已差到第 7 位 | `32.29999923706055` | **32.29999923706055** |

- 双精度存的值离 32.3 太近,`32.3` 就是能还原回它的最短标签 → 显示干净的 `32.3`。
- 单精度存的值离 32.3 太远,`32.3` 还原不回它了,最短标签变成那个长串 → 露馅。

**误差一直都在,只是单精度的误差大到「最短写法」也藏不住。** 而且这串长数字往往是把单精度值**加宽成双精度**后才暴露的(存进 double 列、转成 Python/JS 的 float),因为换了高分辨率的尺子,藏不住了。

照相机比喻:单精度 = 低像素拍照,小屏看(单精度显示)挺清楚,放大到大屏(双精度)马赛克就露出来。

## 5. 实战:一次真实的 bug

现象:页面体脂率显示 `32.29999923706055 %`。追查链路:

```text
体脂秤/Vital 源 (float32 上报)
   ↓ 加宽存入
series_data.value (double precision) ← 噪声已带进来
   ↓ SQL: INSERT ... SELECT value
th_series_data.value (TEXT) ← double→text 隐式转换,噪声冻成字符串
   ↓ 如实读出
后端 API / 前端页面 ← 原样显示
```

要点:

- **JSON 传输不会产生这种噪声**(JSON 数字是十进制文本,`"32.3"` 解析回来还是干净的 32.3)。出现 float32 痕迹,说明值在**源头**就是二进制单精度。
- TEXT 列把噪声**冻死**了,下游无法还原(再 `::float` 解出来还是那个长串)。
- 修复要在**写入/计算层**:落库时定精度(如 `ROUND(value, 1)`),或源头别用单精度。**前端不该用四舍五入给后端数据兜底**——那是掩盖,职责该各归各层。

判断「这个长串是不是 float32 痕迹」:把目标值用单精度往返一次,看是否相等。

```text
32.3 →(存 float32 再读 float64)→ 32.29999923706055   ✓ 命中,确认是单精度痕迹
```
