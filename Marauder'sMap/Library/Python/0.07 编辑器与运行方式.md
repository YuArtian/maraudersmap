# 编辑器与运行方式

## TL;DR

**运行 Python 代码有四种入口，用途完全不同**：

| 入口 | 命令 | 什么时候用 |
|---|---|---|
| 脚本 | `python hello.py` | 跑一个文件，最常用 |
| REPL | `python` | 试一行语法、探一个 API |
| 内联 | `python -c "print(1)"` | 在 shell 脚本里嵌一句 Python |
| 模块 | `python -m http.server` | 把一个模块/包当命令跑 |

**编辑器选 VSCode 或 PyCharm 都行**，选择本身不重要；重要的是配对三件事：**解释器指对**、**保存自动格式化**、**缩进 4 空格**。

其中「解释器指对」是新手 90% 报错的根源——`ModuleNotFoundError` 几乎总是因为编辑器跑的那个 `python` 不是你装包的那个 `python`（见第 4 节）。

---

## 1. 第一个程序

```python
# hello.py
print("Hello World!")
```

```shell
python hello.py
```

`python` 后面跟文件路径，解释器读源码、编译成字节码、逐条执行，进程退出。全过程发生了什么见 [[Python/Map|Python 知识地图]]。

三个容易踩的点：

- **文件扩展名必须是 `.py`**——某些编辑器保存时会偷偷加 `.txt`
- **终端的工作目录要能找到这个文件**，路径写错报的是 `can't open file`，不是语法错误
- **文件名别和标准库重名**——建一个 `json.py` 或 `random.py`，同目录下别的代码 `import json` 会导入到你这个文件（`import` 的查找顺序见 [[1.12 模块与包]]）

## 2. 四种运行入口

### 2.1 脚本

```shell
python hello.py
python hello.py arg1 arg2     # 参数从 sys.argv 取，见 5.05 argparse
```

### 2.2 REPL

直接敲 `python` 不带参数，进入交互式终端：

```text
>>> from pathlib import Path
>>> Path("hello.py").exists()
True
>>> exit()
```

REPL 里**每个表达式的值会自动打印**，不用写 `print`——这是它和脚本最直观的区别。写脚本时想看中间值必须显式 `print`。

### 2.3 内联执行 `-c`

```shell
python -c "import sys; print(sys.executable)"
```

这条命令值得记住：**它回答「我现在用的到底是哪个 Python」**，是排查环境问题的第一步（见 [[0.01 环境管理]] 第 8 节）。

### 2.4 模块执行 `-m`

```shell
python -m venv .venv          # 把 venv 模块当命令跑
python -m http.server 8000    # 起一个静态文件服务器
python -m pip install requests
```

`-m` 的意义是**用「当前这个 python」去跑那个模块**，而不是去 PATH 里找同名的可执行文件。所以 `python -m pip` 比直接 `pip` 更安全——后者可能是另一个环境的 pip。

## 3. 编辑器选择

| | PyCharm | VSCode |
|---|---|---|
| 类型 | Python 专属 IDE | 通用编辑器 + 插件 |
| 开箱可用度 | 高，装完即用 | 需要装插件 |
| 重构 / 类型推断 | 更强（JetBrains 静态分析） | Pylance 已经够用 |
| 资源占用 | 重 | 轻 |
| 多语言项目 | 要开别的 IDE | 一个窗口全包 |
| AI 编程工具生态 | 有，但选择少 | 更丰富 |

**选哪个基本不影响学习效果。** 本库选 VSCode，理由是全栈开发统一一个编辑器能省心智负担，且它的 AI Coding 工具生态更活跃。

## 4. VSCode 配置

### 4.1 必装插件

| 插件 | 作用 | 必要性 |
|---|---|---|
| **Python**（ms-python.python） | 语法高亮、补全、调试、虚拟环境识别 | **必装**，其余都建立在它之上 |
| **Black Formatter** 或 **Ruff** | 保存时自动格式化 | 强烈建议 |
| **Code Runner** | 右键一键运行，不用敲命令 | 可选，有坑见 4.4 |
| **Chinese (Simplified)** | 界面汉化 | 按需 |

装 Python 扩展时会连带装上 **Pylance**（语言服务器，负责补全和类型推断）和 **Python Debugger**。

### 4.2 第一件事：选对解释器

命令面板（`Cmd/Ctrl + Shift + P`）→ `Python: Select Interpreter`。

这一步决定了补全、报错、调试、运行按钮全部用哪个 Python。**项目根目录下有 `.venv/` 时，扩展会自动发现并推荐它**——选它，别选系统全局的那个。

选好后左下角状态栏会显示当前解释器路径，随时可以点开切换。判断有没有选对：

```shell
python -c "import sys; print(sys.executable)"
```

在 VSCode 的集成终端里跑这条，输出应该指向项目的 `.venv/bin/python`。

### 4.3 格式化与缩进

```json
{
  "editor.formatOnSave": true,
  "[python]": {
    "editor.defaultFormatter": "ms-python.black-formatter",
    "editor.tabSize": 4,
    "editor.insertSpaces": true
  }
}
```

三个设置的理由：

- **`tabSize: 4` + `insertSpaces: true`** —— Python 用缩进表示代码块，**缩进是语法而不是风格**。PEP 8 规定 4 个空格；混用 Tab 和空格在 Python 3 里直接是 `TabError`
- **`formatOnSave`** —— 格式化交给工具，人不再花心思排版，diff 也干净
- **`[python]` 作用域** —— 只对 Python 文件生效，不影响前端文件的 2 空格习惯

**Black 是 opinionated formatter**（不给你选项的格式化器）：只暴露极少配置（主要是行宽，默认 88 字符），其余一律按它的规则改写。好处是团队里没有格式争论。

**用 Ruff 替代也可以**，且现在更常见：Ruff 是 Rust 写的，一个二进制同时做 linter 和 formatter，格式化输出兼容 Black 风格，但快一到两个数量级。它和 [[0.05 uv\|uv]] 出自同一团队（Astral）。用它的话把 formatter 换成 `charliermarsh.ruff` 即可。

### 4.4 Code Runner 的坑

Code Runner 默认执行的是 `python -u <文件>`，去 PATH 里找 `python`。装了多套环境时它经常找错，于是常见的修法是写死绝对路径：

```json
{
  "code-runner.executorMap": {
    "python": "~/.pyenv/shims/python -u"
  }
}
```

**这个改法能跑通 hello world，但一旦项目用了虚拟环境就会坏**：写死的解释器不在项目 `.venv` 里，装的包它一个都看不到，报 `ModuleNotFoundError`。

三个选择，推荐程度从高到低：

1. **别用 Code Runner 跑项目代码**，用 Python 扩展的运行按钮（▷）或调试（F5）——它们走的是 4.2 里选的那个解释器，永远一致
2. 让 Code Runner 跟随扩展选中的解释器，用它提供的 `$pythonPath` 变量代替绝对路径：
   ```json
   { "code-runner.executorMap": { "python": "$pythonPath -u $fullFileName" } }
   ```
3. 打开 `"code-runner.runInTerminal": true`，让它在集成终端里跑（终端会自动激活 `.venv`），而不是在 Output 面板里跑

顺带解释命令里的 **`-u`**：关闭 stdout/stderr 的缓冲。默认情况下 `print` 的内容会先攒在缓冲区里，输出到非终端设备（比如 Output 面板、日志文件、管道）时可能延迟出现，或者和 `stderr` 的顺序错乱。`-u` 让每次写入立刻落地。在容器里跑服务时通常也会设 `PYTHONUNBUFFERED=1`，同一个目的（见 [[0.02 环境变量与配置]]）。

## 5. 从「能跑」到「能查」

编辑器配置的下一步是断点调试——`print` 能解决的问题有限，读框架源码时必须能停在任意一行看调用栈。VSCode 的 Python 扩展自带 debugpy，按 F5 就能用，具体用法和 pdb / logging 的选型见 [[5.06 调试技巧]]。
