# 资源池与连接池

## TL;DR

**池子是"昂贵资源复用"的通用设计模式，预先创建一批资源，用完归还而不是销毁。** 核心要点：

- 适用于创建开销大的资源：进程、线程、数据库连接、HTTP 连接
- 任务多于池子容量时，超额任务排队等空闲资源
- Python 的现代 API 是 `concurrent.futures`，比 `multiprocessing.Pool` 更易用
- 池子大小是关键工程参数：太大浪费、太小不够并发

---

## 1. 为什么需要池子

```text
没有池子（每次新建）：
  任务1来 → 创建资源 → 执行 → 销毁
  任务2来 → 创建资源 → 执行 → 销毁
  ...
  开销大、慢

有池子（固定数量循环复用）：
  启动时创建 N 个资源，闲置等待
  任务来 → 分配空闲资源
  任务完成 → 资源还回池子
  开销小、快
```

资源创建有多贵？

| 资源 | 创建开销 |
|------|---------|
| 进程 | 拷贝内存、初始化运行时（几十 ms） |
| 线程 | 分配栈空间、OS 调度（几 ms） |
| 数据库连接 | TCP 握手 + TLS + 认证（几十 ms） |
| HTTP 连接 | TCP 握手 + TLS（几十 ms） |

如果一次查询只要 5ms，但创建连接要 50ms，那连接池就是 10 倍加速。

## 2. 进程池：multiprocessing.Pool

```python
from multiprocessing import Pool
import os, time, random

def task(name):
    print(f'Task {name} ({os.getpid()})')
    time.sleep(random.random() * 3)

if __name__ == '__main__':
    p = Pool(4)                      # 池子里 4 个进程
    for i in range(5):               # 5 个任务（超过池子容量）
        p.apply_async(task, args=(i,))
    p.close()                        # 不再接受新任务
    p.join()                         # 等所有任务完成
```

执行示意：

```text
时间 →

进程A: [任务0 1.41s              ]
进程B: [任务1 0.27s] (空闲)
进程C: [任务2 0.14s][任务4 1.91s]    ← 任务4 复用了进程C
进程D: [任务3 0.86s] (空闲)
                ↑
          任务4 排队等到这里
```

## 3. 现代 API：concurrent.futures

更推荐用 `concurrent.futures`，统一了线程池和进程池的接口：

```python
from concurrent.futures import ProcessPoolExecutor, ThreadPoolExecutor

# 进程池（CPU 密集）
with ProcessPoolExecutor(max_workers=4) as pool:
    results = list(pool.map(task, range(5)))

# 线程池（IO 密集）
with ThreadPoolExecutor(max_workers=10) as pool:
    results = list(pool.map(fetch_url, urls))
```

| 旧 API | 新 API |
|--------|--------|
| `multiprocessing.Pool` | `concurrent.futures.ProcessPoolExecutor` |
| `threading.Thread` + 手动管理 | `concurrent.futures.ThreadPoolExecutor` |

## 4. 数据库连接池

最常见的池子，几乎所有 Web 框架/ORM 都用：

```python
# 伪代码
pool = ConnectionPool(size=10)

def handle_request():
    conn = pool.acquire()      # 借一个连接
    try:
        conn.execute('SELECT ...')
    finally:
        pool.release(conn)     # 还回去（不是关闭！）
```

实际代码用 SQLAlchemy 等 ORM，连接池是透明的：

```python
from sqlalchemy import create_engine

engine = create_engine(
    'postgresql://...',
    pool_size=10,        # 池子大小
    max_overflow=20,     # 突发时允许多开
)

# 每次查询自动从池子借连接，结束自动归还
with engine.connect() as conn:
    conn.execute('SELECT ...')
```

## 5. HTTP 连接池

频繁请求同一个域名时，复用 TCP 连接（keep-alive）：

```python
import httpx

# 每次都新建连接（慢）
for url in urls:
    httpx.get(url)

# 用 Client 复用连接池（快）
with httpx.Client() as client:
    for url in urls:
        client.get(url)
```

`requests.Session` 同理：

```python
import requests
s = requests.Session()    # 内部维护连接池
for url in urls:
    s.get(url)
```

## 6. 通用原理

```text
池子（Pool）
├─ 启动时预创建 N 个资源
├─ 维护两个状态：
│   ├─ 空闲队列（idle）：等着被用
│   └─ 使用中（in-use）：正在被某个任务用
│
├─ acquire() 取资源：
│   ├─ 有空闲 → 直接给
│   └─ 没空闲 → 阻塞等待（或抛错，看策略）
│
└─ release() 还资源：
    └─ 放回空闲队列，等下一个 acquire
```

不管是进程池、连接池、对象池，骨架都是这个。

## 7. 怎么定池子大小

太大浪费资源，可能压垮下游；太小并发不够，吞吐量低。

| 池类型 | 经验值 |
|--------|--------|
| 进程池（CPU 密集） | = CPU 核心数 |
| 线程池（IO 密集） | = CPU 核心数 × 2~5 |
| 数据库连接池 | 看数据库的 max_connections，留余量 |
| HTTP 连接池 | 看下游服务承受能力 |

注意数据库的限制：

- PostgreSQL 默认 `max_connections = 100`
- MySQL 默认 `max_connections = 151`

多个应用实例共享数据库时，每个实例的连接池要除以实例数，避免总连接数超限。

## 8. 池化的成本

不是所有场景都该用池：

| 场景 | 适合池吗 |
|------|---------|
| 资源创建昂贵 | 适合 |
| 资源能复用（无状态或可清理状态） | 适合 |
| 资源创建很轻量（如对象） | 不必，反而增加复杂度 |
| 资源有状态污染风险 | 要小心（如 DB 连接的事务状态） |

**记住：池子不是免费的，它增加了"资源生命周期管理"的复杂度。** 只有"创建贵 + 能复用"的资源才值得池化。
