# 字符编码

## TL;DR

计算机只能处理数字，文本必须转成数字。演化路线：**ASCII → 各国编码（乱码）→ Unicode（统一编号表）→ UTF-8（省空间的存储方式）**。现在基本一切都是 UTF-8。

一句话分工：**Unicode 负责"字符是几号"，UTF-8 负责"号码怎么存进字节"。**

---

## 1. 演化路线

```text
ASCII（美国）
  ↓ 只有英文，各国不够用
GB2312（中国）/ Shift_JIS（日本）/ Euc-kr（韩国）...
  ↓ 各国编码互相冲突 → 乱码
Unicode（全球统一编号表）
  ↓ 全用 2+ 字节存英文太浪费
UTF-8（变长编码，按需 1~4 字节）
```

类比：
1. **ASCII** — 美国人造了个电话本，只收录 127 个英文字符
2. **各国编码** — 中日韩各自造电话本，互相打电话对不上号（乱码）
3. **Unicode** — 联合国搞了个全球统一电话本，每个字符一个唯一编号
4. **UTF-8** — 聪明的压缩方案，英文 1 字节，中文 3 字节，按需伸缩

---

## 2. ASCII

用 **1 个字节**（8 bit），只用了 7 bit（0~127），收录：

- 大小写英文字母、数字、标点符号、控制字符
- 例：`A` = 65，`z` = 122，`0` = 48

1 个字节最多表示 256 个字符，英文够了，中文（几万个字）远远不够。

### bit 和字节的关系

术语对照：

| 中文 | 英文 | 说明 |
|------|------|------|
| 位（也音译成**比特**） | **bit** | binary digit（二进制数字）的缩写，只能是 0 或 1，最小信息单位 |
| **字节** | **byte** | 8 个 bit 打包成一组，是内存和文件的最小寻址单位 |

byte 这个词是 bite（咬一口）的故意改拼——一次"咬"下 8 个 bit，改成 y 是为了防止手写时和 bit 看混。

单位缩写要分大小写：大写 **B** = Byte（字节），小写 **b** = bit（位）。所以「100 Mbps 宽带」是每秒 100 兆**位**，换算成字节要除以 8，实际下载峰值约 12.5 MB/s。

| 字节数 | bit 数 | 能表示的最大整数 |
|--------|--------|-----------------|
| 1 | 8 | 255（2⁸ - 1） |
| 2 | 16 | 65535（2¹⁶ - 1） |
| 4 | 32 | 4294967295（2³² - 1） |

减 1 是因为 0 也占一个位置。

## 3. Unicode

Unicode 是一张**"字符 → 编号"的对照表**，给每个字符分配一个唯一编号（叫**码点**）：

```text
码点           字符
U+0041        A
U+0061        a
U+0030        0
U+4E2D        中
U+3042        あ
U+1F600       😀
```

### 码点的写法

`U+` 前缀 + 十六进制数字。用十六进制是因为**和字节对齐**：

```text
1 个十六进制位 = 4 bit
2 个十六进制位 = 8 bit = 1 字节
```

每个十六进制位和 4 个 bit 一一对应，可以直接互相转换：

```text
二进制：    0100 1110  0010 1101
十六进制：  4    E     2    D     ← 每位对应 4 个 bit，一一对齐
十进制：    20013                  ← 完全看不出二进制长什么样
```

对照表：

```text
0 = 0000    4 = 0100    8 = 1000    C = 1100
1 = 0001    5 = 0101    9 = 1001    D = 1101
2 = 0010    6 = 0110    A = 1010    E = 1110
3 = 0011    7 = 0111    B = 1011    F = 1111
```

看到 `4E` 可以直接拼出 `0100 1110`，而十进制 `78` 没法直接知道二进制是什么。

### 十六进制计算方式

和十进制一样，每位乘以权重再相加（底数从 10 变成 16）：

```text
十进制 325 = 3×10² + 2×10¹ + 5×10⁰ = 325
十六进制 4E2 = 4×16² + E×16¹ + 2×16⁰ = 1024 + 224 + 2 = 1250
```

（A=10, B=11, C=12, D=13, E=14, F=15）

Python 中可直接验证：`0x4E2` → `1250`

### Unicode 的范围

Unicode 不只是 2 个字节。目前收录超过 14 万个字符，编号从 0 到 0x10FFFF：

| 范围 | 内容 |
|------|------|
| U+0000 ~ U+007F | ASCII（英文、数字） |
| U+0080 ~ U+07FF | 拉丁文、希腊文、阿拉伯文等 |
| U+4E00 ~ U+9FFF | 常用中文 |
| U+10000 ~ U+10FFFF | emoji、生僻字、古文字等 |

```python
>>> ord('A')
65              # 1 字节范围
>>> ord('中')
20013           # 2 字节范围
>>> ord('𠮷')    # 生僻字
131127          # 超出 2 字节，需要更多
>>> ord('😀')
128512          # emoji，也超出 2 字节
```

emoji 号码大是历史原因：它 2010 年前后才从日本运营商符号"转正"进 Unicode，黄金地段（2 字节以内的号段）早被各国文字占满，只能安置到"新开发区"（U+10000 以上）。表情符号街区从 U+1F600 开始，"咧嘴笑"是 1 号住户，所以 😀 = U+1F600。这也是 emoji 在老系统上常显示成方块的原因——老软件不知道城市已扩建。

### Unicode 只是编号表

Unicode **不规定用几个字节存储**。怎么存是编码方式（UTF-8/16/32）的事：

- **Unicode** = 一张表，给每个字符一个编号
- **UTF-8 / UTF-16 / UTF-32** = 把编号存进电脑的具体方式

## 4. UTF-8

把 Unicode 码点编码成 **1~4 个字节**的变长编码，英文省空间，兼容 ASCII：

| 字符 | Unicode 码点 | UTF-8 编码 | 字节数 |
|------|-------------|-----------|--------|
| A | U+0041 | `01000001` | 1 |
| 中 | U+4E2D | `11100100 10111000 10101101` | 3 |
| 😀 | U+1F600 | 4 字节 | 4 |

### UTF-8 名字的由来

UTF = **U**nicode **T**ransformation **F**ormat（Unicode 转换格式）。**数字指"编码单元"的大小**——以多少 bit 为最小搬运单位，不是"每个字符占几字节"：

```text
UTF-8  : 用小箱子（8 bit 一箱）搬，一件货物用 1~4 个箱子
UTF-16 : 用中箱子（16 bit 一箱）搬，一件货物用 1~2 个箱子
UTF-32 : 用大箱子（32 bit 一箱）搬，任何货物一箱装下
```

以 8 bit 为单元的隐藏福利：**没有字节序问题**。UTF-16/32 的单元横跨多字节，要约定高位字节在前还是在后（大端/小端），文件开头常要塞 BOM 标记声明；UTF-8 一箱就是一字节，从第一个字节读起就行，天生适合网络传输。

> 历史脚注：UCS-2 是 UTF-16 的前身——当年以为 2 字节（65536 个号）够用，后来 emoji、古文字超出，只好打补丁扩成 UTF-16。Windows/Java/JavaScript 内部用 UTF-16 是那个年代的遗产。

### 模板填空：码点怎么变成字节

变长编码的致命问题：**读的人怎么知道从哪切**？切错一个位置后面全盘皆错。UTF-8 的解法：每个字节开头几个 bit 当**身份标记**（印死的），剩下的 bit 装号码（空格）——像四张印好格式的快递单：

```text
单子①（1字节）:  0xxxxxxx                               空格数: 7
单子②（2字节）:  110xxxxx  10xxxxxx                     空格数: 5+6  = 11
单子③（3字节）:  1110xxxx  10xxxxxx  10xxxxxx           空格数: 4+6+6 = 16
单子④（4字节）:  11110xxx  10xxxxxx  10xxxxxx  10xxxxxx  空格数: 3+6+6+6 = 21
```

字头规律：

```text
首字节:   开头连续几个 1，这一伙就有几个字节
          0→单人成伙   110→带1跟班   1110→带2跟班   11110→带3跟班
跟班字节: 一律 10 开头 → "我是跟班，别从我这切"
```

选单子看号码需要几个 bit：装不下就换更大的单子。

**实操①：é（U+00E9 = 233，2 字节单）**

```text
① 233 二进制:  11101001（8 bit）
② 7 格装不下 → 换单子②（11 格）
③ 左边补零凑满 11 位:  00011101001
④ 按 5+6 切开:  00011 | 101001
⑤ 填空:  110[00011]  10[101001]
⑥ 结果:  11000011 10101001 = C3 A9
```

**实操②：藜（U+85DC，3 字节单）**

```text
① 码点二进制:  1000010111011100（16 bit，正好 16 格）
② 按 4+6+6 切开:  1000 | 010111 | 011100
③ 填空:  1110[1000]  10[010111]  10[011100]
④ 结果:  E8 97 9C
```

Python 验证：`'藜'.encode('utf-8')` → `b'\xe8\x97\x9c'` ✓

### 反向：解码怎么切分

不需要额外信息，看字头自动断句：

```text
字节流:  41  E8  97  9C  42

41 = 01000001，0 开头   → 单人，字符 65 = 'A'
E8 = 11101000，1110 开头 → 带俩跟班！收下后面 2 个字节
     97、9C 都是 10 开头 ✓ 是跟班
     抠出空格内容拼回: [1000][010111][011100] → U+85DC = '藜'
42 = 01000010，0 开头   → 单人，字符 66 = 'B'

结果: "A藜B"
```

**印死的标记负责断句，空格内容负责还原号码。** 两个推论：随便跳进字节流，见 `10` 开头就知道自己在别人一伙的中间，往前挪到非 `10` 字节即归位（自同步）；单子①就是 `0xxxxxxx`，和 ASCII 一个 bit 不差（完全兼容）。

### 中文一定是 3 字节吗

不一定。**字节数只看码点落在哪个区间，和"是不是中文"无关**：

| 码点区间 | 用哪张单子 | 字节数 |
|---|---|---|
| U+0000 ~ U+007F | 单子① | 1 |
| U+0080 ~ U+07FF | 单子② | 2 |
| U+0800 ~ U+FFFF | 单子③ | 3 |
| U+10000 ~ U+10FFFF | 单子④ | 4 |

区间边界不是硬背的，是每张单子的空格数算出来的：7 格最大 `0x7F`，11 格最大 `0x7FF`，16 格最大 `0xFFFF`，21 格最大 `0x1FFFFF`（Unicode 只用到 `0x10FFFF`，单子④还有余量）。

汉字绝大部分落在第三段，所以"中文 3 字节"多数时候成立，但有例外：

| 区块 | 码点范围 | 字节数 |
|---|---|---|
| 基本汉字（CJK 统一表意） | U+4E00 ~ U+9FFF | 3 |
| 扩展 A | U+3400 ~ U+4DBF | 3 |
| 兼容汉字 | U+F900 ~ U+FAFF | 3 |
| 中文标点、全角符号（，。、《） | U+3000 段 / U+FF00 段 | 3 |
| **扩展 B 及以后**（生僻字、异体字） | **U+20000 以上** | **4** |

```python
>>> [(c, len(c.encode())) for c in '中龥㐀，𠮷𰻞']
[('中', 3), ('龥', 3), ('㐀', 3), ('，', 3), ('𠮷', 4), ('𰻞', 4)]
```

`𠮷` 是日本人名用字（U+20BB7），`𰻞` 是 biángbiáng 面那个字（U+30EDE），都和 emoji 一样住在 U+10000 以上的"新开发区"，所以得用单子④。

两个附带的坑：

- **"中文几个字节"必须先问哪种编码。** GBK 里常用汉字是 2 字节；UTF-16 里基本汉字 2 字节、扩展 B 汉字 4 字节。
- **MySQL 的 `utf8` 存不下 4 字节汉字。** 它真名是 `utf8mb3`，每字符最多 3 字节，遇到扩展 B 汉字会报错或截断——和存 emoji 踩的是同一个坑，解法都是换 `utf8mb4`。

### 哪些字节永远不会出现

一个字节有 256 种取值（2⁸ 穷尽），但**合法 UTF-8 里只用得到 241 种**——有 13 个字节值不匹配任何一张单子，永远不会出现（实测枚举）：

```text
C0 C1   F5 F6 F7 F8 F9 FA FB FC FD FE FF
```

原因正好对应四张单子的边界：

| 字节值 | 为什么非法 |
|---|---|
| `F8` ~ `FF` | 开头有 5 个以上连续的 1（`11111xxx`），**不匹配任何一张单子** |
| `F5` ~ `F7` | 形式上是单子④（`11110xxx`），但装出来的码点超过 `0x10FFFF`，**越过 Unicode 上限** |
| `C0`、`C1` | 形式上是单子②，但装的码点小于 `0x80`——**本该用单子①** |

最后一类叫 **overlong 编码**（过长编码），被规范明令禁止，因为它会让同一个字符有多种字节写法。历史上这是真实的安全漏洞：过滤器检查路径里的 `/`（单字节 `2F`），攻击者改用 `C0 AF` 这个"另一种 `/`"——过滤器认不出，解码器却照样解成 `/`，目录穿越就成了。所以规范要求**一个字符只能有唯一一种合法 UTF-8 写法**，解码器必须拒绝 overlong：

```python
>>> b'\xc0\xaf'.decode('utf-8')
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xc0 in position 0: invalid start byte
```

### 与其他编码方式对比

| 编码方式 | 每个字符占用 | 特点 |
|----------|------------|------|
| UTF-8 | 1~4 字节（变长） | 最省空间，兼容 ASCII，用得最多 |
| UTF-16 | 2 或 4 字节 | Windows/Java 内部用 |
| UTF-32 | 固定 4 字节 | 最浪费空间，但定位快 |

同一个字符在不同编码下占用不同：

| 字符 | UTF-8 | UTF-16 | UTF-32 |
|------|-------|--------|--------|
| A | 1 字节 | 2 字节 | 4 字节 |
| 中 | 3 字节 | 2 字节 | 4 字节 |
| 😀 | 4 字节 | 4 字节 | 4 字节 |

### UTF-8 的额外好处

ASCII 编码是 UTF-8 的子集——ASCII 文件天然就是合法的 UTF-8 文件。大量只支持 ASCII 的历史遗留软件可以在 UTF-8 下继续工作。

## 5. Python 3 默认 UTF-8

老教程常见这两行开头声明：

```python
#!/usr/bin/env python3
# -*- coding: utf-8 -*-
```

- 第一行告诉 Linux/macOS 这是 Python 可执行程序（Windows 忽略）
- 第二行告诉 Python 解释器按 UTF-8 读取源代码

**Python 3 已经不需要写了**——默认编码就是 UTF-8。Python 2 时代默认 ASCII，遇到中文会报错，所以必须声明。现在的编辑器（VS Code 等）保存文件也默认 UTF-8，两边都不用操心。

## 6. 现代系统的工作方式

```text
内存中：Unicode（统一编号，方便处理）
存硬盘 / 传网络：UTF-8（省空间）
```

Python 中用 `\u` 和 `\U` 可以直接写 Unicode 码点：

```python
>>> 'A'
'A'
>>> '中'
'中'
>>> '\U0001F600'
'😀'
```

## 7. 乱码的本质：字节没变，查错了表

```python
>>> data = '你好'.encode('utf-8')     # E4 BD A0 E5 A5 BD
>>> data.decode('gbk')                # 拿 GBK 的表去解读
'浣犲ソ'
```

同一串字节，UTF-8 的表查出「你好」，GBK 的表查出「浣犲ソ」——**乱码不是数据坏了，是解读用错了对照表**。「锟斤拷」「烫烫烫」都是这类事故的特产。

三条实战铁律：

- encode 和 decode 必须用同一张表
- 打开文本文件显式写 `open(f, encoding='utf-8')`（Windows 默认可能是 GBK，跨平台的坑大多在此）
- "长度"先问单位：同一段文本，字符数、字节数、token 数是三个不同的数字（`len('你好')` = 2，`len('你好'.encode())` = 6）

## 8. 常见误区

**误区一："U+1F600 是 2.5 个字节"**

码点是**数字**，不是字节。5 个十六进制位 × 4 bit = 20 bit 只说明"这个数字写出来要 5 个字符"，写法长度 ≠ 存储长度。实际存储由编码方案决定、永远整数个字节：UTF-8 存 `F0 9F 98 80`（4 字节），UTF-16 存 `D8 3D DE 00`（4 字节，代理对），UTF-32 存 `00 01 F6 00`（4 字节，号码补零直存）。

> **U+1F600 是车牌号，字节是车位；车牌号几位数无所谓，车停进去永远占整数个车位。**

**误区二："UTF-8 是字符对应数字的表"**

那张表是 Unicode。UTF-8 从头到尾不认识任何字符，它拿到的只是数字，干的只是"数字 → 字节"的装箱。

**误区三："数字是十进制的"**

数字本身没有进制。34268、0x85DC、1000010111011100 是同一个数的三种写法，进制只是给人看的记法。`hex()` / `bin()` 不是"转换数据"，只是换个格式打印——内存里那串 bit 一个都没动。

顺带一提：**整数写成二进制永远是有限位**（辗转除 2 必然终止），所以码点不存在"存不完"的问题，编码这条链上一个 bit 都不会丢。会因为二进制而丢精度的是**小数**（`0.1` 在二进制里无限循环），那是浮点数的事，见 [[1.01 数据类型基础]]。
