# 解释型语言与代码发布

## TL;DR

Python 和 JavaScript 都是**解释型语言**，发布程序 = 发布源代码。前端 JS 更没隐私（浏览器里 F12 直接看）。想保护代码，要么打包二进制（仅限后端），要么用 WebAssembly，要么做成服务端 API。Python 不流行混淆/压缩：压缩的动机（传输体积）不存在，代码也从不出门。

---

## 1. 编译型 vs 解释型

```text
编译型（C/Java）:  源代码 → 编译 → 二进制文件 → 运行
                   发布的是二进制，别人看不到源代码

解释型（Python/JS）: 源代码 → 解释器逐行执行
                     发布的就是源代码本身
```

类比：
- 编译型 = 把菜谱做成一道菜，别人吃到菜但拿不到菜谱
- 解释型 = 直接把菜谱发给别人，别人既能做菜也能看到配方

---

## 2. Python 发布 = 发布源代码

Python 的 `.py` 文件就是源代码，打开就能看到每一行代码。

`.pyc` 文件（字节码缓存）只是加速加载用的，很容易被反编译回接近原始的源代码，起不到保护作用。

详见 [[5.15 CPython 解释器原理]]。

---

## 3. JavaScript 也是一样

| 场景 | 情况 |
|------|------|
| 前端 JS | **完全公开**，浏览器 F12 就能看到 |
| 后端 JS (Node.js) | 和 Python 一样，部署的就是 `.js` 文件 |

前端 JS 几乎必做混淆/压缩（Webpack/Terser），但只是把变量名变成 `a, b, c`、去掉空格换行，本质还是源代码，有耐心就能还原。

---

## 4. 保护手段对比

| 手段 | Python | JavaScript |
|------|--------|------------|
| 混淆/压缩 | 不常见 | 前端几乎必做 |
| 打包成二进制 | PyInstaller, Nuitka | pkg, nexe |
| 做成服务端 API | 常见 | 常见 |
| WebAssembly | 可以（通过 C 扩展） | 可以 |

打包成二进制只能用于**后端/桌面端**，浏览器不能运行二进制文件。

### 为什么 Python 不常见混淆/压缩

一句话：**混淆/压缩是为「把代码交到别人机器上跑」的场景服务的，Python 代码几乎总是留在自己的服务器上**——场景不存在，手段自然不常见。拆开是三层：

**第一，前端压缩的主要动机在 Python 里不存在。** 前端做混淆/压缩，第一动机不是保密而是**传输体积**——每个用户打开页面都要下载 JS，少 100KB 就快一截，所以 Terser 是构建标配，混淆只是「顺便」。Python 文件不传给任何用户，没有「下载体积」概念，压缩的最大收益直接归零。

**第二，运行环境是自己的，保密靠门锁而不是伪装。**

| | 前端 JS | Python 后端 |
|---|---|---|
| 代码跑在哪 | 用户的浏览器（别人的机器） | 自己的服务器 |
| 用户能看到源码吗 | 能，F12 就是全部 | 不能，除非入侵服务器 |
| 保护思路 | 藏不住，只能混淆恶心一下 | 不用藏，靠服务器访问控制 |

**第三，就算想混淆，Python 也比 JS 更容易被弄坏。** Python 工程大量依赖「名字在运行时可见」：

```python
getattr(obj, 'user_name')        # 反射按字符串找属性
User(**{'name': 'x'})            # dict 的 key 对应字段名
class User(BaseModel):
    name: str                    # Pydantic/ORM 靠字段名生成校验和 SQL
```

把 `user_name` 改名成 `a`，这些全坏——而 Pydantic、SQLAlchemy、pickle、日志 traceback 这类「按名字工作」的机制正是 Python 工程的日常（反射机制见 [[2.08 对象信息获取]]）。JS 的同类问题经过多年工具链演化才勉强处理好，Python 社区没有这个需求压力，工具自然不成熟。

所以「不常见」的潜台词是：Python 跳过了混淆这个弱手段，直接用「代码不出门（服务端 API）」和「编译成二进制」两个更强的方案覆盖需求——即上表的其他几行。

## 5. WebAssembly (WASM)

浏览器只认三样东西：**HTML、CSS、JavaScript**。WASM 是第四种——一种浏览器能运行的二进制格式：

- 用 C/C++/Rust 写代码 → 编译成 `.wasm` → 浏览器执行
- 比 JS 快，且很难反编译回可读源代码
- 适合需要性能或保护逻辑的场景（游戏引擎、加密算法）

### WASM 不能替代 JS

WASM **不能直接操作网页（DOM）**，必须通过 JS 当"中间人"：

| 能力 | JS | WASM |
|------|-----|------|
| 修改页面元素 | 直接操作 | 必须调 JS |
| 监听点击/输入事件 | 直接监听 | 必须通过 JS |
| 发网络请求 | `fetch()` | 必须通过 JS |
| 高性能计算 | 较慢 | 很快 |

类比：
- JS = 自己去餐厅点菜，能直接跟服务员（DOM）说话
- WASM = 外国人，必须带个翻译（JS）才能跟服务员沟通

现实中的分工：**JS 负责页面交互，WASM 负责重计算**（图像处理、视频编解码、3D 渲染等），两者配合。

---

## 6. 最靠谱的保护方式

不发给用户——放在服务端，只暴露 API。这也是 SaaS 模式流行的原因之一。
