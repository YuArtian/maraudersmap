# uv

## TL;DR

**uv 是 Rust 写的单个二进制，把「装解释器 + 建虚拟环境 + 装包 + 锁依赖 + 跑命令」整条链一口气全包了。**

- 覆盖范围 = pyenv + venv + pip + pip-tools + pipx + PDM/Poetry
- **只管项目级，默认不碰你的全局 `python`**——没有 `pyenv global` 那种东西
- 装 Python 是**下载预编译二进制**（几秒），不是像 pyenv 那样现场编译（几分钟）
- 建的虚拟环境就是**标准 venv**，不是自创格式，IDE 和其他工具都认
- Windows 是一等公民（pyenv 官方不支持 Windows）
- 边界：只装 Python 包（但包里可以带任意原生二进制），装不了 ffmpeg、gcc 这类独立程序——那是 Conda 的地盘

它是 [[0.01 环境管理]] 里三条路线中的路线 C，三条路线怎么选见那篇第 6.3 节。

## 1. uv 是什么

### 1.1 一个二进制覆盖整条链

传统做法要装好几个工具、记好几套命令，uv 是一个可执行文件全包：

```bash
uv python install 3.13    # 装解释器
uv venv                   # 建虚拟环境
uv add requests           # 装包并记进锁文件
uv run python app.py      # 跑命令，自动用项目环境
```

### 1.2 替掉了哪些工具

| 干的事 | 传统做法 | uv |
|---|---|---|
| 装 / 切 Python 解释器 | pyenv | `uv python install 3.13` |
| 钉住项目用的版本 | `pyenv local`（写 `.python-version`） | `uv python pin 3.13`（写同一个文件） |
| 建虚拟环境 | `python -m venv` | `uv venv` |
| 装包 | pip | `uv pip install` / `uv add` |
| 锁依赖版本 | pip-tools / Poetry / [[PDM]] | `uv lock` → `uv.lock` |
| 按锁文件还原环境 | `pip install -r` | `uv sync` |
| 跑命令 | 手动 activate | `uv run` |
| 全局装 CLI 工具 | pipx | `uv tool install` |

pyenv 只占前两行——**uv 的覆盖面比 pyenv 大得多**，这是两者最根本的差别。

### 1.3 装它

单个二进制，不依赖 Python（它自己是 Rust 写的，不存在「先有鸡还是先有蛋」的问题）：

```bash
# macOS / Linux
curl -LsSf https://astral.sh/uv/install.sh | sh

# Windows
powershell -c "irm https://astral.sh/uv/install.ps1 | iex"
```

装完之后升级用 `uv self update`。

## 2. 作用域：项目级，不动全局

这是最容易误解的一点，单独拿一节讲。

### 2.1 三个命令的作用域各不相同

| 命令 | 动了什么 | 作用域 |
|---|---|---|
| `uv python install 3.13` | 往 uv 自己的目录下载一个解释器 | **无**——纯粹是下载到仓库，谁都不影响 |
| `uv python pin 3.13` | 在当前目录写一个 `.python-version` | **当前目录**及子目录 |
| `uv venv` / `uv run` / `uv sync` | 建 / 用当前项目的 `.venv` | **当前项目** |

`uv python install` 完全是惰性的——它只是把解释器下载到仓库里备用，不会改变任何现有行为。

### 2.2 实测：全局的 python 没被碰

```text
uv python dir  →  C:\Users\...\AppData\Roaming\uv\python
                  └── cpython-3.12.13-windows-x86_64-none

PATH 里有没有这个目录：  没有
py -V：                  Python 3.13.1      ← 装了 3.12 之后还是它
```

`uv python pin 3.12` 的全部效果就是当前目录多出一个两行不到的文件：

```bash
$ cat .python-version
3.12
```

**跟 pyenv 的关键差别：uv 根本没有 `pyenv global` 的对应物。** pyenv 有全局和目录两个层级，且因为 shim 机制，两个都会改变你敲 `python` 得到的东西。uv 只有目录这一层，且不接管 `python` 命令。

### 2.3 uv 挑解释器和 shell 挑解释器是两套

这一点反直觉，值得记住。没 pin 的时候两者会给出不同答案：

```text
（没有 .python-version 的目录）
uv run python -c "print(sys.version)"  →  3.12.13   ← uv 管的那个
py -V                                  →  3.13.1    ← 系统那个
```

因为 uv 默认 `python-preference = "managed"`——**优先用自己下载的，而不是回落到系统的**。

「我系统装的是 3.13，uv 怎么跑出个 3.12」不是 bug。要它认系统解释器，加 `--no-managed-python`，或在 `pyproject.toml` / `uv.toml` 里配 `python-preference = "system"`。

### 2.4 唯一会动全局的两件事

都得主动做，不会自己发生：

| 命令 | 影响 |
|---|---|
| `uv python update-shell` | 显式把 uv 的 Python 目录加进 `PATH`，这才让 `python` 变成 uv 管的 |
| `uv tool install ruff` | 装全局 CLI 工具（pipx 那个位置），可执行文件落到 `~/.local/bin` |

不跑这两个，uv 对系统的影响就只有 `%APPDATA%\uv\` 一个文件夹。

## 3. 怎么用

### 3.1 兼容层：venv + pip 的原地替换

心智完全不变，只是快：

```bash
uv venv --python 3.13
uv pip install requests
uv pip install -r requirements.txt
uv pip freeze
```

适合往老项目里插，不改任何工作流。

### 3.2 项目模式：推荐

```bash
uv init myproj && cd myproj
uv add fastapi pydantic
uv run python app.py
```

**不需要手动 activate**——`uv run` 会自己保证 `.venv` 和 `uv.lock` 是同步的，缺什么补什么。产出物是 `pyproject.toml`（你要什么）+ `uv.lock`（实际锁定的精确版本）两个文件，都该提交进 git。

这是路线 A（pyenv + venv + pip）原生缺的那一块：**pip freeze 只是当前环境的快照，不区分「我直接要的」和「被依赖拖进来的」，也不记录依赖关系**（见 [[0.01 环境管理]] 第 3.4 节）。

### 3.3 建出来的就是标准 venv

```text
$ cat .venv/pyvenv.cfg
home = C:\Users\...\uv\python\cpython-3.12.13-windows-x86_64-none
implementation = CPython
uv = 0.11.3
version_info = 3.12.13
include-system-site-packages = false
```

除了多一行 `uv = 0.11.3`，和 `python -m venv` 产出的一模一样，`Scripts/` 下 activate 脚本齐全。

**所以 IDE、pytest、任何认 venv 的工具都直接认**——这跟 Conda 自成一套不同，迁移成本几乎为零。想退回 pip 也随时可以，环境本身没有任何 uv 专有的东西。

### 3.4 常用命令速查

| 命令 | 作用 |
|---|---|
| `uv python list` | 列出已装和可下载的解释器 |
| `uv python install 3.13` | 下载一个解释器 |
| `uv python pin 3.13` | 在当前目录写 `.python-version` |
| `uv python find` | 看 uv 当前会选哪个解释器 |
| `uv venv [--python 3.13]` | 建虚拟环境 |
| `uv init` | 新建项目（生成 `pyproject.toml`） |
| `uv add / remove <包>` | 增删依赖并更新锁文件 |
| `uv lock` | 只更新锁文件 |
| `uv sync` | 按锁文件把环境调成一致 |
| `uv run <命令>` | 在项目环境里跑，自动同步 |
| `uv tree` | 看依赖树 |
| `uv pip install` | pip 兼容接口 |
| `uv tool install <包>` | 全局装 CLI 工具（替代 pipx） |
| `uv cache clean` | 清缓存 |
| `uv self update` | 升级 uv 自己 |

## 4. 与 pyenv 的差别

两者覆盖面差得远（见第 1.2 节），这里只比重叠的那部分：**装和切 Python 解释器**。

### 4.1 pyenv 现场编译，uv 下载预编译二进制

pyenv 的 `install` 会下载源码在你机器上 build，几分钟起步，还得先装齐编译器和一堆开发头文件。uv 拉的是 python-build-standalone 项目提供的现成构建：

```text
$ time uv venv --python 3.12 demo-env
Downloading cpython-3.12.13-windows-x86_64-none (20.8MiB)
Creating virtual environment at: demo-env
real  0m6.3s        ← 下载整个 3.12 + 建好环境，六秒
```

装包同理，`requests` 全家 2.6 秒。

### 4.2 pyenv 靠 shim 劫持 `python`，uv 不碰 PATH

pyenv 在 `PATH` 最前面塞一堆同名脚本（叫 shim），每次执行 `python` 都被拦下来查 `.python-version` 再转发——所以才有 `pyenv rehash` 这种东西，也常出现「我以为在这个版本其实在那个」。

uv 把解释器放自己目录里，靠 `uv run` / `uv venv --python 3.13` 显式指定。

这接上 [[Python/Map|Python 知识地图]] 第 1 节那句话：环境问题绝大多数是「`python` 这个词解析到了谁」，**uv 的做法是不去搅这滩水**。

### 4.3 Windows 支持

pyenv 官方不支持 Windows，得用第三方的 pyenv-win（独立项目，跟进慢）。uv 三平台都是一等公民。

### 4.4 uv 替代不了 pyenv 的地方

只有一类：**uv 只能用 python-build-standalone 提供的现成构建，pyenv 是现场编译，所以能编 uv 给不了的东西。**

| 情况 | 说明 |
|---|---|
| 要自定义编译选项 | PGO / LTO 优化、链接指定版本的 OpenSSL、特殊 configure 参数 |
| 要 3.8 以前的版本 | `uv python list` 最老到 3.8，2.7 或 3.6 得自己编 |
| 踩到 standalone 构建的差异 | 它为可移植性做了大量静态链接，极少数 C 扩展或 `sysconfig` 相关场景表现不同 |

日常开发这三条基本碰不上，所以装了 uv 之后一般不需要再装 pyenv。

## 5. 能装什么，边界在哪

### 5.1 载体是 Python 包，但内容不限于 Python 代码

wheel 是个 zip，里面可以塞任意编译好的二进制（详见 [[0.04 打包与分发]]）。所以：

```text
uv pip install numpy pillow          →  258 毫秒装完，落盘的东西包括：

numpy.libs/libscipy_openblas64_….dll     ← 整个 OpenBLAS（Fortran/C 写的）
numpy 的 .pyd 共 21 个                    ← 编译好的 C 扩展
PIL/_imaging.cp312-win_amd64.pyd         ← libjpeg / libpng 静态链在里面
```

没装编译器，没装系统库。**「uv 只装 Python 包」说的是外壳格式，不是里面的内容。**

### 5.2 CUDA 也能装

把平台切到 Linux 解析一次 `torch`：

```text
$ uv pip install --dry-run --python-platform x86_64-unknown-linux-gnu torch
 + nvidia-cublas          + nvidia-cudnn-cu13
 + nvidia-cuda-runtime    + nvidia-nccl-cu13
 + nvidia-cufft           + nvidia-cusolver
 ...共 15 个 nvidia-* 包
```

**整套 CUDA runtime 就是 PyPI 上的普通 wheel。** 这几年 PyTorch 生态已经从「conda install cudatoolkit」迁到这条路上，所以「装 torch 得用 Conda」这条老经验基本过期了。

（Windows 上默认的 torch wheel 是 CPU 版，CUDA 版在 PyTorch 自己的 index 上，要用 `--index-url` 指定。）

### 5.3 真正的边界：有没有人打包成 wheel

边界不是「Python vs 非 Python」，而是**「这东西有没有被打包成 wheel 发到某个包仓库上」**。

能装：任何以 wheel 形式发布的东西，不管里面是什么语言写的。
不能装：没人做成 wheel 的东西——但很多有 wheel 变体，比如 `cmake`、`ninja`、`imageio-ffmpeg` 都能从 PyPI 装。

### 5.4 与 Conda 的分界

| | uv | Conda |
|---|---|---|
| 包格式 | wheel（Python 包，可内嵌任意原生二进制） | conda 包（通用跨语言二进制） |
| numpy / torch / CUDA runtime | ✅ | ✅ |
| ffmpeg、cmake、gcc 这类**独立命令行程序** | ❌ 除非有人做了 wheel 变体 | ✅ |
| R、Node.js、Java 这类**别的语言生态** | ❌ | ✅ conda-forge 什么都装 |
| NVIDIA 显卡驱动 | ❌ 内核态，必须系统装 | ❌ 同样不行 |

一句话：**conda-forge 本质是个跨语言的系统包仓库，PyPI 是个 Python 包仓库。** 差别在仓库定位，不在「能不能带 C 代码」。

这也是 Conda 至今不可替代的唯一理由——需要装非 Python 的系统级程序时，只有它行。

### 5.5 uv 下载的不止包

- **Python 解释器本身**（python-build-standalone）——这个严格说就不是 Python 包
- **uv 自己**：`uv self update`
- `uv tool install` 装的 CLI 工具——那个仍然是 Python 包

## 6. 为什么快

### 6.1 三个来源

| 来源 | 说明 |
|---|---|
| **Rust 实现 + 并行** | 依赖解析和下载全并发，不像 pip 那样基本串行 |
| **靠 wheel 文件名筛选** | 不用下载解包就知道某个 wheel 适不适配本机（见 [[0.04 打包与分发]] 第 4.7 节） |
| **全局缓存 + 链接** | 同一个包全局只落盘一次，各环境靠硬链接共享 |

### 6.2 中央存储 + 链接：三个生态同一个思路

uv 在这方面做得比 Conda 更彻底——同样是全局缓存，且在 macOS 的 APFS 文件系统上直接用 copy-on-write 克隆，建环境几乎不占额外空间。

```text
Conda   pkgs/ 中央缓存      + 硬链接
pnpm    全局 store          + 硬链接
uv      全局 cache          + 硬链接 / copy-on-write
```

**这套心智模型建立一次，Conda、pnpm、uv 就全通了**——完整展开见 [[0.01 环境管理]] 第 7 节。
