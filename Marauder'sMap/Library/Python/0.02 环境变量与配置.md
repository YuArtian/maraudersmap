# 环境变量与配置

## TL;DR

**`os.environ` 是 Python 读写环境变量的接口，主要用来读取配置，避免硬编码敏感信息。** 核心要点：

- `os.environ` 是 dict-like 对象，但值**永远是字符串**
- 用 `.get(key, default)` 安全读取，避免 KeyError
- 没有 `.set()` 方法——写入用字典式下标赋值 `os.environ[k] = v`
- 推荐用 `.env` 文件 + `python-dotenv` 管理配置
- 多环境（本地/测试/生产）用 `APP_ENV` 总开关切换 `.env.{env}` 文件；生产由部署平台注入变量、不用文件
- 修改 `os.environ` 只影响当前进程的副本

---

## 1. 基本用法

```python
import os

# 读取
os.environ['HOME']               # 不存在会 KeyError
os.environ.get('HOME')           # 不存在返回 None
os.environ.get('XXX', '默认值')  # 提供默认值

# 设置
os.environ['MY_VAR'] = 'hello'

# 删除
del os.environ['MY_VAR']

# 查看所有
for key, value in os.environ.items():
    print(f'{key}={value}')
```

---

## 2. 为什么没有 os.environ.set()

从 JS 过来会下意识找 `.set()`（`Map.get()` / `Map.set()` 成对出现），但 Python 这边的逻辑不同：`os.environ` 实现了和 `dict` 一样的接口（`MutableMapping` 协议），读写方式和普通字典完全一致——**下标赋值就是官方写法**，底层调用的是 dunder 方法 `__setitem__`。

`.get()` 存在的意义也不是「读取」本身（读取用 `d[key]`），而是「**读不到时不报错、给默认值**」：

```python
os.environ['XXX']                # 不存在 → 抛 KeyError
os.environ.get('XXX')            # 不存在 → 返回 None
os.environ.get('XXX', '默认值')  # 不存在 → 返回默认值
```

JS 的 `Map` 必须要 `.set()`，是因为 `map[key] = x` 在 JS 里设置的是对象属性而不是 Map 条目；Python 靠 `__setitem__` 让下标赋值直达数据，没有这个问题。

| 操作 | JS Map | Python dict / os.environ |
|------|--------|--------------------------|
| 读取 | `map.get(key)` | `d[key]`（不存在报错） |
| 安全读取带默认值 | `map.get(key) ?? def` | `d.get(key, def)` |
| 写入 | `map.set(key, val)` | `d[key] = val` |
| 仅当不存在时写入 | 手动 if 判断 | `d.setdefault(key, val)` |
| 删除 | `map.delete(key)` | `del d[key]` / `d.pop(key)` |

两个补充：

- `os.environ.setdefault('KEY', 'val')` 是标准字典方法，加载配置默认值时常用
- **别用 `os.putenv()`**——它只改底层环境、不更新 `os.environ` 这个字典，读回来会不一致；给 `os.environ` 下标赋值时 Python 会自动同步调用 putenv

这套「实现了 `__getitem__`/`__setitem__` 就能像字典一样用」的机制，详见 [[2.06 定制类]]。

## 3. 三个重要特性

### 值永远是字符串

```python
os.environ['PORT'] = 8080        # TypeError! 必须是字符串
os.environ['PORT'] = '8080'      # OK

port = int(os.environ['PORT'])   # 用的时候手动转类型
debug = os.environ.get('DEBUG', 'false') == 'true'
```

### 只是当前进程的副本

```python
os.environ['MY_VAR'] = 'hello'
# 只在这个 Python 进程里有效
# 退出后 shell 里 echo $MY_VAR 还是空的
```

### 修改会传给子进程

```python
import subprocess
os.environ['MY_VAR'] = 'hello'
subprocess.run(['env'])   # 子进程能看到 MY_VAR=hello
```

## 4. 实际场景：配置管理

最常见的用途是**避免敏感信息硬编码**：

```python
# 危险！密码写死在代码里
DB_PASSWORD = 'my_secret_123'

# 应该从环境变量读
DB_PASSWORD = os.environ.get('DB_PASSWORD')
API_KEY = os.environ['OPENAI_API_KEY']
DEBUG = os.environ.get('DEBUG', 'false') == 'true'
```

运行时通过环境变量传入：

```bash
DB_PASSWORD=my_secret_123 python app.py
```

---

## 5. python-dotenv（最常见做法）

用 `.env` 文件 + `python-dotenv` 库管理配置：

```text
.env 文件（不要提交到 git！）:
DB_PASSWORD=my_secret_123
API_KEY=sk-xxxxx
DEBUG=true
```

```python
from dotenv import load_dotenv
load_dotenv()   # 把 .env 加载到 os.environ

import os
db_password = os.environ['DB_PASSWORD']
```

记得把 `.env` 加到 `.gitignore`：

```text
.gitignore:
.env
```

通常项目会提供一个 `.env.example` 作为模板：

```text
.env.example（提交到 git）:
DB_PASSWORD=
API_KEY=
DEBUG=false
```

## 6. 多环境配置（本地/测试/生产）

真实项目里代码只有一份，配置随环境变化。核心做法：**用一个环境变量当「总开关」来选配置**（12-Factor 原则）：

```text
                APP_ENV=local / test / production
                          │
          ┌───────────────┼───────────────┐
          ▼               ▼               ▼
    .env.local       .env.test      生产不用文件，
    (本地数据库)     (测试数据库)    由部署平台注入
```

### 6.1 多 .env 文件 + 总开关

```text
.env              # 公共默认值，无敏感信息，可提交
.env.local        # 本地覆盖，不提交
.env.test         # 测试环境，无敏感信息可提交
.env.example      # 模板，提交
```

```python
import os
from dotenv import load_dotenv

env = os.environ.get('APP_ENV', 'local')   # 总开关，默认本地
load_dotenv(f'.env.{env}')   # 先加载环境专属配置
load_dotenv('.env')          # 再加载公共默认值
```

两个关键细节：

- **加载顺序反直觉**：`load_dotenv` 默认不覆盖已存在的变量，所以要**先专属、后公共**——先设置的值不会被后来的默认值冲掉
- 由此形成优先级：**平台注入的真实环境变量 > `.env.{APP_ENV}` > `.env` 默认值**。和 Next.js 的 `.env.local > .env.development > .env` 同一逻辑，只是 Next 自动做了、Python 要自己写这三行

运行时切换：

```bash
python app.py                    # 本地（默认 local）
APP_ENV=test pytest              # 测试
APP_ENV=production python app.py # 生产
```

### 6.2 pydantic-settings（工程标准做法）

相当于「用 Zod 校验 `process.env`」，FastAPI 项目几乎都这么写：

```python
from pydantic_settings import BaseSettings

class Settings(BaseSettings):
    app_env: str = 'local'
    database_url: str            # 缺了会直接报错，启动即失败
    debug: bool = False          # 自动把 'true'/'1' 转成 bool

    model_config = {'env_file': '.env'}

settings = Settings()
settings.database_url   # 全项目从这一个对象读配置，带类型提示
```

比裸用 `os.environ` 好在：类型自动转换（绕开「值永远是字符串」的痛点）、缺配置启动时立刻报错而不是运行到一半炸、IDE 有补全。

### 6.3 生产环境根本不用 .env 文件

`.env` 文件只是本地开发的便利，测试/生产的变量由部署平台直接注入进程：

| 环境 | 变量来源 |
|------|----------|
| 本地 | `.env.local` 文件 |
| CI 跑测试 | CI 平台的 secrets 配置（如 GitHub Actions） |
| 生产 | Docker `-e` / K8s ConfigMap+Secret / 云平台控制台 |

所以生产服务器上通常找不到 `.env` 文件——变量早就在进程环境里了，代码里的 `load_dotenv()` 什么都不加载、直接读到平台注入的值。密码因此永远不需要进代码仓库。

### 6.4 和前端的对照

| | Vite / Next.js | Python |
|---|---|---|
| 总开关 | `NODE_ENV` / `MODE`（框架内建） | `APP_ENV`（自定义约定，无统一标准） |
| 按环境加载文件 | 框架自动 | python-dotenv 手动写 |
| 配置校验 | Zod parse env | pydantic-settings |

最大差异一条：**Python 没有框架帮你自动加载 `.env.{环境}`，约定要自己立。**

## 7. 对比 JS / Node.js

| Python | Node.js |
|--------|---------|
| `os.environ['HOME']` | `process.env.HOME` |
| `os.environ.get('XXX', '默认值')` | `process.env.XXX ?? '默认值'` |
| `os.environ['X'] = '1'` | `process.env.X = '1'` |
| `python-dotenv` | `dotenv` |

完全一样的概念，API 名字不同。
