# Python 环境管理

## TL;DR

**一个"环境"本质上就是一个文件夹**，里面装着独立的 Python 和库；「激活环境」做的唯一一件事是改 `PATH`。

管理环境有**三条独立路线**，选一条用就行：

| 路线 | 组成 | 一句话 |
|---|---|---|
| A | pyenv + venv + pip | 经典组合，三个工具各管一段 |
| B | Conda（Anaconda / Miniconda） | 数据科学向，**能装非 Python 的系统级依赖** |
| C | [[0.05 uv\|uv]] | 一个二进制把 A 的三段全包了，还多管锁文件，**快** |

选择建议：新项目走 C；需要 ffmpeg、gcc、R 这类非 Python 程序走 B；需要自定义编译选项的解释器才用到 A 里的 pyenv。

多环境**不会**成倍占磁盘——三条路线都用「中央缓存 + 链接」去重（和 pnpm 同一思路，见第 7 节）。

---

## 1. 环境是什么

### 1.1 环境就是一个文件夹

一个环境就是一个文件夹，里面装着一套独立的 Python 和库。以 Conda 为例（工具本身第 4 节再讲）：

```bash
conda env list
# base     ~/anaconda3
# d2l      ~/anaconda3/envs/d2l
```

文件夹结构：

```text
~/anaconda3/envs/d2l/
├── bin/
│   ├── python          ← 这个环境自己的 Python
│   └── pip             ← 这个环境自己的 pip
└── lib/
    └── python3.13/
        └── site-packages/
            ├── numpy/   ← 这个环境装的库
            ├── torch/
            └── ...
```

**三条路线建出来的环境都是这个结构**，差别只在放在哪个目录、由谁来建。

### 1.2 为什么要隔离

项目 A 需要 `numpy 1.x`，项目 B 需要 `numpy 2.x`，放两个文件夹就不会打架。

类比：每个项目是一台"手机"，各装各需要的 app，互不干扰。

### 1.3 「激活环境」做的唯一一件事是改 PATH

`conda activate d2l`、`source .venv/bin/activate` 这类命令，本质上都只是**把那个环境的目录插到 `PATH` 最前面**，让 `python` 命令指向环境里的那个 Python，而不是系统默认的。

终端提示符开头的括号就是当前环境名：

```text
(base) user@... %        ← 默认环境
(d2l)  user@... %        ← 切到了 d2l 环境
```

**理解这一点，绝大多数「环境问题」就不神秘了**：包装在了 A 环境、脚本用 B 环境跑，起因永远是 `python` 这个词解析到了谁。第一件事永远是确认现在站在哪：

```bash
python -c "import sys; print(sys.executable)"
```

（这条线的完整展开见 [[Python/Map|Python 知识地图]] 第 1 节。）

## 2. 三条路线

### 2.1 三条路线各是什么

```text
路线 A：pyenv + venv + pip          经典组合，三个工具各管一段
路线 B：Conda（Anaconda/Miniconda）  一个工具全包，还能装非 Python 依赖
路线 C：uv                          一个二进制全包，只管 Python 生态，但快
```

三者是**完全独立的体系**，没有依赖关系，不需要先学会一条再学下一条。

### 2.2 职责分工对照

一条路线要覆盖四件事，看各自怎么分：

| | 管 Python 版本 | 管虚拟环境 | 管第三方库 | 管锁文件 |
|---|---|---|---|---|
| **A** pyenv + venv + pip | pyenv | venv | pip | 不管（要额外上 pip-tools） |
| **B** Conda | conda | conda | conda | 半管（`environment.yml`） |
| **C** [[0.05 uv\|uv]] | uv | uv | uv | **uv**（`uv.lock`） |

「锁文件」指的是把每个依赖的精确版本记下来，保证换台机器装出一模一样的环境。路线 A 原生缺这块，是它最大的短板。

### 2.3 怎么选

完整对比在第 6 节，先给结论：

- **新项目** → 路线 C（uv）
- **要装非 Python 的程序**（ffmpeg、gcc、cmake、R） → 路线 B（Conda）
- **要自定义编译选项的解释器** → 路线 A 里的 pyenv
- **接手的老项目已经在用某条路线** → 跟着它走，别混用

## 3. 路线 A：pyenv + venv + pip

### 3.1 三个工具各管一段

这条路线的特点是**职责拆得很细**，每个工具只做一件事：

```text
pyenv   →  装哪个版本的 Python 解释器
venv    →  用某个解释器建一个隔离的环境文件夹
pip     →  往环境里装第三方库
```

好处是每一层都能单独替换，坏处是要记三套命令，而且**没有一个工具管锁文件**。

### 3.2 pyenv：只管解释器版本

它不管库、不管环境，只负责「机器上装哪几个 Python，当前用哪个」：

```bash
pyenv install 3.13    # 装 3.13
pyenv install 3.14    # 装 3.14
pyenv global 3.13     # 全局默认用 3.13
pyenv local 3.14      # 这个项目目录用 3.14（写一个 .python-version 文件）
```

两个要点：

- **它是现场编译的**——`pyenv install` 会下载源码在你机器上 build，几分钟起步，还得先装齐编译器和开发头文件
- **它靠 shim 机制劫持 `python` 命令**——在 `PATH` 最前面塞一堆同名脚本，每次执行 `python` 都被拦下来查 `.python-version` 再转发。所以才有 `pyenv rehash` 这种东西，也常出现「我以为在这个版本其实在那个」

另外，**pyenv 官方不支持 Windows**，Windows 上要用第三方的 pyenv-win。

### 3.3 venv：只管虚拟环境

Python 自带的标准库模块，不需要额外安装：

```bash
python -m venv .venv          # 用当前的 python 建一个环境
source .venv/bin/activate     # 激活（Windows 是 .venv\Scripts\activate）
deactivate                    # 退出
```

建出来就是第 1.1 节那个文件夹结构，外加一个 `pyvenv.cfg` 记录「我是基于哪个 Python 建的」。

**venv 是 Python 官方标准（PEP 405）**，所以 IDE、pytest、各种工具都认它。uv 建的环境也是这个格式。

### 3.4 pip：只管装包

```bash
pip install requests
pip install -r requirements.txt    # 按清单装
pip freeze > requirements.txt      # 导出当前环境的包
pip uninstall requests
pip list
```

`pip freeze` 导出的**不是锁文件**——它只是当前环境的快照，不区分「我直接要的」和「被依赖拖进来的」，也不记录依赖之间的关系。这就是路线 A 需要额外上 pip-tools 或干脆换路线的原因。

pip 装的到底是什么东西（wheel / 源码包）见 [[0.04 打包与分发]]。

## 4. 路线 B：Conda

### 4.1 Anaconda 是发行版，Conda 是工具

这两个词经常被混着说，实际是**包含关系**：

```text
Anaconda（一个发行版 = 打包好的安装包）
├── Python 本身
├── 几百个预装的数据科学库（numpy、pandas、matplotlib、scikit-learn、jupyter…）
└── Conda（命令行工具 = 包管理器 + 环境管理器）   ← 装完之后你天天敲的是它
```

类比：

- **Python 官方** = 裸机电脑，什么软件都没有，需要什么自己装
- **Anaconda** = 预装好常用软件的电脑，开箱即用
- **Conda** = 那台电脑上的应用商店 + 分身管理器

### 4.2 Anaconda 与 Miniconda 怎么选

| | Anaconda | Miniconda |
|---|---|---|
| 装什么 | Python + Conda + 几百个库 | 只装 Python + Conda |
| 体积 | 几个 GB | 几百 MB |
| 适合 | 想开箱即用、不在乎体积 | 想自己控制装什么（**推荐**） |

两者的 Conda 是同一个，后续用法完全一样。

### 4.3 Conda 装包

```bash
conda install numpy
conda install pytorch
conda remove numpy
conda list              # 看当前环境装了什么
conda search xxx        # 搜索可用的包
```

**和 pip 的关键区别：pip 只能装 Python 包，Conda 能装非 Python 的东西**——C 库、CUDA 工具包、甚至 ffmpeg、cmake、gcc、R。这是路线 B 至今不可替代的唯一理由。

（不过这条优势比几年前小了：现在 CUDA 运行时也以普通 wheel 的形式发在 PyPI 上，`pip install torch` 就能装齐，见 [[0.05 uv]] 第 5.2 节。）

**尽量别在 Conda 环境里混用 pip**——两套包管理器互相不知道对方装了什么，容易把环境搞坏，磁盘也会多占（见第 7.2 节）。实在要混，原则是「先 conda 装完，最后再 pip 补」。

### 4.4 Conda 管环境

```bash
conda create -n d2l python=3.13   # 创建环境
conda activate d2l                 # 进入环境
conda deactivate                   # 退出，回到 base
conda env list                     # 列出所有环境
conda remove -n d2l --all          # 删掉整个环境
```

注意 Conda 的环境**默认统一放在 `~/anaconda3/envs/` 底下**，按名字管理，而不是像 venv/uv 那样放在项目目录里。所以它是「全局一张环境列表」的心智模型。

### 4.5 常用命令速查

| 命令 | 作用 |
|------|------|
| `conda --version` | 查看 Conda 版本 |
| `conda env list` | 列出所有环境 |
| `conda list` | 当前环境的所有包 |
| `conda list -n 环境名 python` | 查看某环境的 Python 版本 |
| `conda install xxx` | 装包 |
| `conda update xxx` | 更新包 |
| `conda search xxx` | 搜索可用的包 |
| `conda create -n 名字 python=3.x` | 创建新环境 |
| `conda activate 名字` | 切换环境 |
| `conda deactivate` | 退出当前环境 |
| `conda remove -n 名字 --all` | 删掉整个环境 |
| `conda clean --all` | 清理缓存 |

查看当前环境的 Python 版本直接用 `python --version`。

## 5. 路线 C：uv

### 5.1 一个二进制全包

Rust 写的单个可执行文件，把路线 A 的三段加上锁文件一口气全管了：

```bash
uv python install 3.13    # 相当于 pyenv install
uv venv                   # 相当于 python -m venv
uv pip install requests   # 相当于 pip install
uv lock / uv sync         # 路线 A 原生没有的那一块
```

三个和前两条路线不同的地方：

- **装解释器是下载预编译二进制**（几秒），不是像 pyenv 那样现场编译（几分钟）
- **默认不碰你的全局 `python`**，没有 `pyenv global` 那种东西，也没有 shim 拦截
- **建出来的就是标准 venv**，不是自创格式，IDE 和其他工具直接认（这点和 Conda 不同）

### 5.2 与前两条路线的对应关系

| 路线 A 的做法 | 路线 C 的做法 |
|---|---|
| `pyenv install 3.13` | `uv python install 3.13` |
| `pyenv local 3.13` | `uv python pin 3.13`（写同一个 `.python-version`） |
| `python -m venv .venv` | `uv venv` |
| `pip install requests` | `uv pip install requests` 或 `uv add requests` |
| `pip install -r requirements.txt` | `uv sync` |
| 手动 activate 再跑命令 | `uv run <命令>`（自动用项目环境） |
| （需要额外上 pip-tools） | `uv lock` |

### 5.3 完整展开在另一篇

作用域（为什么它只管项目不管全局）、能装什么、边界在哪、命令速查——见 [[0.05 uv]]。

## 6. 三条路线横向对比

### 6.1 能力对照

| | pyenv + venv + pip | Anaconda / Conda | [[0.05 uv\|uv]] |
|---|---|---|---|
| 管 Python 版本 | pyenv 管 | 管 | 管 |
| 管虚拟环境 | venv 管 | 管 | 管 |
| 管第三方库 | pip 管 | 管 | 管 |
| 管锁文件 | 不管 | 半管 | **管** |
| 预装科学库 | 不预装 | 预装几百个 | 不预装 |
| 能装非 Python 程序 | 否 | **能** | 否 |
| 体积 | 很小 | 很大（几个 GB） | 很小（单个二进制） |
| 装解释器的方式 | **现场编译**，几分钟 | 下载预编译 | **下载预编译**，几秒 |
| 环境放在哪 | 项目目录里（`.venv/`） | 全局统一（`~/anaconda3/envs/`） | 项目目录里（`.venv/`） |
| 会改你的 `python` 命令吗 | **会**（shim 拦截 PATH） | 会（activate 改 PATH） | **不会**（除非主动开启） |
| Windows 支持 | pyenv 官方不支持 | 支持 | 一等公民 |
| 速度 | 一般 | 慢（依赖解析尤其慢） | **快** |

### 6.2 类比

- **pyenv** = 遥控器，专门切电视频道（Python 版本），别的不管
- **Anaconda** = 一整套家庭影院系统，全包了，但占地方
- **uv** = 也是全包，但只装 Python 生态这一套，换来体积小和速度快

### 6.3 什么时候必须用哪条

| 场景 | 选择 | 理由 |
|---|---|---|
| 新项目、纯 Python 生态 | **uv** | 一个工具全包，且有锁文件 |
| 已有 `requirements.txt` 的老项目 | **uv** 兼容层 | `uv pip` 原地替换，工作流不用改 |
| 要 ffmpeg / gcc / cmake / R | **Conda** | 只有它能装非 Python 程序 |
| 要自定义编译选项的解释器 | **pyenv** | 只有它是现场编译 |
| 需要 3.8 以前的老版本 Python | **pyenv** | uv 提供的预编译版本最老到 3.8 |

## 7. 磁盘占用：中央缓存 + 链接

这一节对三条路线都适用。

### 7.1 库不是每个环境存一份

环境文件夹确实一个项目一个，但**库不是完全重复存储的**。以 Conda 为例，下载的每个包只真正落盘一次，存在中央包缓存 `pkgs/` 里，各环境通过**硬链接**共享同一份文件：

```text
~/anaconda3/
├── pkgs/                    ← 中央缓存（相当于 pnpm 的全局 store）
│   ├── numpy-1.26.4-py313.../
│   └── torch-2.3.0-.../
└── envs/
    ├── d2l/lib/.../site-packages/numpy/      ← 硬链接指向 pkgs/
    └── another-env/.../site-packages/numpy/  ← 指向磁盘上同一份数据
```

创建新环境时，如果 `pkgs/` 里已有完全相同版本和构建的包，Conda 不重新下载也不复制，只建硬链接。**10 个环境都装 `numpy 1.26.4`，磁盘上只占一份。**

### 7.2 什么时候还是会重复占空间

| 情况 | 原因 |
|------|------|
| 版本不同 | `numpy 1.x` 和 `2.x` 各存一份——这正是隔离的目的，不算浪费 |
| pip 装进 Conda 环境的包 | pip 的安装产物不做硬链接，每个环境复制一份；混用越多重复越多 |
| 跨文件系统 | 环境建在另一块盘上时硬链接失败，降级为复制 |
| 缓存膨胀 | 删环境不会自动清缓存，只增不减 |

### 7.3 清理与检查

```bash
du -sh ~/anaconda3/envs/*   # 看各环境大小（硬链接会让数字虚高，实际占用更小）
conda clean --all           # 清理没有被任何环境引用的缓存包
uv cache clean              # uv 的对应命令
```

### 7.4 三个生态是同一个思路

[[0.05 uv|uv]] 在这方面做得更彻底——同样是全局缓存，且在 macOS 的 APFS 文件系统上直接用 copy-on-write 克隆，建环境几乎不占额外空间。

```text
Conda   pkgs/ 中央缓存      + 硬链接
pnpm    全局 store          + 硬链接
uv      全局 cache          + 硬链接 / copy-on-write
```

**「中央存储 + 链接」这套心智模型建立一次，Conda、pnpm、uv 就全通了**（pnpm 那侧见 [[1.03 npm、yarn 与 pnpm]]）。

## 8. 为什么终端里有那么多 python 命令

同时装了几条路线的工具，机器上的 Python 就会很多：

| 命令 | 来源 |
|------|------|
| `python` | 当前激活的环境（Conda base / venv / 系统默认） |
| `python3` | 系统自带 |
| `python3.13`、`python3.14` | pyenv 装的 |
| `py` | Windows 的 Python 启动器 |
| `python3-config` 等 | C 扩展编译工具，不用管 |
| `pythonw`、`python.app` | macOS GUI 相关，不用管 |
| `python-build` | pyenv 的内部工具 |

**别去数有几个，直接问当前这个是谁：**

```bash
python -c "import sys; print(sys.executable)"    # 我现在用的是哪个
which -a python                                   # PATH 里所有同名的，按优先级排
```

第一条给的是确定答案，第二条能看出为什么是它——排在最前面的赢。
