# 打包与分发

## TL;DR

**PyPI 上一个包通常有两种分发形式**：

| 形式 | 后缀 | 是什么 | 安装时 |
|---|---|---|---|
| 源码包（sdist） | `.tar.gz` | **原料**：源码 + 构建脚本 | 在你机器上跑一遍构建，带 C 代码就要编译器 |
| wheel | `.whl` | **成品**：别人编译打包好的 | 解压 + 拷贝，不执行任何代码 |

- wheel 的**文件名本身就是说明书**：五段分别是包名、版本、Python 版本、ABI、平台
- 纯 Python 的包一个 wheel 通吃全平台；带编译产物的包要为每种组合各发一个（numpy 一个版本 65 个）
- **两种形式都得留着**：wheel 覆盖不到的平台只能靠源码包兜底
- wheel 用 zip、源码包用 tar.gz，是「能随机读取」和「压得更小」之间的相反取舍

---

## 1. 为什么需要两种发布形式

### 1.1 大部分库就是一堆 .py 文件

解释器读进去直接跑，跟你自己写的代码没区别。这种库怎么发都好办，打个压缩包发过去就行。

### 1.2 追求速度的库里藏着 C 代码

Python 本身跑得慢（原因见 [[5.15 CPython 解释器原理]]：每条字节码都要过解释器循环，每个数字都是带引用计数的堆对象），所以 numpy、Pillow 这类性能敏感的库会把关键部分**改用 C 语言重写**。

两个词先说清楚：

- **编译**：C 源码是人能读的文本，CPU 看不懂，必须先翻译成机器码。Python 不需要这步，C 必须要。
- **C 扩展**：用 C 写好、编译成机器码、能被 Python 当普通模块 `import` 的东西。Windows 上是 `.pyd`，Linux/macOS 上是 `.so`。

### 1.3 编译有三个讨厌的性质

正是它们决定了后面的一切：

| 性质 | 后果 |
|---|---|
| **需要工具** | 用户机器上得有编译器和开发头文件，很多人（尤其 Windows）没有 |
| **需要时间** | 大型库几分钟到几十分钟 |
| **产物不通用** | Windows 上编的拿到 Linux 用不了；给 3.12 编的给 3.13 也用不了 |

于是「怎么把库发给用户」就成了一道选择题：**发原料让用户自己加工，还是发成品？** Python 的答案是两种都提供。

## 2. 源码包与 wheel

下面用 `markupsafe` 做对比——**同一个库、同一个版本、两种形式**。选它是因为个头小又确实带 C 代码。

### 2.1 源码包（sdist）：原料

`sdist` 是 source distribution 的缩写，后缀 `.tar.gz`：

```text
markupsafe-3.0.3.tar.gz    80 KB

markupsafe-3.0.3/src/markupsafe/__init__.py     ← Python 代码
markupsafe-3.0.3/src/markupsafe/_speedups.c     ← C 源码，还没编译 ★
markupsafe-3.0.3/setup.py                       ← 构建脚本
markupsafe-3.0.3/pyproject.toml                 ← 构建配置
markupsafe-3.0.3/tests/...                      ← 测试
markupsafe-3.0.3/docs/...                       ← 文档
```

装它的时候，pip / uv 必须**在你机器上执行那个构建脚本**，现场把 `.c` 编译一遍。没编译器就报错。

注意它还带着测试和文档——**源码包是「项目的完整快照」**，不只是能跑的那部分。

### 2.2 wheel：成品

```text
markupsafe-3.0.3-cp312-cp312-win_amd64.whl    11 个文件 37 KB

markupsafe/__init__.py
markupsafe/_speedups.c                        ← C 源码还留着（仅供参考）
markupsafe/_speedups.cp312-win_amd64.pyd      ← 13 KB，编译好的机器码 ★
markupsafe-3.0.3.dist-info/METADATA
markupsafe-3.0.3.dist-info/WHEEL
markupsafe-3.0.3.dist-info/RECORD
markupsafe-3.0.3.dist-info/licenses/LICENSE.txt
```

**关键差别就是那个 `.pyd`**：源码包里只有 `_speedups.c`，wheel 里多了它编译之后的产物。测试和文档则被剥掉了——wheel 只装你真正要用的东西。

### 2.3 两者对比

| | 源码包 `.tar.gz` | wheel `.whl` |
|---|---|---|
| 里面装的 | 源码 + 构建脚本 + 测试 + 文档 | 直接能用的成品 |
| 安装时干什么 | 在你机器上跑构建脚本 | 解压、拷贝，完 |
| 需要编译器吗 | 带 C 代码就需要 | 不需要 |
| 耗时 | 几十秒到几十分钟 | 通常一秒内 |
| 会执行别人的代码吗 | **会**（构建脚本就是代码） | **不会** |
| 一个版本发几个 | 1 个通吃 | 每种平台 × 每个 Python 版本各一个 |

最后一行的代价是实打实的。numpy 2.5.2 在 PyPI 上：

```text
源码包：  1 个
wheel：  65 个
```

### 2.4 装包工具怎么选：快车道 + 备用道

pip 和 uv 的逻辑是**优先找 wheel，找不到才回退源码包**：

```text
① 按文件名找匹配本机的 wheel
     找到  →  下载、解压、拷贝（一秒）
     没有  →  ② 下载源码包，本机构建（要编译器，几分钟）
                   失败 → 报错，提示装编译工具
```

日常安装几乎全走 wheel 那条快车道，所以你平时感觉不到源码包的存在。它为什么还必须留着，见第 5 节。

## 3. 拆开一个 wheel

### 3.1 它就是个 zip

```bash
$ head -c 4 requests-2.34.2-py3-none-any.whl | xxd
00000000: 504b 0304        →  "PK\x03\x04"
```

`PK` 是 zip 的固定标志（取自 zip 发明者 Phil Katz 的姓名缩写）。后缀改成 `.zip` 双击就能打开。

### 3.2 内容分两部分

```text
第一部分——库本身，装完原样躺在 site-packages 里：

    requests/__init__.py
    requests/sessions.py
    ...

第二部分——说明书目录，名字固定是「包名-版本.dist-info」：

    requests-2.34.2.dist-info/METADATA
    requests-2.34.2.dist-info/WHEEL
    requests-2.34.2.dist-info/RECORD
```

**装 wheel 基本上就是把第一部分解压过去，没有别的动作。** 第二部分是给工具看的，下面三节逐个拆。

### 3.3 METADATA：这个包是谁、依赖谁

```text
Name: requests
Version: 2.34.2
Requires-Python: >=3.10
Requires-Dist: charset_normalizer<4,>=2
Requires-Dist: idna<4,>=2.5
Requires-Dist: urllib3<3,>=1.26
Requires-Dist: certifi>=2023.5.7
```

`Requires-Dist` 就是依赖声明。**pip / uv 做依赖解析读的就是它**——装一个包结果拉进来十个，答案在这。

### 3.4 WHEEL：这个 wheel 本身的规格

```text
Wheel-Version: 1.0
Generator: setuptools (82.0.1)
Root-Is-Purelib: true          ← 纯 Python，不含编译产物
Tag: py3-none-any
```

`Root-Is-Purelib` 决定装到哪个目录（纯 Python 的和带二进制的在某些系统上分开放）。numpy 那个 wheel 这一行是 `false`。`Tag` 就是第 4 节要讲的文件名标签。

### 3.5 RECORD：每个文件的指纹清单

```text
requests/__init__.py,sha256=MRFX5_pKqRZsgn1SN-b9aU7rXKVJ7kDi6Q-J8hq81W4,5922
```

三段：路径、内容的 sha256、字节数。

sha256 是一种把任意文件算成固定长度字符串的算法——文件改一个字节，算出来的串就完全不同。两个用途：

- **校验**——装完核对文件有没有损坏或被篡改
- **卸载**——`pip uninstall` 靠它知道该删哪些文件。没有这份清单，工具根本不知道 `site-packages` 里哪些文件属于哪个包

## 4. 文件名就是说明书

### 4.1 五段结构

wheel 的文件名不是随便起的，用 `-` 分成五段，每段都有确定含义：

```text
numpy  -  2.5.2  -  cp312  -  cp312  -  win_amd64  .whl
  ①        ②         ③        ④          ⑤
 包名      版本    Python版本   ABI        平台
```

前两段不用解释，后三段各自展开。

### 4.2 ③ Python 版本标签：给哪个 Python 用

```text
cp312   CPython 3.12（cp = CPython，即官方那个解释器）
cp313   CPython 3.13
py3     任何 Python 3 都行
pp310   PyPy 3.10（另一个 Python 解释器实现）
```

### 4.3 ④ ABI 标签：机器码和解释器之间的约定

ABI 全称 Application Binary Interface（应用二进制接口），指**编译好的机器码和解释器之间互相调用时遵守的约定**：参数怎么传、数据结构在内存里怎么摆、函数怎么命名。

为什么需要单独一个标签？因为**这套约定在 Python 大版本之间会变**。给 3.12 编的 C 扩展按 3.12 的内存布局访问数据，换到 3.13 上布局变了，轻则报错重则崩溃。

```text
cp312   只能配 CPython 3.12 的 ABI
none    不含编译产物，不依赖任何 ABI
abi3    用了「稳定 ABI」——只用官方承诺不变的那部分接口，
        一次编译能跨多个 Python 版本用
```

`abi3` 是发布者减少 wheel 数量的办法：代价是只能用受限的 API，换来不必为每个 Python 版本单独编一份。

### 4.4 ⑤ 平台标签：能在什么系统和 CPU 上跑

```text
win_amd64                 64 位 Windows（Intel/AMD 芯片）
win32                     32 位 Windows
win_arm64                 ARM 芯片的 Windows
macosx_11_0_arm64         macOS，Apple 芯片
macosx_14_0_x86_64        macOS，Intel 芯片
manylinux_2_27_x86_64     大部分 Linux，Intel/AMD 芯片
musllinux_1_2_x86_64      Alpine 这类精简 Linux
any                       任何平台
```

Windows 和 macOS 的标签一看就懂，Linux 那两个需要单独解释。

### 4.5 manylinux：Linux 上的兼容性约定

Windows 和 macOS 各只有一家厂商，环境统一。Linux 有几百个发行版，底层库版本各不相同——「给 Linux 编译的包」到底能在哪些 Linux 上跑？

关键卡在 **glibc** 上。glibc 是 Linux 最底层的 C 标准库，几乎所有程序都依赖它，特点是**新版本兼容老版本编译的程序，反过来不行**。

`manylinux_2_27` 的意思就是：**这个包在 glibc 2.27 环境里编译，所以任何 glibc ≥ 2.27 的 Linux 都能用。**

发布者的策略因此是「用尽量老的 glibc 编译」，换取尽量广的兼容范围。

`musllinux` 是另一套，给 Alpine Linux 这类用 musl 而非 glibc 的精简系统准备——Docker 镜像里常见，因为 Alpine 体积小。

### 4.6 两个真实文件对照读

```text
requests-2.34.2-py3-none-any.whl
                 ↑    ↑    ↑
                 |    |    └─ 任何操作系统
                 |    └────── 不依赖 ABI
                 └─────────── 任何 Python 3
读法：纯 Python 写的，一个文件全世界通用


numpy-2.5.2-cp312-cp312-win_amd64.whl
              ↑     ↑      ↑
              |     |      └─ 只能 64 位 Windows
              |     └──────── 只能配 CPython 3.12 的 ABI
              └────────────── 只给 CPython 3.12
读法：含编译产物，挑系统也挑版本
```

两个文件各自的 `WHEEL` 文件也对得上：

```text
requests:  Root-Is-Purelib: true     Tag: py3-none-any
numpy:     Root-Is-Purelib: false    Tag: cp312-cp312-win_amd64
```

### 4.7 这样设计的好处

**装包工具光看文件名就知道该不该下载**，不用先拉几十兆下来解开看。

面对 numpy 那 65 个 wheel，uv 只要知道「64 位 Windows + Python 3.12」，一眼挑出唯一那个。这是依赖解析能做得快的原因之一（见 [[0.05 uv]] 第 6 节）。

## 5. 为什么不全部切换到 wheel

wheel 好处这么多，为什么还留着源码包？

### 5.1 纯 Python 的包早就全切了

`py3-none-any` 那种 wheel 全平台通用，requests 一个 wheel 走遍天下，压根不存在「切不切」的问题。

**所以这个问题只存在于带编译产物的包。**

### 5.2 成品必须先有人做

发布者只能为**他们预见到的组合**编译，而组合是「系统 × CPU 架构 × Python 版本 × 解释器实现」乘出来的，永远有覆盖不到的角落。

numpy 2.5.2 的 65 个 wheel 覆盖 Python 3.12~3.15 和 11 种平台，没覆盖的包括：

- **Python 3.10、3.11**——新版 numpy 已不再为它们发 wheel
- **PyPy**——另一个 Python 解释器实现，不是官方 CPython
- **FreeBSD、32 位 Linux、IBM 大型机架构**——不在那 11 种里
- **明天才出现的新平台**

这些人走的就是那 1 个源码包。**源码包的角色是兜底**——没有它，上面这些组合就彻底装不上这个库了。

### 5.3 有些场景必须从源码构建

即使有现成 wheel，这些情况也得自己编：

| 场景 | 原因 |
|---|---|
| Linux 发行版打包 | Debian / Fedora 有硬性政策，必须在自己的构建服务器上从源码编译 |
| 针对本机 CPU 优化 | 通用 wheel 只敢用老旧通用指令集，榨性能要自己编 |
| 打补丁 | 改了库里一行代码就得重新构建 |
| 链接系统特定版本的库 | 比如全系统统一某个加密库版本，而非用 wheel 自带的 |
| 安全审计与合规 | 要看源码、要能复现构建；wheel 剥掉了测试、文档、构建脚本 |

### 5.4 结论：不是二选一

回到第 2.4 节那张流程图——**wheel 是快车道，源码包是备用道**。真要「全切 wheel」，等于宣布没有预编译版本的平台就别用这个库了。生态不会这么干。

## 6. 两种压缩格式：zip 与 tar.gz

wheel 用 zip，源码包用 tar.gz。这不是历史遗留，两边各有各的道理。

### 6.1 `.tar.gz` 是两层叠在一起

它不是一个格式，是两个各干一件事：

```text
markupsafe-3.0.3.tar.gz
                └─┬─┘└┬┘
                  │   └── 第二步：gzip 压缩
                  └────── 第一步：tar 打包
```

- **tar**（tape archive，磁带归档，1979 年就有了）：把一堆文件**串成一个文件**，只合并、不压缩
- **gzip**：压缩，把一个文件变小

为什么分两步？因为 **gzip 一次只能压一个数据流，完全不懂「多个文件」和「目录」**。必须先用 tar 揉成一个再压。典型的 Unix 思路：每个工具只做一件事，靠组合解决问题。

拆开跑一遍就看清楚了：

```bash
$ gzip -d markupsafe-3.0.3.tar.gz    # 只解压缩，不解包
$ file markupsafe-3.0.3.tar
POSIX tar archive                     # 里面是 tar 归档，还没拆
```

### 6.2 这个格式跟 Python 无关，是 Unix 通用标准

npm 的包也是它——`npm pack` 产出的 `.tgz` 就是 `.tar.gz` 的缩写（早年 DOS 只允许三字符后缀，塞不下就缩了）：

```bash
$ head -c 2 markupsafe-3.0.3.tar.gz   →  1f 8b
$ head -c 2 is-odd-3.0.1.tgz          →  1f 8b     # 同一个格式
```

`1f 8b` 是 gzip 的固定标志。同一条 `tar` 命令能打开两个生态的包。

除此之外，Linux 内核源码、Docker 镜像的每一层、服务器备份，用的都是它。

### 6.3 随机读取与压缩率是同一枚硬币的两面

zip 能**不解开整个包就单独取出某个文件**（文件末尾有目录表，想拿哪个直接跳过去读）。tar.gz 做不到——gzip 是流式压缩，要读第 500 个文件必须把前面 499 个全解一遍。

但这个能力有代价。同一份 markupsafe 源码，**都用 deflate 算法、都开最高压缩级别 9**：

```text
源码原始大小 ： 262282 字节（37 个文件）
tar.gz       ：  79700 字节   压到 30%
zip          ：  88204 字节   压到 34%     ← 大了 11%
```

算法相同、级别相同，差别在于：**zip 每个文件独立压缩，tar.gz 把所有文件连成一条流整体压缩。**

压缩靠找重复模式。几十个 `.py` 文件的 import、命名习惯、缩进高度相似，tar.gz 能跨文件利用这些重复；zip 每压一个文件就把「记忆」清零。

而**zip 之所以能随机读取，正是因为每个文件独立压缩**——独立了才能单独取出来解开：

```text
zip     每个文件独立压缩  →  能单独取  →  压得松
tar.gz  所有文件连成一流  →  必须全解  →  压得紧
```

只能挑一个。

### 6.4 tar 还保留 Unix 文件属性

源码包里的构建脚本需要**可执行权限**，有些项目还用**符号链接**（一个文件指向另一个文件）。

tar 原生记录权限、属主、时间戳、符号链接——它本来就是为 Unix 备份设计的。zip 出身 DOS，那个系统没这些概念，后来靠扩展字段补，但支持零碎、各家实现不一致。

源码包解开后要直接拿来构建，权限丢了就出问题。wheel 没这顾虑——里面主要是 `.py` 和二进制，装包工具按自己的规则设权限。

### 6.5 于是两边各自选对了

| | 需求 | 选择 | 理由 |
|---|---|---|---|
| **wheel** | 装包工具想先偷看几 KB 的 METADATA 做依赖解析 | zip | 用得上随机读取，接受体积大一点 |
| **源码包** | 必须整个解开才能构建 | tar.gz | 用不上随机读取，换更小的体积；顺带保住文件权限 |

（这跟 [[AI/Map|AI 知识地图]] 里 safetensors「按偏移量随机读取某个张量」是同一个设计思路：**在文件里留一张索引表，换取按需读取的能力**。）

### 6.6 常见的几个亲戚

换掉压缩那层就是另一个后缀，打包那层始终是 tar：

| 后缀 | 压缩工具 | 特点 |
|---|---|---|
| `.tar.gz` / `.tgz` | gzip | 最通用，压解都快 |
| `.tar.bz2` | bzip2 | 压得更小但慢，现在少见 |
| `.tar.xz` | xz | 压缩率最高，压时慢，Linux 内核用 |
| `.tar.zst` | zstd | 新秀，接近 xz 的压缩率但快得多 |
| `.tar` | 无 | 只打包不压缩 |

## 7. 三个容易搞错的点

### 7.1 wheel 不等于闭源

requests 的 wheel 解开就是一堆 `.py` 明文，谁都能读。**只有 C 那部分才真正被编译成了看不懂的机器码。**

所以发 wheel 保护不了纯 Python 代码——这跟 [[0.03 解释型语言与代码发布]] 讨论的是同一件事。

### 7.2 wheel 比源码包安全一档

装源码包会在你机器上执行构建脚本，那是别人写的代码，能干任何事。装 wheel 只是解压和拷贝文件，不执行任何东西。

（当然，装完之后你 `import` 它，那就是另一回事了。）

### 7.3 名字的来历

wheel 取自 cheese wheel（一整轮奶酪），因为 PyPI 早年叫 CheeseShop——来自 Monty Python 的一个小品，而 Python 这门语言的名字本来就取自 Monty Python。

## 8. 与 JS 生态对照

| 概念 | Python | JavaScript |
|---|---|---|
| 包仓库 | PyPI | npm registry |
| 包文件格式 | `.whl`（zip）/ `.tar.gz` | `.tgz`（tar.gz） |
| 依赖声明 | `pyproject.toml` → wheel 里的 METADATA | `package.json` |
| 装到哪 | `site-packages/` | `node_modules/` |
| 预编译二进制 | wheel 里直接带 | 靠 `node-gyp` 现场编译或 prebuild 下载 |
| 平台标签 | 写在文件名里 | `os` / `cpu` 字段 + 可选依赖 |

最大的差别是**预编译**：Python 把「为每个平台编译好」做进了分发格式本身（wheel 的文件名标签），npm 直到今天还常常要在安装时现场编译原生模块——`npm install` 卡在 node-gyp 上就是这个原因。
