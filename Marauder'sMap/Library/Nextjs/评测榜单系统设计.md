# 评测榜单系统设计：baseline 预置 + 用户提交统一表

## TL;DR

**用同一张 `Submission` 表既装系统预置 baseline，又装用户提交，靠 `userId + isPublic` 区分来源，避免双轨数据。**

- 所有分数（不管哪来的）都写进同一张 `Submission` 表
- 系统 baseline 由 seed 脚本以 `official@xxx.com` 用户身份 upsert，`isPublic=true`
- 用户提交走正常评测流程，写入同表
- 榜单 API 按 `(userId, agentName, benchmark)` 聚合取最高分
- 离线评测报告（JSON）是 baseline 的数据源，seed 脚本读 JSON → 写 DB

---

## 1. 为什么要这么设计

榜单页面常见的需求是「展示官方测过的 baseline 模型分数 + 让用户自己跑分上榜」。直觉上会想：

- 方案 A：baseline 写死在前端常量里，用户分数走 DB
- 方案 B：baseline 一张表，用户提交另一张表
- 方案 C：**统一一张表，靠字段区分**

方案 C 的好处一目了然：

| 维度 | A: 前端常量 | B: 两张表 | C: 统一表 |
|------|------------|----------|----------|
| 排名计算 | 要写两套逻辑 | 要 JOIN 或并联查询 | 一条 SQL 解决 |
| 更新 baseline | 改前端代码 + 部署 | 单独写脚本 | 跟用户提交走同样链路 |
| 数据 schema 变更 | baseline 跟不上 | 两张表都得改 | 改一处 |
| 排序融合（Borda/RRF） | 混不起来 | 要先归一 | 天然在一起 |

代价是 schema 需要带几个区分字段：`userId`、`isPublic`、可能再加 `source` / `isBaseline`。

## 2. 数据流全景

```text
                ┌──────────────────────────────────────┐
                │       离线评测框架（外部）           │
                │  跑评测 → 产出 JSON 报告              │
                │  benchmark/report/medhall/*.json     │
                │  benchmark/report/eslbench/*.json    │
                └──────────────────────────────────────┘
                              │
                              │ Node 脚本读 JSON
                              ▼
                ┌──────────────────────────────────────┐
                │   seed-baseline-submissions.mts      │
                │   - 确保 official@xxx 用户存在        │
                │   - 按 agentName upsert Submission   │
                │   - isPublic = true                  │
                └──────────────────────────────────────┘
                              │
                              │ Prisma
                              ▼
                ┌──────────────────────────────────────┐
                │              DB                      │
                │  Submission ⨯ Dataset ⨯ User         │
                └──────────────────────────────────────┘
                              ▲           ▲
                              │           │
                  普通用户提交│           │ 榜单 API 查
                              │           │
                ┌──────────────┐         ┌─────────────────────┐
                │ Web 评测页面 │         │ /api/leaderboard    │
                │ POST evaluate│         │ getLeaderboard()    │
                └──────────────┘         └─────────────────────┘
                                                   │
                                                   ▼
                                         前端表格渲染
```

要点：

- **baseline 不走前端硬编码**，跟用户提交一样最终都是 DB 记录
- **离线评测和在线评测产出相同格式**，seed 脚本只是把离线报告塞进 DB

## 3. Schema 关键字段

```text
Submission
├── id
├── userId         ← baseline 是 official@xxx，普通用户是自己
├── agentName      ← gpt-5.4 / theta-smart-miroflow / 用户自己起的名
├── datasetId      ← 对应哪个 benchmark + batch
├── status         ← COMPLETED 才进榜
├── isPublic       ← 控制是否公开展示
├── totalScore     ← 可以现场从 reportData 算
├── matchedCases   ← 已完成的 case 数（部分跑也可入榜）
└── reportData     ← JSON：完整的逐 case 评分明细

Dataset
├── id
├── evalBenchmark  ← medhall / eslbench
├── batch          ← full-20260520 之类的版本号
└── isLatest       ← 只展示最新版本的分数

Agent
└── (userId 1:1)   ← 用户的智能体身份，跟 User 绑定
```

榜单查询的核心条件：

```text
status = COMPLETED
AND isPublic = true
AND dataset.isLatest = true
```

## 4. baseline 怎么落地

### 4.1 准备阶段

在评测框架里跑出 JSON 报告，存到约定目录。文件名包含模型 + 时间戳：

```text
theta_llm_api_gpt-5.4_20260417_112806.json
theta_llm_api_claude-sonnet-4.6_20260417_112806.json
medhall_full-20260520_theta-smart-miroflow.json
```

### 4.2 seed 脚本骨架

```text
1. 确保 official user 存在（upsert by email）
2. 列出预置 agentName 清单 → 对每个 agent：
     - 找到对应的最新 JSON 报告（按文件名 glob + 时间戳排序）
     - 解析 reportData
     - upsert Submission（uniqueKey: userId + agentName + datasetId）
3. 标记对应 Dataset 为 isLatest = true
```

关键设计：**upsert 而不是 insert**。重跑 seed 不会产生重复记录，方便 baseline 数据迭代。

### 4.3 何时跑 seed

| 场景 | 触发 |
|------|------|
| 新增 baseline 模型 | 手动跑 seed 脚本 |
| 现有模型新版本 | 跑评测 → seed 自动取最新报告 |
| 新一批数据集 | 写新的 `seed-baseline-{batch}-submissions.mts` |

## 5. 排序融合：Borda vs RRF

榜单常常要按"综合分"排名，而单项分（ESL 总分 vs MedHall 总分）尺度不一样，直接加权会失真。两种常见融合方法：

| 方法 | 思路 | 优点 | 缺点 |
|------|------|------|------|
| **Borda** | 每个项目内排第 k 名得 (N-k+1) 分，加总 | 简单直观 | 对极端值不敏感，区分度可能不够 |
| **RRF (Reciprocal Rank Fusion)** | 每个项目内排第 k 名得 1/(k+c) 分，加总（c 通常 60） | 头部权重高，抗噪 | 不直观，需要解释 |

Service 层通常这样组织：

```text
1. SELECT 所有合格的 Submission，按 (userId, agentName, benchmark) 聚合取最高分
2. 在每个 benchmark 内排序，得到 rank
3. 用 Borda 或 RRF 把多个 benchmark 的 rank 融合成 overallScore
4. 按 overallScore 排序
5. 取 top N + 可选的当前用户（即使没进 top N 也展示）
```

## 6. 「self 行」的常见模式

榜单只展示 top 10，但当前登录用户即使排第 200 也希望看到自己。常见做法：

```text
正常 top 10 查询  ──┐
                    ├──→ 合并去重后渲染
当前用户行查询    ──┘  （前端给 self 一个高亮样式）
```

API 返回结构：

```text
{
  "rows": [...top10...],
  "self": { "rank": 47, "agentName": "...", ... } | null
}
```

如果 self 已在 top 10 里，`self` 可以省略或仍返回（前端只用 rows 渲染）。

## 7. 适用场景与边界

适合用这套模式的场景：

- 评测/竞赛榜单（有官方 baseline + 用户参赛）
- 性能 benchmark 展示（厂商基准 + 社区贡献）
- 任何"官方数据 + 用户贡献"的合并展示

**不适合**：

- baseline 数量极大且很少变动（如全国房价大盘） → 单独表 + 物化视图更合适
- baseline 计算口径完全不同（不能跟用户数据共享 schema）→ 强行合并 schema 会污染字段
