# interface 与 type

## TL;DR

**能力上 type 是超集**（联合、交叉、元组、条件类型、`typeof`/映射都只有 type 能写），**interface 独有的是声明合并**（同名自动合并，可给第三方类型「打补丁」）。经验准则：**描述对象/类的形状用 interface（可扩展、报错更友好），描述类型关系与运算用 type**；团队统一即可，别在这上面开战。

---

## 1. 能力对比总表

| 能力 | `interface` | `type` |
|---|---|---|
| 描述对象/函数形状 | ✔ | ✔ |
| 联合类型 `A \| B` | ✘ | **✔** |
| 交叉/元组/字面量/条件/映射类型 | ✘ | **✔** |
| `typeof x` 取类型 | ✘ | **✔** |
| 扩展 | `extends`（可多继承） | `&` 交叉 |
| **声明合并**（同名自动合并） | **✔** | ✘（同名报错） |
| 被 class `implements` | ✔ | ✔（对象形状的 type 也可以） |
| 递归自引用 | ✔ | ✔ |

```ts
// 只有 type 能做的
type Status = 'idle' | 'loading';           // 联合
type Pair = [string, number];                // 元组
type Fn = typeof someFunction;               // 取现有值的类型
type Keys = keyof User;                      // 类型运算（见 1.03）

// 只有 interface 能做的：声明合并
interface Window { myApp: AppInstance; }     // 给全局 Window 加属性——第三方类型打补丁的标准手法
```

**扩展差异的细节**：`extends` 是「继承并检查兼容」——冲突属性会立即报错，提示清晰；`&` 是「机械合并」——同名不同类型的属性会得到 `never` 而不报错，问题延迟暴露。这是「对象形状优先 interface」的技术理由（另一个理由是编译器对 interface 有缓存优化，超大类型时更快）。

---

## 2. 怎么选：一句话准则

- **对外暴露的对象结构、类的契约、需要被使用方扩展的类型** → `interface`（声明合并让使用方能增强，比如给库的类型加自定义字段）；
- **联合、交叉、工具类型、函数签名别名、任何类型运算** → `type`（interface 根本写不了）；
- React 组件 props：两者皆可，社区两派都有——**团队约定一致**比选哪个重要。

---

## 3. 关联概念：结构化类型

TS 判断兼容看**形状**不看名字（鸭子类型）：

```ts
interface Point { x: number; y: number }
class Vec { constructor(public x: number, public y: number) {} }
const p: Point = new Vec(1, 2);   // ✅ 形状匹配即可，无需 implements
```

推论：`implements` 只是让编译器**校验**这个类符合契约，并不改变类型兼容规则（详见 [[1.04 类、枚举与装饰器]]）。想要「名义类型」的效果（防止两个形状相同但语义不同的类型混用，如 UserId 与 OrderId），用**品牌类型**：

```ts
type UserId = string & { readonly __brand: 'UserId' };
```

## 面试问答

### Q: interface 和 type 有什么区别？怎么选？

满分答案：能力上 type 是超集——联合、交叉、元组、条件类型、映射类型、typeof 取类型都只有它能写；interface 独有声明合并，同名接口自动合并，这是给第三方库或全局类型（如 Window）打补丁的标准手法。扩展方式也不同：interface 的 extends 会检查冲突并报错，type 的 & 交叉遇到同名冲突属性会静默产出 never。准则：对象形状与对外契约用 interface（可被扩展、报错友好、编译器有缓存优化），类型运算用 type，团队保持一致最重要。

### Q: 什么是声明合并？有什么用？

满分答案：同名 interface（以及 namespace）会自动合并成员而非报错。核心用途是类型增强——给 Window、Express 的 Request、Vue 组件实例等既有类型添加自定义属性，无需修改原始声明；库作者也靠它提供可扩展的插件类型接口。type 没有这个能力，同名直接报错。

### Q: TS 的类型兼容是怎么判断的？

满分答案：结构化类型（鸭子类型）——只要形状（属性与方法签名）兼容就视为同类型，不要求显式继承或 implements，这与 Java/C# 的名义类型相反。好处是与 JS 的动态灵活性契合、第三方对象无需改造即可传入；副作用是语义不同但形状相同的类型可以互换（UserId 与 OrderId 都是 string），需要区分时用品牌类型（交叉一个带唯一标记的私有字段）人为制造不兼容。
