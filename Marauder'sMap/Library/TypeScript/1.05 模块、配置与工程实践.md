# 模块、配置与工程实践

## TL;DR

**namespace 是 ES Module 之前的模块方案（编译成 IIFE 挂对象），现代项目一律用 ESM，namespace 只留在 .d.ts 里描述全局库**。tsconfig 最该记住的：`strict`（全家桶开关）、`target/module/moduleResolution`（决定产物与解析行为）、`isolatedModules`（单文件转译约束）。类型声明用 `declare`，第三方库类型走 `@types/*`。

---

## 1. namespace vs ES Module

```ts
namespace Utility { export function log(m: string) {} }
// 编译产物：(function (Utility) { Utility.log = …; })(Utility || (Utility = {}));
```

本质是「全局对象 + IIFE 封装」（同 [[1.01 JS 模块化演进：CommonJS 与 ESM]] 里的模块模式）——依赖关系隐式、全局污染、无法 Tree Shaking，**typescript-eslint 的 no-namespace 规则默认禁用它**。

判定规则：**文件里有顶级 import/export 就是模块（作用域私有），否则内容是全局的**——「为什么我的 .ts 里声明的类型报重复」多半是忘了 export 变成全局脚本。

namespace 唯一的现役场景：**`.d.ts` 中描述全局 UMD 库的层级结构**（`declare namespace JQuery {}`），以及 `declare global {}` 里扩展全局类型（配合声明合并，见 [[1.02 interface 与 type]]）。

## 2. tsconfig 关键项

```jsonc
{
  "compilerOptions": {
    "target": "ES2020",           // 语法降级目标（配合 browserslist 思路，见 Babel 篇）
    "module": "ESNext",           // 产物模块格式；配 "moduleResolution": "Bundler"（TS 5.0+，给 Vite/webpack 用）
    "strict": true,               // ★ 全家桶：strictNullChecks、noImplicitAny 等一并开
    "isolatedModules": true,      // 保证每个文件可独立转译（Babel/esbuild/swc 前提）
    "esModuleInterop": true,      // 修正 CJS 默认导入的互操作
    "skipLibCheck": true,         // 跳过 .d.ts 检查，显著提速
    "paths": { "@/*": ["src/*"] },// 路径别名（构建工具需同步配置 alias）
    "noEmit": true                // 只做类型检查，产物交给 Vite/esbuild
  }
}
```

四个必答点：

- **strict 必开**——尤其 strictNullChecks，它是 TS 防空值崩溃的核心（见 [[1.01 类型系统基础]]）；老项目迁移可分阶段开子项；
- **isolatedModules 的由来**：Babel/esbuild/swc 是**单文件转译**（不做跨文件类型分析），因此 `export { SomeType }` 这类「只在类型层存在」的导出会出错——解法是 `export type { T }` / `import type { T }` 显式标注；这也是 **const enum 在 Babel 下不可用**的同一根因（见 [[1.04 类、枚举与装饰器]]）；
- **类型检查与转译分离**（现代工程标配）：Vite/esbuild 只做「删类型」的极速转译（因此 IDE 报错不会阻断 dev 启动），类型检查交给 `tsc --noEmit` 在 CI 和编辑器里跑；
- 动态 `import()` 要保留成运行时代码分割语句（见 [[2.04 代码分割与构建优化实战]]），`module` 必须是 ESNext/ES2020 一类而非 CommonJS，否则被降级成 require 就失去分包能力。

## 3. 类型声明与第三方库

```ts
// 1) 描述全局变量/UMD 库
declare const __APP_VERSION__: string;
declare module 'legacy-lib' { export function doIt(): void }   // 无类型的库先兜住

// 2) 让非代码资源可导入（Vite/webpack 项目常见）
declare module '*.svg' { const src: string; export default src }

// 3) 扩展全局类型（声明合并）
declare global {
  interface Window { __store: Store }
}
export {};   // ★ 有 declare global 的文件必须是模块，故补一个空 export
```

第三方库类型三种来源：**库自带**（package.json 的 `types` 字段，见 [[1.02 package.json 与依赖管理]]）→ **DefinitelyTyped**（`npm i -D @types/xxx`）→ **自己写 .d.ts 兜底**。

## 4. 工程实践清单

- **边界处校验**：接口响应用 `unknown` + zod/valibot 做运行时校验再断言——**TS 只保证编译期，运行时的锅得运行时接**（呼应 [[1.01 类型系统基础]] 的 any/unknown 之辨）；
- 迁移策略：`allowJs` 渐进、先补关键模块类型、`strict` 分项开启、`@ts-expect-error`（优于 `@ts-ignore`：多余时会报错，防注释腐化）；
- 性能：`skipLibCheck`、项目引用（project references）拆分大仓、避免过度复杂的条件类型递归（类型体操会拖垮编译速度，见 [[1.03 泛型与类型编程]]）。

## 面试问答

### Q: namespace 和 module 的区别？现在还用 namespace 吗？

满分答案：namespace 编译成 IIFE 包裹的全局对象，是 ESM 出现前的组织方式——依赖隐式、污染全局、无法 Tree Shaking，typescript-eslint 默认禁用；ES Module 以文件为模块单元、依赖显式、可静态分析。判定规则：文件含顶级 import/export 即为模块，否则声明是全局的。namespace 现在只保留在 .d.ts 中描述全局 UMD 库或 declare global 扩展全局类型的场景。

### Q: tsconfig 里你最关注哪些配置？

满分答案：strict 必开（其中 strictNullChecks 是防空值崩溃的核心）；target/module/moduleResolution 决定语法降级与模块解析，用打包器时 moduleResolution 选 Bundler、module 保持 ESNext 以保留动态 import 的分包能力；isolatedModules 配合 Babel/esbuild 单文件转译，要求类型导出用 export type 显式标注；skipLibCheck 提速；现代工程 noEmit 把转译交给 esbuild/Vite、类型检查交给 tsc --noEmit 在 CI 跑。

### Q: TS 能保证运行时安全吗？接口数据怎么处理？

满分答案：不能——TS 类型在编译后完全擦除，运行时零校验；接口返回与声明不符时，类型注解只是「一厢情愿」。正确做法：边界处用 unknown 接收，再用 zod、valibot 这类运行时校验库解析（校验通过后自动获得类型），失败进入错误处理。类型系统负责内部一致性，边界安全必须由运行时校验补上——这是「类型安全」认知深度的分水岭。

### Q: 项目里 TS 编译很慢怎么优化？

满分答案：先分离职责——转译交给 esbuild/swc（Vite 默认），tsc 只做 noEmit 类型检查并在 CI/编辑器异步跑；配置层面开 skipLibCheck 跳过依赖声明检查、用 incremental 增量编译、大仓用 project references 拆分；代码层面避免深度递归的条件类型与超大联合（类型体操是编译耗时的常见元凶），必要时用 tsc --generateTrace 定位慢在哪个类型。
