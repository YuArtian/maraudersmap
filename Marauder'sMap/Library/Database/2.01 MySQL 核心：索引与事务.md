# MySQL 核心：索引与事务

## TL;DR

**索引 = B+ 树：非叶节点只存键、叶子存数据且串成链表——三层树扛千万行，范围查询沿链扫**。用索引的三大军规：最左前缀、别在索引列上做计算、覆盖索引免回表。**事务 ACID 中隔离性靠四级隔离实现，InnoDB 默认可重复读（MVCC 实现，快照读不加锁）**。深分页优化：游标法或延迟关联。

---

## 1. 索引：为什么是 B+ 树

对比答题法：哈希表——等值快但**不支持范围/排序**；二叉/红黑树——行数一多**树太高**（每层一次磁盘 IO）；**B+ 树**——多叉矮胖（一个节点一页 16KB，能放几百个键），千万行三层搞定；**数据全在叶子层且叶子间有双向链表**——范围查询、排序沿链顺序扫，非叶层纯索引更小更缓存友好。

索引分类速查：

| 维度 | 类型 |
|---|---|
| 约束 | 主键（唯一非空，一表一个）、唯一（可 NULL）、普通、全文 |
| 结构 | **聚簇索引**：主键树，叶子存整行——「表就是主键索引」；**二级索引**：叶子存主键值，查完要**回表**（拿主键再查聚簇树） |
| 列数 | 单列、联合索引（最左前缀原则的主场） |

三条军规展开：

- **最左前缀**：联合索引 (a,b,c) 能服务 a / a,b / a,b,c 与 a 的范围；跳过 a 直接查 b 用不上——树是先按 a 排、a 相同再按 b 排的，没有 a 的定位 b 无序；
- **索引列不做计算**：`WHERE YEAR(created) = 2024`、隐式类型转换（字符串列传数字）都会让索引失效——改写成范围条件；
- **覆盖索引**：查询的列全在二级索引里就**免回表**（EXPLAIN 的 Using index）——`SELECT id, name` 配 (name) 索引即是；这也是「不要 SELECT *」的性能论据。

EXPLAIN 三件事：type（const/ref/range 好，index/ALL 差）、key（用了哪个索引）、rows（预估扫描行数）——「怎么排查慢查询」的答案是慢日志定位 + EXPLAIN 分析 + 建/改索引。

## 2. 事务：ACID 与隔离级别

ACID 一句一个：原子性（要么全做要么全不做，undo log 回滚）、一致性（约束不被破坏，是其余三者的目标）、隔离性（并发事务互不干扰）、持久性（提交即落盘，redo log 保证）。

**四级隔离与并发异常**（矩阵必背）：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 | ✗有 | ✗ | ✗ |
| 读已提交（RC，Oracle 默认） | ✓无 | ✗ | ✗ |
| **可重复读（RR，InnoDB 默认）** | ✓ | ✓ | 基本解决* |
| 串行化 | ✓ | ✓ | ✓ |

三个异常的一句话：脏读=读到别人**未提交**的数据；不可重复读=同一事务内两次读**同一行**值变了（别人提交了 update）；幻读=两次**范围查询**行数变了（别人提交了 insert）。

**MVCC**（RR 为什么性能还行）：每行带隐藏的事务版本号，undo log 保留旧版本链；事务开启时建立**读视图（快照）**，普通 SELECT 读快照**不加锁**——读写不阻塞。*InnoDB 在 RR 下用「MVCC 快照读 + 间隙锁（Next-Key Lock）锁住范围」把幻读基本消灭——这是超出教科书矩阵的加分点。

## 3. 深分页优化（高频实战题）

`LIMIT 1000000, 20` 慢的原因：**扫描并丢弃前一百万行**（还可能各回一次表）。两个解法：

```sql
-- ① 游标/键集分页（最优，要求有序唯一键，适合无限滚动）
SELECT * FROM t WHERE id > #{last_id} ORDER BY id LIMIT 20;

-- ② 延迟关联（跳页场景）：先在索引里翻页拿 id，再回表取整行
SELECT t.* FROM t
JOIN (SELECT id FROM t ORDER BY id LIMIT 1000000, 20) tmp ON t.id = tmp.id;
```

①把「跳过一百万行」变成「索引定位」；②让翻页发生在覆盖索引内，只对最终 20 行回表。

## 面试问答

### Q: MySQL 索引为什么用 B+ 树而不是哈希或红黑树？

满分答案：哈希只支持等值、无法范围与排序；二叉系树高随数据量增长，每层一次磁盘 IO 不可接受。B+ 树多叉矮胖（节点即数据页，容纳数百键），千万级三层即达；数据全部下沉叶子且叶子链表相连——范围与排序沿链顺扫，非叶层只存键更利缓存。再补聚簇与二级索引的分工：主键树存整行，二级索引存主键、需要回表，覆盖索引可免。

### Q: 事务隔离级别有哪些？InnoDB 默认是什么、怎么实现的？

满分答案：读未提交、读已提交、可重复读、串行化，分别递进解决脏读、不可重复读、幻读。InnoDB 默认可重复读，靠 MVCC——行带版本号、undo log 存版本链、事务首次读建立快照，普通 SELECT 走快照读不加锁，读写互不阻塞；配合 Next-Key（记录+间隙）锁，当前读下的幻读也基本消除。选型补充：互联网业务常调成 RC 减少间隙锁死锁。

### Q: LIMIT 一百万后很慢，怎么优化分页？

满分答案：慢因是引擎要扫过并丢弃 offset 之前的所有行。首选键集分页——记录上页末尾 id，用 WHERE id > last ORDER BY id LIMIT n，索引直接定位，复杂度与页深无关，适合信息流；需要跳页时用延迟关联——子查询在覆盖索引里完成翻页只取 id，外层再回表拿 20 行整行。顺带说明业务层配合：限制最大页深、totals 用估算。

### Q: 哪些写法会让索引失效？

满分答案：违反最左前缀（联合索引跳过首列）；索引列参与函数或运算（YEAR(col)、col+1）；隐式类型转换（字符串列与数字比较）；前导通配 LIKE '%xx'；OR 连接非索引列；范围条件后的联合索引列失效。验证手段统一是 EXPLAIN 看 type 和 key，慢查询日志定位问题 SQL。
