# 高频场景题集

## TL;DR

**方案设计类小题打包**：大数组高效查找（按结构选算法）、新版本上线通知用户刷新（轮询版本号/构建指纹）、通用组件与 SDK 设计原则（插件化的 useRequest 范式）、低代码平台核心机制、SSE 流式渲染。这类题考的是**权衡叙述能力**，不是唯一正确答案。

---

## 1. 大数组里高效查找

按「数据结构 × 查找频率」选择：

| 场景 | 方案 | 复杂度 |
|---|---|---|
| 小数组 / 一次性查找 | `find`/循环 | O(n) |
| **频繁按唯一键查** | 预建 `Map<id, item>` 索引 | 建 O(n)，查 **O(1)** |
| 已排序数组 | 二分查找 | O(log n) |
| 前缀/模糊搜索 | 排序 + 二分定界，或 Trie；量大上后端/搜索引擎 | — |

答题要点是「问清前提再选型」：查几次？有没有唯一键？有序吗？数据多大（几百条其实怎么都快，量级到十万才谈优化）？——**反问前提**本身就是分数。超大数据的兜底：Web Worker 里建索引防阻塞（见 [[2.04 并发控制与耗时任务优化]]）。

## 2. 上线新版本，如何通知用户刷新

问题本质：SPA 用户长驻页面，旧 JS 里跑着旧逻辑调新接口，可能出错。方案分层：

1. **地基**：index.html 走协商缓存/不缓存（见 [[1.04 HTTP 缓存策略]]）——用户刷新必得新版本；
2. **检测**：构建时注入版本号（`window.__APP_VERSION__` 或 meta 标签）→ 前端**轮询**请求 HTML/version.json 对比版本（或对比 script hash）；也可 WebSocket/SSE 推送发版事件（见 [[1.09 WebSocket 与实时通信]]）；
3. **触达**：检测到新版本弹「发现新版本，点击刷新」条——**让用户选择时机**，别在表单填一半时强刷；路由跳转时静默 `location.reload()` 是低打扰时点；
4. **兜底**：接口层带版本头，后端识别过旧版本返回特定错误码，前端统一拦截提示刷新（协议兜底，防轮询失效）。

加分对比：monorepo/微前端下子应用独立发版的通知粒度；Service Worker 场景的 skipWaiting 更新流。

## 3. 通用组件 / SDK 设计原则（讲设计的题）

拿 useRequest 的插件化架构当例子讲五条（架构详见 [[2.06 自定义 Hook 实战]]）：

- **单一职责**：内核只管核心流程（请求三态），能力拆成插件；
- **插件化 + 生命周期钩子**：内核暴露 onBefore/onSuccess/onError 等钩子，插件按需挂载——扩展不改内核（开闭原则），通知机制用观察者模式（见 [[3.04 发布订阅与观察者模式]]）；
- **接口隔离与稳定**：对外 API 面积最小化、内部重构不破坏外部；
- **参数归一化**：多种入参形态（字符串/对象/函数）在入口统一成标准形状再进内核——DX 友好而内核简单；
- 配套工程：类型完备、零副作用可摇（sideEffects，见 [[2.03 Tree Shaking 与按需引入]]）、文档与 demo、semver 承诺（见 [[1.02 package.json 与依赖管理]]）。

## 4. 低代码平台核心机制（概览级）

面试讲四个机制点即可：**物料与 DSL**——组件注册全局配置，页面是「组件树 + 属性」的 JSON Schema；**渲染器**——运行时把 DSL 递归渲染成组件（编辑态包一层 wrapper 负责选中/拖拽/z-index）；**事件与动画的声明化**——预定义事件函数映射名，配置里存事件名列表，wrapper 上统一绑定、仅预览/发布态触发；动画存类名数组，运行时逐个加 animated 类并监听 animationend 移除（Promise 串行）；**编辑器交互**——拖拽定位、旋转（Math.atan2 算弧度差）、吸附对齐线，辅助能力如 PSD 导入解析成 DSL、dom-to-image 生成缩略图。收尾说边界：低代码适合模式化页面（活动页、表单报表），复杂交互逻辑仍需代码逃生舱。

## 5. SSE 流式渲染（AI 时代新宠）

机制回顾（详见 [[1.09 WebSocket 与实时通信]]）：`text/event-stream` 长连 HTTP，服务器持续推 `data:` 块。前端消费两条路：EventSource（自动重连但只支持 GET）；**fetch + ReadableStream 手动读流**（POST/自定义头场景，AI 对话标配，见 [[1.10 fetch 与 XHR]]）：

```js
const res = await fetch('/chat', { method: 'POST', body });
const reader = res.body.getReader();
const decoder = new TextDecoder();
while (true) {
  const { done, value } = await reader.read();
  if (done) break;
  appendToUI(decoder.decode(value, { stream: true }));   // 打字机效果
}
```

配套细节：分块渲染节流（rAF 批量上屏）、中断用 AbortController、断线重连与续传标记。

## 面试问答

### Q: 几十万条数据的列表，前端怎么做搜索？

满分答案：先反问前提——数据能否分页留在后端（首选：搜索本就该服务端做）；必须前端时：唯一键查找预建 Map 索引 O(1)；有序字段用二分；模糊搜索考虑 Trie 或分词倒排，构建索引放 Web Worker 防阻塞主线程；渲染侧配虚拟列表。体现「量级判断 + 前后端分工 + 结构选型」三层思考。

### Q: 发新版后用户停留在旧页面，怎么让他们用上新版本？

满分答案：四层——缓存地基：HTML 不缓存保证刷新即新；检测：构建注入版本号，前端轮询 version.json 或 HTML 指纹对比，也可推送通道广播发版；触达：非强制的更新提示条，用户空闲或路由切换时机刷新，避免打断操作；协议兜底：请求带版本标识，后端对过旧版本返回专用错误码统一引导刷新。有 Service Worker 的场景再谈 waiting worker 的 skipWaiting 流程。

### Q: 让你设计一个给多团队用的 SDK，你会考虑什么？

满分答案：架构上内核 + 插件——内核只做最小核心流程并暴露生命周期钩子，能力以插件挂载，扩展不动内核；API 设计上参数归一化、接口面积最小、语义化版本承诺；工程上 TS 类型、ESM 产物可 tree shaking、sideEffects 声明、双格式发布；质量上单测、文档 demo、错误边界与降级、埋点可观测。举 useRequest 插件化为原型案例，展示「原则落到结构」的能力。
