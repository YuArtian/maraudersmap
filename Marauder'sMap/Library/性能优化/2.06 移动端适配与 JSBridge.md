# 移动端适配与 JSBridge

## TL;DR

**适配方案演进：flexible 的 rem 动态根字号（已弃用）→ vw 视口单位 + postcss 转换（现役主流）**。**JSBridge 双向通信：JS 调 Native 靠「注入 API」（现代 WebView 标准做法）或 URL 拦截（老方案）；Native 调 JS 靠 evaluateJavascript 触发挂在 window 的事件中心——两个方向都是发布订阅 + callbackId 的回调管理**。

---

## 1. 移动端布局适配的演进

**flexible/rem 时代**（理解原理，注明已弃用）：设计稿 750px 映射 10rem（1rem = 75px），脚本按视口宽动态设 html 的 font-size，rem 随屏等比缩放；对高倍屏再用 initial-scale=1/dpr 整体缩放解决 1px 问题。缺点：依赖运行时 JS、字体缩放副作用、与第三方组件库的 px 混用冲突（rem 机制见 [[1.01 盒模型与 box-sizing]]，构建期 px 转换见 [[2.07 Babel 与编译体系]]）。

**vw 时代（现役答案）**：100vw 恒等于视口宽——750 设计稿下 1vw = 7.5px，纯 CSS 无 JS 依赖：

```text
构建链：写 px → postcss-px-to-viewport 转 vw
宽高比：aspect-ratio 原生属性（老方案 padding 百分比盒）
1px 问题：transform: scaleY(0.5) 或 border-image / 0.5px（DPR≥2 已普遍支持）
上限保护：大屏用 clamp() 或 max-width 容器限制过度放大
```

配套知识点：**1px 问题的本质**是 DPR——CSS 1px 在二倍屏渲染成 2 物理像素显粗；**安全区适配**见 [[1.10 CSS 细节题集]] 的 env(safe-area-inset)。收尾一句：媒体查询 + 弹性布局（flex/grid）负责结构自适应，vw/rem 负责等比还原，两者配合而非二选一。

## 2. JSBridge：H5 与 Native 的双向通道

**JS → Native 三代方式**：

| 方式 | 机制 | 现状 |
|---|---|---|
| URL 拦截（假跳转） | location.href / 隐藏 iframe 发自定义协议 `myapp://action?param`，Native 拦截解析 | 老方案：URL 长度受限、连续跳转被 WebView 合并（要消息队列缓冲）——知道即可 |
| **注入 API（现役）** | Android `addJavascriptInterface` 注入 window.NativeApi；iOS WKWebView 的 `window.webkit.messageHandlers.x.postMessage()` | 标准做法，Bridge 层封装抹平双端差异 |
| 弹窗拦截 | 劫持 alert/prompt 传参 | 基本淘汰 |

**Native → JS**：Native 执行 `evaluateJavascript`，调用 H5 预先挂在 window 上的入口函数/事件中心。

**回调管理（Bridge 封装的核心，手写考点）**：原生调用是异步的，靠 **callbackId + 发布订阅**闭环：

```js
// H5 侧 Bridge 骨架
const callbacks = new Map();
let id = 0;

function callNative(method, params) {
  return new Promise((resolve, reject) => {
    const callbackId = `cb_${++id}`;
    callbacks.set(callbackId, { resolve, reject });     // 注册回调
    postToNative({ method, params, callbackId });       // 注入 API 发消息
  });
}
// Native 完成后 evaluateJavascript 调它，带回 callbackId
window.__onNativeCallback = (callbackId, error, data) => {
  const cb = callbacks.get(callbackId);
  error ? cb.reject(error) : cb.resolve(data);
  callbacks.delete(callbackId);
};
// Native 主动推送：约定事件名的发布订阅（见 3.04 发布订阅与观察者模式）
window.__onNativeEvent = (event, data) => eventBus.emit(event, data);
```

判分点：**callbackId 关联请求与响应**（多次并发调用不串台）、**Promise 化**对业务暴露现代接口、**双端差异封装在发送层**、Native 主动消息走事件订阅。整套就是「跨线程/跨端 RPC」的通用模式——与 postMessage 跨窗口通信、WebSocket 消息信封（见 [[1.09 WebSocket 与实时通信]]）同构。

## 面试问答

### Q: 移动端适配方案有哪些？现在推荐哪种？

满分答案：讲演进——早期媒体查询断点适配；flexible 方案用 JS 按视口动态设根字号、rem 等比还原设计稿，曾是主流但依赖运行时脚本且已官方弃用；现役是 vw 方案：750 稿下 1vw=7.5px，postcss-px-to-viewport 构建期转换，零 JS，配 aspect-ratio 控宽高比、clamp 限大屏。附带答 1px 问题（DPR 导致，scaleY(0.5)/0.5px 解决）与刘海屏安全区（viewport-fit=cover + env()）。结构自适应交给 flex/grid + 媒体查询，等比还原交给 vw，两层配合。

### Q: JSBridge 的原理？怎么实现双向通信？

满分答案：JS 调 Native——现代标准是注入 API：Android addJavascriptInterface、iOS WKWebView 的 messageHandlers.postMessage，Bridge 层封装双端差异；老方案 URL 拦截（自定义协议假跳转）有长度限制和连跳合并问题。Native 调 JS——evaluateJavascript 执行 H5 挂在 window 的入口。核心封装是回调管理：每次调用生成 callbackId 注册进回调表并随消息传给 Native，Native 完成后带 id 回调，H5 侧 resolve 对应 Promise；Native 主动推送则走约定事件名的发布订阅。本质是一套跨端 RPC + 消息信封设计。

### Q: 为什么 URL 拦截方案会丢消息？怎么解决？

满分答案：WebView 对连续的跳转请求有合并/过滤策略，短时间多次改 location.href 只有最后一次生效；且 URL 有长度上限，大参数被截断。老方案的补救：消息队列缓冲 + 定时批量发送（Native 收到信号后主动来取队列），或用隐藏 iframe 每条消息独立触发。根治是换注入 API 通道——这题价值在展示对「通道可靠性」的工程思考。
