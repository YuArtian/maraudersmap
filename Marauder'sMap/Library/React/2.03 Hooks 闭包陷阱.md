# Hooks 闭包陷阱

## TL;DR

**闭包陷阱 = 回调里用的是「过去某次渲染」捕获的旧 state**。根源是函数组件的值捕获语义（每次渲染一份快照）+ 依赖数组没把用到的值列全。四种解法按优先级：函数式更新 > 补全依赖 > useRef 存最新值 > useEffectEvent（实验性）。

> 前置知识：闭包机制见 [[1.03 执行上下文、调用栈与闭包]]，值捕获语义见 [[2.01 Hooks 原理与规则]]。

---

## 1. 经典病例：每秒 +1 的计时器

```jsx
function Counter() {
  const [count, setCount] = useState(0);
  useEffect(() => {
    const id = setInterval(() => {
      setCount(count + 1);      // 🔴 永远是 0 + 1：闭包捕获了首帧的 count
    }, 1000);
    return () => clearInterval(id);
  }, []);                        // 🔴 依赖为空 → effect 只跑一次 → 回调永远是「第一帧的函数」
  return <div>{count}</div>;
}
// 页面显示 1 之后不再变化
```

发生了什么：effect 只在挂载时执行一次，`setInterval` 的回调是**第一次渲染时创建的函数**，闭包里的 `count` 永远是 0。之后每秒执行 `setCount(0 + 1)`——值相同，界面卡在 1。

同型题：事件监听里读 state 总是旧值、防抖回调拿到过期表单、`console.log` 在 setTimeout 里输出「上一个」状态——全是同一个病。

## 2. 解法族（按推荐顺序）

**① 函数式更新（首选，能用就用）**：

```jsx
setInterval(() => setCount(c => c + 1), 1000);   // c 由 React 从队列取最新值，不依赖闭包
```

适用条件：新状态只由旧状态算出。它从根本上绕开快照——更新函数在 render 阶段消费队列时才求值（机制见 [[1.04 setState 与批量更新]]）。

**② 补全依赖，配合清理**：

```jsx
useEffect(() => {
  const id = setInterval(() => setCount(count + 1), 1000);
  return () => clearInterval(id);
}, [count]);        // count 变 → 清旧定时器 → 用新快照重建
```

正确但有代价：每秒销毁重建定时器。原则：**依赖该列就列**（exhaustive-deps 不是敌人），觉得重建太贵再考虑下面的手段，而不是删依赖。

**③ useRef 存「永远最新」的值**：

```jsx
const countRef = useRef(count);
countRef.current = count;                    // 每次渲染同步最新值
useEffect(() => {
  const id = setInterval(() => {
    console.log(countRef.current);           // 读 ref，永远最新
  }, 1000);
  return () => clearInterval(id);
}, []);
```

ref 是跨渲染的同一个盒子（见 [[2.05 Ref 体系]]），不参与快照。适合「长寿回调要读最新状态」：订阅、全局监听、第三方库回调。常封装成 `useLatest`：

```js
function useLatest(value) {
  const ref = useRef(value);
  ref.current = value;
  return ref;
}
```

**④ useEffectEvent（React 实验性 API）**：把「读最新值但不作为依赖」的逻辑声明为 effect event——官方给这个问题的正名方案，截至 React 19 仍是实验特性，面试提到名字和动机即可。

## 3. useCallback/useMemo 里的同款陷阱

```jsx
const handler = useCallback(() => {
  submit(form);        // 🔴 deps 里没有 form → handler 永远用旧 form
}, []);
```

useCallback/useMemo 的缓存同样按 deps 决定「要不要换新函数」——**漏依赖 = 主动索要过期闭包**。lint 规则 react-hooks/exhaustive-deps 检查的就是这件事：该修依赖或改用 ref/函数式更新，**不要注释掉规则**。

面试完整叙事：「hook 状态存在 fiber 链表上（[[2.01 Hooks 原理与规则]]），deps 浅比较决定是否采用新传入的函数；不列依赖 → React 沿用旧函数 → 旧函数闭包里是旧快照」——原因、机制、解法三段齐了。

## 面试问答

### Q: 什么是 Hooks 的闭包陷阱？为什么会发生？

满分答案：回调函数读到的是创建它那次渲染的 state 快照而非最新值。三个成因叠加：函数组件每次渲染是独立调用、props/state 被闭包按值捕获；useEffect/useCallback 等靠 deps 浅比较决定是否更新传入的函数；依赖没列全时 React 继续持有旧函数，旧函数连着旧快照。典型症状：定时器里 count 恒为初值、事件回调拿到过期表单。

### Q: 解决闭包陷阱有哪些手段？怎么选？

满分答案：按序——新状态源于旧状态时用函数式更新 setX(v => …)，最干净；否则补全依赖数组并在清理函数里撤销旧副作用（重建成本可接受时的正解）；长寿回调需要「读最新」时用 useRef 桥接（useLatest 模式），ref 不参与快照；官方的长期答案是实验性的 useEffectEvent。红线：不要用删依赖/关 lint 的方式「解决」。

### Q: 写一个正确的 React 计时器？

满分答案：useEffect 空依赖建立 setInterval，回调用函数式更新 setCount(c => c + 1)，返回清理函数 clearInterval；如果还要暂停/重置，把 interval id 或运行态放 ref/state 里控制。判分点：函数式更新避开闭包、清理函数防泄漏与重复计时、（追问时）说明为何不能直接 setCount(count + 1)。

### Q: useCallback 的依赖数组漏写会怎样？

满分答案：React 会一直返回缓存的旧函数，其闭包捕获的旧 state/props 造成「提交过期数据」类 bug——比显式 bug 更隐蔽，因为函数身份稳定了、memo 的子组件也不再更新。exhaustive-deps 规则就是防它的：依赖如实声明，函数身份确需稳定时用 ref 桥接可变部分，而不是撒谎式的空数组。
