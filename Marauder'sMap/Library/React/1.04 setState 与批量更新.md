# setState 与批量更新

## TL;DR

**setState 本身是同步调用，但状态的应用和重渲染是异步批处理的——「本次渲染里读不到新值」**。React 17 只在事件回调/生命周期里批处理（setTimeout 里逐次同步刷新是著名例外）；**React 18 的 createRoot 起按优先级自动批处理，任何上下文都合并**，需要立即刷新用 flushSync。

---

## 1. 「异步」的准确表述

```js
const [count, setCount] = useState(0);

function handleClick() {
  setCount(count + 1);
  console.log(count);   // 还是 0 —— 本次闭包里的快照不会变
}
```

严谨说法：setState/setXxx **不是宏微任务意义上的异步**，而是「**更新入队 + 延迟到本轮批次统一处理**」。当前作用域里的 state 是本次渲染的**快照**（函数组件靠闭包，类组件靠 this.state 未被立即改写），所以调用后立刻读不到新值。

**连续多次 setState 的合并规则**：

```js
setCount(count + 1); setCount(count + 1);  // 只 +1：两次都基于同一快照 0
setCount(c => c + 1); setCount(c => c + 1); // +2：函数式更新依次消费队列
```

面试判分点：**依赖前值必须用函数式更新**。类组件同理：对象式 setState 浅合并（Object.assign 语义，后者覆盖前者），函数式 `setState((state) => …)` 串行计算。

---

## 2. 批处理的版本差异（必考对比）

| | React 17（legacy） | React 18+（createRoot） |
|---|---|---|
| 事件回调、生命周期 | ✅ 批处理 | ✅ |
| setTimeout / Promise.then / 原生事件监听 | ❌ **每次 setState 同步渲染一次** | ✅ 自动批处理 |
| 实现依据 | 全局标志 isBatchingUpdates：进入事件回调置 true（try/finally 收尾统一 flush），异步回调执行时早已复位 | 不看执行上下文，**看更新优先级（lane）**：同优先级更新只调度一次，在微任务里统一处理 |
| 手动逃生 | unstable_batchedUpdates 手动开批 | `flushSync(() => setX(...))` 强制同步刷新 |

React 17 的经典输出题（setTimeout 里连续两次 setState 触发两次 render）在 18 的 createRoot 下不再成立——**回答时必须带版本前提**，这是最能体现知识新旧的地方。

flushSync 的正当用途很少：需要在下一行同步读取更新后的 DOM（如设置滚动位置）时才用，滥用会退化性能。

---

## 3. 调用 setState 后发生了什么（流程串讲）

1. 创建 update 对象（携带新值/更新函数与优先级 lane），挂到该 fiber 的更新队列；
2. 调度：Scheduler 按优先级安排一次渲染（同批次同优先级的更新合并，只调度一次）；
3. render 阶段：从根开始构建 workInProgress 树，执行组件函数/render 方法——**队列里的更新在此刻依次计算出新 state**；diff 打标记（见 [[1.02 Fiber 架构]]、[[1.03 Diff 算法与 key]]）；
4. commit 阶段：应用 DOM 变更，跑 effect。

**「setState 了但值没变，会重新 render 吗？」**——会。类组件默认 shouldComponentUpdate 返回 true，函数组件同样重新执行（`Object.is` 相等的 useState 更新会提前 bail out，但类组件的对象合并总是产生新引用）。不过 render ≠ 改 DOM：diff 发现无差异就不会有真实 DOM 操作。想跳过 render 本身：PureComponent / React.memo / useMemo（见 [[2.04 记忆化：memo、useMemo 与 useCallback]]）。

---

## 4. 类组件补充：哪些生命周期能 setState

- ✅ componentDidMount、componentDidUpdate（**必须有条件**，否则死循环）、事件回调；
- ❌ render 里调用 → 死循环；
- ❌ componentWillUnmount 里调用 → 无意义（不会再渲染）；
- shouldComponentUpdate / getDerivedStateFromProps 里不应触发新更新。

## 面试问答

### Q: setState 是同步还是异步的？

满分答案：分层回答——调用本身同步，但状态应用与重渲染是批处理的，当前代码里读到的仍是本次渲染的快照，所以表现为「异步」。版本差异是关键：React 17 只在事件回调和生命周期里批处理（靠 isBatchingUpdates 标志），setTimeout/Promise/原生事件里每次 setState 都同步渲染；React 18 的 createRoot 改为按更新优先级自动批处理，所有上下文统一合并，需要立即拿到渲染结果用 flushSync。补充：连续更新依赖前值要用函数式写法，否则多次调用消费的是同一快照。

### Q: 调用 setState 之后发生了什么？

满分答案：四步——创建带优先级的 update 入队到对应 fiber；调度器按优先级安排渲染（同优先级合并只调度一次）；render 阶段执行组件计算新 state、构建新 fiber 树并 diff 打标记，此阶段可中断；commit 阶段同步应用 DOM 变更并执行 effect。强调 state 的真正计算发生在 render 阶段消费更新队列时，而非调用那一刻。

### Q: setState 传相同的值会重新渲染吗？

满分答案：类组件会——默认 shouldComponentUpdate 恒 true，且对象式合并总产生新 state 引用；可用 PureComponent 浅比较拦截。函数组件的 useState 若新值与旧值 Object.is 相等会 bail out 跳过（个别边界下仍可能执行一次函数体但不 commit）。同时纠正概念：重新 render 不等于操作 DOM，diff 无差异时真实 DOM 零变更，代价只是执行函数与对比。

### Q: React 18 的自动批处理和 17 有什么本质区别？

满分答案：17 判断「现在处于 React 管理的执行上下文吗」（全局标志），出了事件回调就失效；18 改为以更新的 lane 优先级为分组依据，任何来源的同优先级更新都在微任务时机合并成一次渲染——机制从「上下文驱动」变为「调度驱动」，这也是并发渲染体系（见 [[1.05 并发特性与优先级调度]]）的一部分。逃生舱从 unstable_batchedUpdates（手动开批）反转为 flushSync（手动关批）。
