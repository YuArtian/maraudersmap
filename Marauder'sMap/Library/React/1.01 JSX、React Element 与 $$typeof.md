# JSX、React Element 与 $$typeof

## TL;DR

**JSX 是创建 React Element（描述对象）的语法糖：React 17 前编译成 `React.createElement`（所以必须 import React），17 起编译成自动引入的 `jsx-runtime` 函数（不用再 import）**。Element 上的 `$$typeof: Symbol.for('react.element')` 是防注入的身份戳——JSON 里带不了 Symbol，伪造的「元素」过不了这道门。

> 「Element 只是描述、父先子后执行、render/commit 两阶段」的机制全景见 [[React 渲染机制]]；与 Vue 的范式对比见 [[React vs Vue 渲染对比]]。

---

## 1. JSX 编译成什么

```jsx
const el = <div className="box">hi</div>;

// React 17 之前（classic runtime）：
const el = React.createElement('div', { className: 'box' }, 'hi');
// ← 编译产物用到 React 标识符，所以每个 JSX 文件都必须 import React

// React 17+（automatic runtime）：
import { jsx as _jsx } from 'react/jsx-runtime';   // 编译器自动插入
const el = _jsx('div', { className: 'box', children: 'hi' });
// ← 不再需要手动 import React
```

新转换（automatic runtime）的启用：`@babel/preset-react` 或 TS 配置 `runtime: 'automatic'`（现代脚手架默认），同时可以关掉 `react-in-jsx-scope` 这类旧 ESLint 规则。改进点：免 import、children 进 props 传参更规范、为未来优化留了口子。

面试连环问的答案链：**「为什么以前必须引入 React」→ 因为编译产物是 React.createElement；「为什么现在不用了」→ 因为 17 起编译目标换成了独立的 jsx-runtime 模块，由编译器自动引入。**

## 2. React Element：一个纯描述对象

```js
console.log(<App color="blue" />);
// {
//   $$typeof: Symbol.for('react.element'),  // React 19 起改为 Symbol.for('react.transitional.element')
//   type: App,          // 字符串（宿主元素）或 函数/类（组件）
//   key: null,
//   ref: null,
//   props: { color: 'blue' },
// }
```

三个认知（高频误区）：

1. **写 `<App />` 不会调用 App**——只是造了个 `{ type: App }` 的对象，什么时候调用、要不要调用由 React 调度决定；
2. Element 是**不可变的**，每次渲染重新创建，它是「这一刻 UI 应该长什么样」的快照；
3. 「虚拟 DOM」的价值口径：不是「比真实 DOM 快」，而是**在数据驱动的声明式模型下，用可接受的成本自动算出最小 DOM 操作**（diff + 批处理），同时解耦渲染目标（DOM、Native、Canvas 都能当宿主）。

## 3. $$typeof：防 XSS 注入的身份戳

场景：服务端把用户输入存进数据库，前端 `{message}` 渲染。若用户存的是一个「长得像 React Element 的 JSON」：

```json
{ "type": "div", "props": { "dangerouslySetInnerHTML": { "__html": "<script>…</script>" } } }
```

没有防护的话它会被当成元素渲染，注入就成功了。React 的对策：**创建元素时打上 `$$typeof: Symbol.for('react.element')`，渲染前校验**——而 **JSON 无法序列化 Symbol**，从接口/数据库来的伪造对象必然缺这个戳，直接被拒绝渲染。

两个细节：`Symbol.for` 用全局注册表，保证多个 React 副本间一致；不支持 Symbol 的远古环境退化为魔数 `0xeac7`（此时防护失效，这是历史包袱）。

---

## 4. 顺手记牢的编译小识

- JSX 里 `false/null/undefined` 不渲染，`0` **会渲染**——`{list.length && <List/>}` 的经典 0 bug，改用 `list.length > 0 &&` 或三元；
- 组件名必须大写：编译器按首字母大小写决定 `type` 是字符串（'div'）还是标识符（App）；
- `<></>` Fragment 编译为 `jsx(Fragment, …)`，不产生真实节点；
- props 展开 `{...obj}` 就是对象展开，后写的覆盖先写的。

## 面试问答

### Q: JSX 的本质是什么？为什么以前必须 import React，现在不用了？

满分答案：JSX 是创建 React Element 描述对象的语法糖，本身不是模板语言，编译期由 Babel/TS 转换。React 17 前转换目标是 React.createElement，产物引用 React 标识符，所以每个 JSX 文件必须 import React；17 起换成 automatic runtime，编译器自动从 react/jsx-runtime 引入 _jsx 函数，无需手动导入。配置上是 preset 的 runtime: 'automatic'，现代脚手架已默认。

### Q: $$typeof 是干什么的？为什么用 Symbol？

满分答案：React Element 的身份标记，值为 Symbol.for('react.element')，渲染前校验它以拒绝伪造元素。威胁模型是「服务端返回的 JSON 被当作元素渲染」实现注入（比如带 dangerouslySetInnerHTML 的假元素）；因为 JSON 不能承载 Symbol，来自网络/存储的数据必然没有合法的 $$typeof，从而被拦截。Symbol.for 走全局注册表，跨 React 实例一致。

### Q: 谈谈你对虚拟 DOM 的理解？它一定比直接操作 DOM 快吗？

满分答案：虚拟 DOM 是描述 UI 的 JS 对象树，配合 diff 与批量提交，把声明式「重新渲染整个视图」的心智模型转换成最小化的真实 DOM 操作。不比精心手写的命令式操作快——它的价值是在「自动化、通用化」的前提下把成本压到可接受，换来开发效率、可预测性和跨端能力（DOM/Native 渲染器共用协调层）。回答要点是把「性能」修正为「工程权衡」。

### Q: 写 `<Child />` 时发生了什么？Child 函数执行了吗？

满分答案：没执行——只是创建了 { type: Child, props } 的 Element 对象。真正调用 Child 发生在 React 的 render 阶段，由调度器决定时机（可能因优先级推迟，甚至被 memo 跳过）。这也是父组件函数先 return、子组件函数后执行的原因；机制细节在渲染流程与 Fiber 的话题里展开（见 [[1.02 Fiber 架构]]）。
