# 生命周期与类组件遗产

## TL;DR

**React 16 废掉三个 componentWill\*（因为 Fiber 的 render 阶段可重复执行，它们不再可靠），补上两个静态方法 getDerivedStateFromProps 与 getSnapshotBeforeUpdate**。挂载：constructor → getDerivedStateFromProps → render → componentDidMount。类组件的 this 绑定与 super(props) 属于「遗产题」，但仍常被问。

---

## 1. 现行生命周期（16.3+）

```mermaid
flowchart TD
    subgraph 挂载
        A[constructor] --> B["static getDerivedStateFromProps"] --> C[render] --> D[componentDidMount]
    end
    subgraph 更新（props/state 变化）
        E["static getDerivedStateFromProps"] --> F[shouldComponentUpdate] --> G[render] --> H[getSnapshotBeforeUpdate] --> I[componentDidUpdate]
    end
    subgraph 卸载
        J[componentWillUnmount]
    end
```

对齐 Fiber 两阶段（见 [[1.02 Fiber 架构]]）：render 阶段的钩子（constructor、getDerivedStateFromProps、shouldComponentUpdate、render）**必须纯净、可能执行多次**；commit 阶段的钩子（getSnapshotBeforeUpdate、componentDidMount/Update/Unmount）只跑一次、可以做副作用。

**为什么废弃 componentWillMount / WillReceiveProps / WillUpdate**：它们属于 render 阶段，Fiber 下这一阶段可被打断重跑——「Will」系钩子里的副作用（请求、订阅）会重复执行；且开发者常在里面写等价于 setState 的同步逻辑引发混乱。替代品全是**静态方法或带快照的受限接口**，故意让你写不了副作用：

- `getDerivedStateFromProps(props, state)`：静态、拿不到 this，只能返回新 state（或 null）——「从 props 派生 state」的唯一合法口；
- `getSnapshotBeforeUpdate(prevProps, prevState)`：DOM 更新**前**最后一瞥（读滚动位置），返回值作为 componentDidUpdate 第三参。

错误边界：`static getDerivedStateFromError`（render 降级 UI）+ `componentDidCatch`（上报）——**函数组件至今没有等价 Hook，错误边界仍必须用类组件**（这是类组件仅存的独有能力，答出来很加分）。

## 2. 与 Hooks 的对应（迁移心智）

| 类组件 | 函数组件 |
|---|---|
| componentDidMount | `useEffect(fn, [])` |
| componentDidUpdate | `useEffect(fn, [deps])`（带依赖） |
| componentWillUnmount | effect 返回的清理函数 |
| shouldComponentUpdate | `React.memo`（见 [[2.04 记忆化：memo、useMemo 与 useCallback]]） |
| getSnapshotBeforeUpdate | 无直接对应（useLayoutEffect 近似） |
| getDerivedStateFromProps | 渲染期间直接计算 / key 重置（多数场景根本不需要） |

注意口径：**Hooks 不是生命周期的一对一翻译**——effect 围绕「同步外部系统」而非「组件时刻」设计，强行按生命周期思考 effect 是常见反模式（见 [[2.02 useEffect 与 useLayoutEffect]]）。

## 3. 类组件遗产题两连

**为什么事件处理要绑定 this？**

```jsx
<button onClick={this.handleClick}>  // 方法被「拿出来」作为回调
```

三个知识点的叠加：class 内部默认严格模式 + 隐式绑定丢失（方法作为回调传递后按默认绑定调用，见 [[1.04 this 与 call、apply、bind]]）+ React 合成事件系统以普通函数形式调用回调 → this 为 undefined。老 createClass API 曾自动绑定，ES6 class 不会。解法演进：constructor 里 `bind` → **类字段 + 箭头函数**（`handleClick = () => {}`，Babel class-properties 插件普及后的主流）→ 函数组件后问题消失。

**为什么 constructor 里要 super(props)？**

ES6 规则：子类 constructor 中必须先调 super 才能用 this（见 [[1.06 继承与 class]]）。传 props 的意义：让 `this.props` 在 **constructor 里**就可用；只写 `super()` 时 constructor 内 this.props 是 undefined——但 render 等其他地方仍能用，因为 React 在构造之后还会把 props 赋到实例上。所以答案是「必须 super，最好带 props，不带只影响 constructor 内的访问」。

## 面试问答

### Q: React 16 生命周期发生了什么变化？为什么？

满分答案：废弃 componentWillMount、componentWillReceiveProps、componentWillUpdate，新增 static getDerivedStateFromProps 和 getSnapshotBeforeUpdate。原因是 Fiber 架构下 render 阶段可中断、可重复执行，「Will」系钩子会被多次调用，其中的副作用不安全；替代 API 刻意设计成静态方法（拿不到 this 写不了副作用）。副作用一律移到 commit 阶段钩子（componentDidMount/Update）。加分点：getSnapshotBeforeUpdate 在 DOM 变更前读取现场（滚动位置），返回值传给 componentDidUpdate。

### Q: 挂载和更新阶段的生命周期执行顺序？

满分答案：挂载——constructor → getDerivedStateFromProps → render → componentDidMount；更新——getDerivedStateFromProps → shouldComponentUpdate → render → getSnapshotBeforeUpdate → componentDidUpdate；卸载 componentWillUnmount。按 Fiber 分组记：render 阶段的可能重复执行须纯净，commit 阶段的只执行一次可做副作用。

### Q: 函数组件怎么「模拟」生命周期？有什么不能替代的？

满分答案：useEffect 空依赖近似 didMount、带依赖近似 didUpdate、清理函数近似 willUnmount，React.memo 替代 shouldComponentUpdate。但强调心智差异：effect 的设计是「让副作用与渲染结果同步」，不是时刻钩子，按生命周期硬套容易写出依赖缺失的 bug。目前唯一不可替代：错误边界（getDerivedStateFromError/componentDidCatch）没有 Hook 版，需要类组件或 react-error-boundary 库封装。

### Q: 为什么类组件的事件处理函数要 bind(this)？有哪些写法？

满分答案：方法作为回调传给合成事件系统后以普通函数调用，class 体内是严格模式，默认绑定得到 undefined。写法演进：render 里内联箭头（每次渲染新函数，影响子组件 memo）、constructor 里 bind 一次（性能最稳）、类字段箭头函数（简洁、每实例一份函数）。函数组件时代问题本身消失，这题实质考 this 绑定规则 + 严格模式。
