# 记忆化：memo、useMemo 与 useCallback

## TL;DR

**三件套各管一层：React.memo 缓存「组件渲染结果」（props 浅比较跳过重渲染），useMemo 缓存「计算值」，useCallback 缓存「函数身份」**。铁律：useCallback/useMemo 传引用给子组件时，**只有子组件包了 memo 才有意义**——否则子组件照样重渲染，缓存白做。React Compiler 正在让手工记忆化退役。

---

## 1. 先建立问题模型

父组件渲染 → 默认**整棵子树跟着重渲染**（这是 React 的 push 模型，见 [[React vs Vue 渲染对比]]）。重渲染 ≠ 改 DOM（diff 兜底），但大子树的函数执行 + 对比本身也有成本。记忆化的目标：**在「引用相等」可判定的前提下跳过这些执行**。

---

## 2. 三件套分工

```jsx
// ① memo：props 浅比较，相等则跳过整个组件的重渲染
const List = React.memo(function List({ items, onPick }) { ... });
// 可传第二参自定义比较：React.memo(List, (prev, next) => 是否相等)

function Parent() {
  const [query, setQuery] = useState('');

  // ② useMemo：缓存昂贵计算的【值】
  const filtered = useMemo(() => bigFilter(items, query), [items, query]);

  // ③ useCallback：缓存【函数引用】——否则每次渲染新函数，List 的 memo 永远失效
  const onPick = useCallback((id) => setSelected(id), []);

  return <List items={filtered} onPick={onPick} />;
}
```

关系再强调一遍（最高频判分点）：**memo 是消费端，useMemo/useCallback 是供给端**——子组件没有 memo，父组件缓存函数/对象毫无收益；反过来子组件有 memo，父组件却传内联对象/函数，memo 每次都被新引用击穿。两端必须配套。

`useCallback(fn, deps)` ≡ `useMemo(() => fn, deps)`，只是语义化包装。依赖都用 Object.is 逐项浅比较；**依赖里放每次渲染新建的对象 = 缓存永久失效**（对象也要先 memo 或降级为原始值依赖）。

---

## 3. 类组件对应物与 shallowEqual

PureComponent = 内置了「props/state 浅比较」的 shouldComponentUpdate；函数组件对应 React.memo（只比 props）。浅比较的实现（react-redux/React 内部同款，手写高频）：

```js
function shallowEqual(a, b) {
  if (Object.is(a, b)) return true;                    // 同引用/同原始值
  if (typeof a !== 'object' || a === null ||
      typeof b !== 'object' || b === null) return false;
  const ka = Object.keys(a), kb = Object.keys(b);
  if (ka.length !== kb.length) return false;
  return ka.every(k =>
    Object.prototype.hasOwnProperty.call(b, k) && Object.is(a[k], b[k]));
  // 只比第一层：值仍是对象时按引用判断——嵌套变更检测不到，这就是「浅」
}
```

`Object.is` 的两处特判（NaN、±0）见 [[1.07 对象属性与属性描述符]]。浅比较的局限即 PureComponent 的坑：**原地 mutate 的对象引用没变，更新被误跳过**——不可变更新（展开/`toSpliced` 等）是配套纪律。

---

## 4. 使用准则与反模式

- **先测量再优化**：React DevTools Profiler 找到真正渲染频繁/耗时的组件再包 memo——比较本身有成本，全员 memo 是负优化；
- 更结构化的免费优化先做：**状态下沉**（把变化的状态挪进小组件）、**children 提升**（`<Layout>{children}</Layout>` 中 children 引用不变不重渲染）；
- useMemo 的第二用途：稳定引用以喂给依赖数组/Context value（见 [[1.08 组件通信与 Context]]）；
- 漏依赖会拿到过期闭包（见 [[2.03 Hooks 闭包陷阱]]），如实声明依赖是底线；
- **React Compiler**（React 19 生态）在编译期自动插入细粒度记忆化，目标就是让手写 useMemo/useCallback 成为历史——现状与原理见 [[ReactCompiler]] 系列。面试带上这个趋势判断很加分。

## 面试问答

### Q: useMemo 和 useCallback 的区别与使用场景？

满分答案：useMemo 缓存计算结果的值，用于昂贵计算和「需要稳定引用的对象」（依赖项、Context value）；useCallback 缓存函数引用，等价于 useMemo 返回函数，专门配合 memo 子组件或作为其他 hook 的依赖。共同机制：deps 逐项 Object.is 比较，变了才重算。关键判断：传给 memo 组件的引用类型 props 才需要缓存，子组件没 memo 时缓存无意义；依赖必须如实声明否则闭包过期。

### Q: React.memo 和 PureComponent 的关系？浅比较是什么？

满分答案：同一思想的两代实现——PureComponent 用浅比较实现 shouldComponentUpdate（比 props 和 state），memo 是函数组件版（只比 props，支持自定义比较函数）。浅比较：先 Object.is 整体判断，再比第一层 key 数量与每个值的 Object.is——嵌套对象按引用比较，所以必须配合不可变更新，原地修改会被误判「没变」而跳过渲染。可现场手写 shallowEqual。

### Q: 是不是所有组件都应该包 memo？

满分答案：不是——比较有成本、缓存占内存，props 频繁变化的组件包了反而多做一次全量浅比较。方法论：先用 Profiler 定位「渲染次数多且耗时」的组件；先尝试结构优化（状态下沉、children 提升）这类零成本手段；确认是「父频繁渲染 + 子 props 基本不变 + 子渲染昂贵」三条件齐备再上 memo，并保证传入引用已稳定化。趋势：React Compiler 自动做细粒度记忆化，未来手工三件套会大幅减少。
