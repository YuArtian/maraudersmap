# 并发特性与优先级调度

## TL;DR

**并发渲染 = Fiber 可中断 + Lane 优先级 + Scheduler 时间切片**：紧急更新（输入）可以打断非紧急更新（大列表刷新）的 render，被打断的稍后重来。开发者入口就三个：`startTransition`/`useTransition` 把更新降级为「可打断的过渡」，`useDeferredValue` 让派生值延迟跟随，`Suspense` 声明加载边界。

---

## 1. 要解决的体验问题

输入框 + 万条结果过滤：每敲一个字都触发大列表重渲染，同步模式下 render 一旦开始就不能停——输入卡成幻灯片。

并发思路：**输入框的更新是紧急的，列表的更新不紧急**。让紧急更新随时打断不紧急的 render（反正 render 阶段无副作用、可作废重来，见 [[1.02 Fiber 架构]]），键入永远即时响应，列表「稍后跟上」。

---

## 2. Lane 模型：31 条二进制车道

优先级用 31 位二进制表示，**位越靠右优先级越高**：

```text
SyncLane            0b…0000001   离散交互（点击、输入）→ 同步级
InputContinuousLane 0b…0000100   连续交互（滚动、拖拽）
DefaultLane         0b…0010000   setTimeout、网络回调等默认更新
TransitionLanes     0b…1111111000000（16 条）  startTransition 系
RetryLanes          …             Suspense 重试
```

用位运算的收益：**一个数字承载一组优先级**——合并（`|`）、包含判断（`&`）、取最高优（`lanes & -lanes`，孤立最低位）都是 O(1)。每个 update 带 lane 入队，调度时取最紧急的 lane 批次先渲染；**同 lane 的更新合并为一次渲染**——这正是 React 18 自动批处理「按优先级分组」的机制基础（见 [[1.04 setState 与批量更新]]）。

**饥饿问题**：低优先级反复被插队怎么办？lane 会记录过期时间，过期后强制以同步方式完成，保证不被饿死。

---

## 3. Scheduler 与时间切片

Scheduler 是独立的包：维护任务小顶堆，按过期时间排序；用 **MessageChannel 宏任务**安排每一片（不用 setTimeout 是因为其 4ms 嵌套最小延迟；不用微任务是因为微任务清空前不让渲染，见 [[2.01 事件循环与宏微任务]]）。每片约 5ms，workLoop 每处理完一个 fiber 就 `shouldYield()` 检查，时间片用尽或有更高优任务就让出主线程，浏览器得以插入绘制和事件处理。

---

## 4. 三个开发者 API

**useTransition / startTransition**——把回调里的更新标记为 Transition lane：

```jsx
const [isPending, startTransition] = useTransition();

function onChange(e) {
  setQuery(e.target.value);                    // 紧急：输入框立即回显
  startTransition(() => setList(filter(e.target.value)));  // 非紧急：可被打断
}
// isPending 为 true 时可以渲染「加载中」态
```

**useDeferredValue**——没法包住 set 调用时（值来自 props），让派生值「延迟跟随」：

```jsx
const deferredQuery = useDeferredValue(query);   // 紧急渲染先用旧值，空闲后再用新值重渲染
const results = useMemo(() => search(deferredQuery), [deferredQuery]);
```

与防抖节流的本质区别（高频追问）：防抖节流是**固定时间延迟**，快机器也白等、慢机器照样卡（渲染本身没变便宜也不可中断）；Transition 是**调度让位**，没有人为延迟，且慢机器上长 render 可被新输入打断作废。两者解决的层次不同，可叠加。

**Suspense**：声明式等待——子树在「等数据/等代码」时挂起，最近的 Suspense 显示 fallback。React.lazy 代码分割、React 19 的 `use(promise)` 读数据、SSR 流式渲染选择性水合都建立在它上面（路由层的取舍见 [[React Router v7 路由懒加载与切页 UI]]）。

**现状补充（截至 React 19）**：并发特性默认按需启用——只有用了 Transition/Suspense 等特性的更新才走并发路径；`use` Hook、Actions（useActionState/useOptimistic）进一步把「异步 + 过渡」标准化。回答带上「createRoot 是入场券，特性按需生效」很加分。

## 面试问答

### Q: React 的并发模式是什么？解决什么问题？

满分答案：并发渲染让 React 可以同时准备多个版本的 UI——render 阶段可中断，紧急更新（输入、点击）能打断非紧急更新（大列表、数据刷新）的渲染，被打断的作废重来。解决「一次大 render 阻塞交互」的体验问题。三块地基：Fiber 链表化使循环可中断、Lane 位运算优先级模型、Scheduler 基于 MessageChannel 的约 5ms 时间切片。18 的 createRoot 开启能力，实际是否并发按特性使用情况按需生效。

### Q: 讲讲 Lane 模型？为什么用位运算？

满分答案：31 位二进制车道，位越低优先级越高：SyncLane 给离散交互、InputContinuousLane 给连续交互、DefaultLane 给默认更新、16 条 TransitionLanes 给过渡更新、RetryLanes 给 Suspense 重试。位运算让「一组优先级」压缩在一个数字里，合并、求交、取最高优都是 O(1)；同 lane 更新合并渲染实现自动批处理。低优先级任务有过期时间兜底，防止被高优任务无限插队饿死。

### Q: useTransition 和 useDeferredValue 怎么选？和防抖有什么区别？

满分答案：能拿到 set 调用就用 useTransition 包住非紧急更新，还附赠 isPending；值从 props 传下来、改不了源头时用 useDeferredValue 做延迟跟随的派生值，配合 useMemo。与防抖节流的区别是本质性的：防抖是固定墙钟延迟、渲染本身仍不可中断；Transition 无人为延迟、靠优先级调度让位，且长渲染可被打断作废。输入抖动明显时两者可以叠加使用。

### Q: 时间切片为什么用 MessageChannel 而不是 setTimeout 或微任务？

满分答案：setTimeout 有嵌套 5 层后最小 4ms 的规范限制，切片频繁让出时累计浪费明显；微任务会在当前宏任务后全部清空、清空期间浏览器无法插入渲染，起不到「让出主线程」的作用。MessageChannel 是无延迟下限的宏任务，每片结束 postMessage 安排下一片，让渲染和输入事件有机会插进片与片之间。
