# 组件通信与 Context

## TL;DR

**按关系选通道：父传子 props、子传父回调、兄弟提升到共同父级、远亲用 Context 或外部状态**。Context 的两个关键认知：它为「低频全局数据」（主题、用户、语言）设计；**Provider 的 value 变化会让所有消费组件重渲染且无视 memo**，value 记得稳定化。

---

## 1. 通信方式全景

| 关系 | 手段 |
|---|---|
| 父 → 子 | props；ref 拿子组件命令式句柄（useImperativeHandle，见 [[2.05 Ref 体系]]） |
| 子 → 父 | 回调函数 props（onXxx）；受控组件模式 |
| 兄弟 | **状态提升**到最近共同父级 |
| 跨层级 | Context |
| 任意/全局 | 外部状态管理（Redux/zustand，见 [[3.01 Redux 原理与取舍]]）；发布订阅事件总线（可追踪性差，慎用） |

状态提升是默认答案；「provider 地狱」或高频共享状态才升级到外部 store。

---

## 2. Context 正确用法

```jsx
const ThemeContext = createContext('light');   // 默认值：只在「上面没有 Provider」时生效

function App() {
  const [theme, setTheme] = useState('light');
  // ★ 稳定化 value：否则 App 每次渲染都造新对象，所有消费者跟着全部重渲染
  const ctx = useMemo(() => ({ theme, setTheme }), [theme]);
  return (
    <ThemeContext.Provider value={ctx}>
      <Page />
    </ThemeContext.Provider>
  );
}

function Button() {
  const { theme } = useContext(ThemeContext);   // 函数组件的标准消费方式
  ...
}
```

工作机制要点：

- 消费组件更新的判定是 **`Object.is(旧 value, 新 value)`**——value 是内联对象字面量时每次渲染都「变了」，全体消费者重渲染，这是最常见的 Context 性能事故，解法是 useMemo 包 value 或把 state 与 dispatch 拆成两个 Context；
- **Context 更新穿透 memo/shouldComponentUpdate**：中间组件被 memo 跳过，不影响下方消费者收到新值（React 沿 fiber 树找消费者，不依赖 props 传递）；
- 消费方式演进：`Consumer` render props（老）→ `useContext`（主流）→ **React 19 起可直接 `use(Context)`，且支持在条件语句里调用**；
- 默认值只在组件树上方**完全没有** Provider 时使用，传 `undefined` 不会回退到默认值。

---

## 3. Context vs 状态管理库（辨析题）

Context 本身**不是状态管理**——它只是依赖注入的传输管道，状态仍然靠 useState/useReducer 维护。局限：

1. 无选择性订阅：value 一变全体消费者重渲染（store 库可以 selector 精准订阅切片）；
2. 组合多个状态源要嵌套多层 Provider；
3. 无中间件/devtools/时间旅行等治理能力。

结论口径：**低频、小体积的全局数据（主题、登录用户、i18n）用 Context 足矣；高频更新、大 store、跨模块协作用专门的状态库**。`useReducer + Context` 可以搭出小型 Redux（dispatch 天然稳定，适合放单独 Context），但到达上面三条局限时就该换工具。

## 面试问答

### Q: React 组件间有哪些通信方式？

满分答案：按关系答——父传子 props，父调子用 ref + useImperativeHandle 暴露命令式句柄；子传父回调 props；兄弟组件状态提升到共同父级；跨层级 Context；全局/复杂场景用外部状态库（Redux/zustand）或服务端状态库（React Query）。补一句原则：优先最简单的通道，状态提升解决不了（层级太深、更新太频）才升级工具。

### Q: Context 的原理和性能陷阱？

满分答案：Provider 把 value 挂在 fiber 上，更新时 React 向下寻找消费者标记重渲染，判定标准是 Object.is 比较新旧 value——所以内联对象字面量做 value 会让每次父渲染都触发全体消费者更新，且这种更新穿透 React.memo。对策：useMemo 稳定 value、按变更频率拆分 Context（state 与 dispatch 分离）、消费点下沉。加分点：React 19 的 use(Context) 支持条件调用。

### Q: Context 能替代 Redux 吗？

满分答案：定位不同——Context 是传输管道不是状态容器，配 useReducer 可以覆盖小型场景。三个硬局限决定上限：没有 selector 级订阅（一变全更）、多状态源嵌套 Provider、缺中间件与 devtools 生态。主题、用户信息这类低频数据用 Context；高频更新、大规模共享、需要可追踪性的用状态库。能按数据「更新频率与影响面」给出选型标准，比背 API 更重要。
