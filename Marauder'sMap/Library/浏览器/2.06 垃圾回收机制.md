# 垃圾回收机制

## TL;DR

**判断垃圾的标准是「从根出发够不够得着」（可达性），主算法是标记-清除**；V8 在此之上做分代：**新生代小而频、用复制算法（Scavenge），老生代大而稳、用标记-清除 + 标记-整理**，并用并行/增量/并发手段把停顿藏起来。引用计数已弃用——它搞不定循环引用。

---

## 1. 怎么判定「垃圾」

**可达性分析**：从根集合（全局对象、当前调用栈的局部变量、活动闭包）出发，沿引用遍历，够得着的是活对象，够不着的就是垃圾。

早期方案**引用计数**（引用数归零即回收）有致命伤——**循环引用**：

```js
function cycle() {
  const a = {}, b = {};
  a.ref = b; b.ref = a;   // 互相引用，计数永不为 0
}  // 函数退出后 a、b 已不可达，标记清除能回收，引用计数不能
```

所以现代引擎全部采用可达性 + 标记-清除（Mark-Sweep）：标记阶段从根遍历打标，清除阶段回收未标记内存。缺点：清完产生**内存碎片**——由此引出整理（Compact）与分代设计。

---

## 2. V8 的分代回收

**分代假说**：大多数对象朝生夕死；活过几轮的对象倾向于长寿。据此把堆分两块，用不同算法：

```mermaid
flowchart LR
    subgraph 新生代（小，1~8MB 级）
        F[使用区 From] -- "Scavenge：把活对象复制过去" --> T[空闲区 To]
        T -- 角色互换 --> F
    end
    F -- "活过两轮 → 晋升" --> O
    subgraph 老生代（大）
        O[标记-清除 Mark-Sweep<br/>+ 标记-整理 Mark-Compact]
    end
```

- **新生代 · Scavenge 复制算法**：内存对半分为 From/To；回收时把 From 里的活对象**复制**到 To（天然紧凑无碎片），整块清空 From，两区互换。空间换时间——活对象少时极快。**晋升**：经历两次回收仍存活（或 To 区占用超阈值）的对象移入老生代；
- **老生代 · 标记-清除为主**：对象大、存活率高，复制不划算；碎片积累到影响分配时跑一次**标记-整理**（把活对象向一端滑动）。

---

## 3. 把停顿藏起来：全停顿问题的三板斧

GC 时要暂停 JS 执行（Stop-The-World），大堆一次全量标记可能上百毫秒——掉帧卡顿。V8 的优化：

| 手段 | 做法 |
|---|---|
| **并行 Parallel** | 多个辅助线程一起干（新生代回收） |
| **增量 Incremental** | 把老生代标记切成小步，穿插在 JS 执行间隙 |
| **并发 Concurrent** | 标记/清除在后台线程与 JS **同时**进行 |

效果：主线程停顿从「一大段」变成「许多小于一毫秒的碎片」。（这也解释了为什么现代页面很少感知到 GC，却仍要避免瞬间制造海量临时对象——分配速率超过回收速率照样爆。）

---

## 4. 内存泄漏：GC 收不走的「可达垃圾」

GC 只回收**不可达**对象；「逻辑上没用了但仍被引用」它无能为力。前端四大泄漏源：

1. **意外的全局变量**（漏写声明、挂 window）；
2. **忘清的定时器/事件监听**（组件卸载不 clearInterval / removeEventListener——回调闭包连带整棵引用树被拖住）；
3. **闭包长期持有大对象**（机制见 [[1.03 执行上下文、调用栈与闭包]]）；
4. **游离 DOM 引用**（JS 变量还攥着已从文档移除的节点；Map 做缓存不放手——换 WeakMap/WeakRef，见 [[1.09 Set、Map 与弱引用]]）。

排查手法：DevTools Memory 面板拍两次堆快照对比（操作前后），按 Retained Size 排序找可疑对象，看 Retainers 链定位谁抓着不放；Performance 面板看内存曲线是否只涨不落。

## 面试问答

### Q: JS 垃圾回收是怎么工作的？

满分答案：判定标准是可达性——从全局对象、调用栈、活动闭包等根出发遍历引用，够不着的即垃圾；主算法标记-清除，标记活对象、清除未标记者。引用计数因无法处理循环引用已被弃用。V8 再做分代：新生代用 Scavenge 复制算法（From/To 半区复制，快且无碎片，活过两轮晋升），老生代用标记-清除加标记-整理去碎片，配合并行、增量、并发把停顿切碎藏进 JS 执行间隙。

### Q: 为什么新生代用复制算法、老生代不用？

满分答案：算法成本结构不同——复制算法的开销正比于「活对象数量」，新生代对象朝生夕死、活的极少，复制既快又天然整理了内存；但它牺牲一半空间，且老生代对象大、存活率高，复制的搬运成本和空间浪费都不可接受，所以老生代用标记-清除（开销正比于堆大小但不搬对象），碎片多了再做一次标记-整理。这是「分代假说 + 按存活率选算法」的教科书应用。

### Q: 哪些写法会内存泄漏？怎么定位？

满分答案：四类——意外全局变量；未清理的定时器与事件监听（含被回调闭包拖住的大对象）；闭包长期引用大数据；游离 DOM 节点引用与只进不出的 Map 缓存（应换 WeakMap）。定位：Memory 面板对比操作前后的堆快照，按 Retained Size 找嫌疑对象、顺 Retainers 引用链找到持有者；配合 Performance 内存曲线确认「只涨不落」。预防原则：生命周期结束时对称地清理（组件卸载钩子里解绑一切）。

### Q: WeakMap 和垃圾回收是什么关系？

满分答案：WeakMap 的键是弱引用，不计入可达性——键对象在别处失去所有强引用后可被正常回收，对应条目自动消失。因此适合「对象附属数据」和缓存场景：DOM 节点元数据、对象级 memoize（Vue 3 的 reactiveMap 就是例子），数据生命周期自动跟随宿主对象，不会因为缓存本身而泄漏。也因为成员随时可能被回收，它不可遍历、没有 size。
