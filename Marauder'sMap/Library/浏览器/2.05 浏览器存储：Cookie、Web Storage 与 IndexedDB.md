# 浏览器存储：Cookie、Web Storage 与 IndexedDB

## TL;DR

**Cookie 是「给服务器捎话的」（每次请求自动带上，4KB），Web Storage 是「存前端自己的」（5MB 左右，纯客户端），IndexedDB 是「浏览器里的数据库」（大容量、异步、可存对象）**。localStorage 与 sessionStorage 的差别只有生命周期和共享范围。

---

## 1. 四种存储对比总表

| | Cookie | localStorage | sessionStorage | IndexedDB |
|---|---|---|---|---|
| 容量 | ~4KB | ~5MB | ~5MB | 大（磁盘配额级，GB 可谈） |
| 随请求发送 | **自动携带** | 否 | 否 | 否 |
| 生命周期 | 会话或 Expires/Max-Age | **永久**（除非清除） | **标签页关闭即毁** | 永久 |
| 共享范围 | 按 domain + path | 同源的所有标签页 | **仅当前标签页**（刷新存活，新开标签不共享） |同源 |
| API | document.cookie（难用）| 同步 key-value | 同步 key-value | **异步**、事务、索引、可存二进制 |
| 值类型 | 字符串 | 字符串 | 字符串 | 结构化克隆支持的一切（对象/Blob） |

选型口诀：要跟服务器走的（登录态）→ Cookie（配 HttpOnly）；本地长期偏好 → localStorage；单次会话的表单草稿/标签页隔离状态 → sessionStorage；大量结构化数据、离线缓存、文件 → IndexedDB。

---

## 2. Cookie 的属性（安全三件套 + 域规则）

```text
Set-Cookie: sid=abc; Domain=example.com; Path=/; Max-Age=86400;
            HttpOnly; Secure; SameSite=Lax
```

- **HttpOnly**：JS 读不到（`document.cookie` 不可见），防 XSS 偷 Cookie；
- **Secure**：仅 HTTPS 发送；
- **SameSite**：跨站携带策略，Strict/Lax（默认）/None，防 CSRF（详见 [[1.07 Web 安全：XSS 与 CSRF]]）；
- **Domain 规则**：只能设为**当前域或其父域**（`i.example.com` 可设 `i.example.com` 或 `example.com`），设兄弟域、子域、无关域一律无效；设了父域则**父域及其所有子域**的请求都会带上这枚 Cookie——同主域多子系统共享登录态就靠这个；
- **Path**：限定路径前缀；
- 没设 Expires/Max-Age 就是**会话 Cookie**，关浏览器即失效。

---

## 3. localStorage / sessionStorage 细节题

```js
localStorage.setItem('user', JSON.stringify(obj));  // 只能存字符串，对象要序列化
const user = JSON.parse(localStorage.getItem('user') ?? 'null');
```

- **sessionStorage 的「session」是标签页会话**，不是服务器 session：刷新还在、关标签就没；同页面新开标签**不共享**（从当前页用 a 标签新开的标签会复制一份初始值，之后各改各的）；
- **storage 事件**：其他同源标签页改动 localStorage 时触发（本页改动不触发自己）——可以做多标签页通信，现代替代是 BroadcastChannel；
- 同步 API，大量读写会阻塞主线程；隐私模式可能配额为 0，写入要 try/catch（Safari 旧版会直接抛错）；
- 安全：XSS 可整库读走，**token 存 localStorage vs HttpOnly Cookie** 是经典辩论——前者防不了 XSS、后者要防 CSRF，结论是「HttpOnly Cookie + SameSite + CSRF Token」或「内存态 token + 静默刷新」。

---

## 4. IndexedDB：浏览器里的事务型数据库

特征：异步（不阻塞主线程）、同源、支持**对象仓库 + 索引 + 事务 + 游标**、可存结构化克隆对象与 Blob，容量按磁盘配额协商。

原生 API 冗长（open → onupgradeneeded 建表 → transaction → objectStore → request.onsuccess），工程上直接用封装库：**localForage**（localStorage 风格 API，自动降级）、idb（Promise 化薄封装）、Dexie。

适用：离线应用数据、接口缓存、编辑器草稿（大文档）、文件分片断点续传的暂存。

## 面试问答

### Q: Cookie、localStorage、sessionStorage 的区别？

满分答案：三个维度——是否随请求发送：只有 Cookie 自动携带（所以只放服务器需要的最小信息，4KB 限制）；生命周期：Cookie 由 Expires/Max-Age 控制，localStorage 永久，sessionStorage 关标签页即毁；共享范围：Cookie 按 domain/path，localStorage 同源全标签共享，sessionStorage 仅本标签页。补充：都只能存字符串，对象需 JSON 序列化；大数据用 IndexedDB。

### Q: Cookie 的 Domain 能随便设吗？

满分答案：不能——只能设置为当前域或其父域，兄弟域、子域和无关域都无效。设为父域后对该父域及全部子域生效，请求任一子域都会携带，这是同主域多系统共享登录态的机制。配套细节：作用域匹配再叠加 Path 前缀、SameSite 跨站策略；服务端与前端受同样的规则约束。

### Q: 登录 token 放哪里最安全？

满分答案：对比三方案——localStorage：XSS 一锅端，且要手动附加到请求头；HttpOnly Cookie：JS 读不到防 XSS 窃取，但自动携带引入 CSRF，需 SameSite + CSRF Token 配套；内存变量 + refresh token 静默续期：刷新丢失需换取，安全性最好实现最重。工程主流：HttpOnly + Secure + SameSite=Lax 的 Cookie 存会话凭证，敏感操作再加二次校验。关键是展示对两类攻击面的取舍理解。

### Q: 多标签页之间怎么通信？

满分答案：同源场景按现代程度排——BroadcastChannel（专用广播 API，首选）；storage 事件（改 localStorage 触发其他标签页监听，老牌方案）；SharedWorker（共享线程，还能顺便共享 WebSocket 连接）；Service Worker 的 clients.postMessage。跨源只能 window.open/iframe 拿到引用后 postMessage 并校验 origin。
