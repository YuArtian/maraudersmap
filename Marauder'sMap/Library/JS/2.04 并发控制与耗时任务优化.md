# 并发控制与耗时任务优化

## TL;DR

**「限制并发数」的核心是一个补位循环：先发 n 个请求，谁完成谁的坑位就补下一个**。「耗时任务不卡页面」的核心是让出主线程：切片（setTimeout / scheduler.yield / requestIdleCallback）或干脆搬走（Web Worker）。动画对齐渲染帧用 requestAnimationFrame。

---

## 1. 手写并发池（高频手写题）

场景：100 个请求，同时最多跑 5 个。

```js
async function asyncPool(limit, tasks) {
  const results = [];
  const executing = new Set();

  for (const [i, task] of tasks.entries()) {
    const p = Promise.resolve().then(() => task());   // 惰性启动
    results[i] = p;                                    // 保序收集
    executing.add(p);
    p.finally(() => executing.delete(p));

    if (executing.size >= limit) {
      await Promise.race(executing);   // 等最快的一个腾出坑位
    }
  }
  return Promise.all(results);
}

// 用法：tasks 是【函数】数组（不能是已创建的 Promise——那样早就并发起跑了）
asyncPool(5, urls.map(url => () => fetch(url)));
```

判分点：

1. **任务必须传函数**，Promise 一旦 new 出来就已经在跑，谈不上限流；
2. `Promise.race(executing)` 实现「谁先完成谁补位」，而不是一批一批地 all（分批会让快的等慢的）；
3. 结果按下标保序；单个失败是否中断按需求定（收集错误可先 catch 包装）。

生产直接用 `p-limit` / `p-queue`。

## 2. 倒计时为什么不准 & 怎么修

`setInterval(fn, 1000)` 的三个不准来源：回调排队被同步任务挤压、**后台标签页节流**（Chrome 对不可见页面把定时器限到约 1 次/分钟）、误差累计。

正确姿势：**每次醒来用时间戳重新计算剩余量，而不是每次减一**：

```js
function countdown(endTime, onTick) {
  function tick() {
    const remain = endTime - Date.now();       // 永远以系统时间为准
    onTick(Math.max(0, remain));
    if (remain > 0) {
      // 下一次对齐到整秒边界，抵消漂移
      setTimeout(tick, remain % 1000 || 1000);
    }
  }
  tick();
}
```

加强手段：

- **Web Worker 里跑定时器**：Worker 不受页面渲染阻塞影响、后台节流也更宽松，tick 时 postMessage 通知主线程（电商秒杀倒计时常用）；
- 服务端时间校准：进页面时拿服务器时间与本地时间的差值修正 endTime。

## 3. requestAnimationFrame：动画的正确打开方式

rAF 的回调在**下一次渲染（重绘）之前**执行，与显示器刷新率对齐（60Hz 即约 16.7ms 一帧）。

用定时器做动画的问题：定时器间隔与渲染帧对不上——一帧里跑了两次回调（浪费）或一帧里一次都没跑（跳帧），且事件循环繁忙时间隔失真。rAF 保证**每帧恰好一次**，后台标签页自动暂停省电。

```js
function animate(t) {
  update(t);                 // t 是高精度时间戳
  requestAnimationFrame(animate);   // 一次性 API，要续帧就再注册
}
requestAnimationFrame(animate);
```

归类澄清（常考）：rAF 既不是典型宏任务也不是微任务，**它属于渲染流程的一个阶段**（渲染前回调）；多个 rAF 回调在同一帧内一起执行。另外：rAF 只解决「渲染同步」，回调本身太重照样掉帧。

## 4. 耗时任务不卡主线程的四板斧

主线程一次性跑 200ms 的计算，页面就冻 200ms（掉帧、点不动）。指导线：**单个任务超过 50ms 就算 Long Task**。

| 手段 | 思路 | 适用 |
|---|---|---|
| 时间切片 | 大任务拆小块，块间让出主线程 | 可分割的循环类计算 |
| `requestIdleCallback` | 只在**每帧空闲期**干活，deadline 告诉你还剩多少时间 | 低优先级、可延后的任务（上报、预热） |
| `scheduler.yield()` / `scheduler.postTask` | 新一代调度 API，带优先级、可中断续跑 | Chrome 系，渐进增强 |
| **Web Worker** | 计算整个搬到别的线程，postMessage 通信 | 重计算（解析、加密、图像处理） |

时间切片的通用骨架：

```js
async function chunkedRun(items, process, chunkMs = 8) {
  let i = 0;
  while (i < items.length) {
    const start = performance.now();
    while (i < items.length && performance.now() - start < chunkMs) {
      process(items[i++]);
    }
    // 让出主线程：渲染、用户输入得以插队
    await new Promise(r => setTimeout(r));   // 有 scheduler.yield 则优先用它
  }
}
```

requestIdleCallback 注意事项：回调可能长时间不触发（页面一直忙），关键任务要给 `{ timeout }` 兜底；它不适合做动画（那是 rAF 的事）。

Worker 的限制：无 DOM 访问、通信走结构化克隆（大数据用 Transferable 转移所有权避免拷贝开销）。

## 面试问答

### Q: 实现一个并发限制的请求调度器？

满分答案：维护一个执行中集合，顺序遍历任务：启动（注意传入函数惰性启动）、加入集合、finally 时移出；集合大小达到上限就 await Promise.race 等最快的一个完成再补位；结果按下标存数组保序，最后 Promise.all 返回。强调 race 补位优于分批 all——分批会让整批等最慢者。生产可用 p-limit。

### Q: 前端倒计时为什么会不准？怎么做一个精确倒计时？

满分答案：三个原因——事件循环里回调被挤压延迟、浏览器对后台标签页做定时器节流、逐次累加的误差滚雪球。方案：不做「每秒减一」，每次 tick 用目标时间戳减当前时间重算剩余，并把下次 setTimeout 对齐到整秒边界；要求更高就把定时器放进 Web Worker（不受渲染阻塞、节流更宽松），配合服务端时间校准本地时钟偏差。

### Q: 为什么动画要用 requestAnimationFrame 而不是 setTimeout？

满分答案：渲染是按帧进行的，定时器间隔与帧边界无关，会出现一帧多跑（浪费）或一帧不跑（跳帧），加上事件循环延迟导致间隔失真；rAF 保证回调在每次重绘前恰好执行一次，与刷新率同步，后台标签自动暂停。归类上 rAF 属于渲染流程的渲染前阶段，不是普通宏任务。注意它只保证时机正确，回调太重仍会掉帧。

### Q: 页面要执行一个很重的计算任务，怎么不卡 UI？

满分答案：按任务性质选——可拆分的用时间切片：每块控制在几毫秒内，块间 setTimeout/scheduler.yield 让出主线程；可延后的用 requestIdleCallback 在帧空闲期执行并设 timeout 兜底；重计算直接上 Web Worker 换线程，大数据用 Transferable 避免克隆开销。判断标准：主线程单任务超 50ms 即 Long Task，Performance 面板可验证优化效果。
