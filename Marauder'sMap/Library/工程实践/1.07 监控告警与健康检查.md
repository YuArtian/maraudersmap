# 监控告警与健康检查

## TL;DR

**可观测性三件套：Metrics（指标，出没出问题）、Logging（日志，发生了什么）、Tracing（链路，问题在哪一环）**。前端侧接监控 SDK 上报性能与异常，服务侧暴露健康检查端点供编排平台探活。告警的关键不是「能报」而是**分级与降噪**——遍地告警等于没有告警。

> 前端指标采集与异常捕获的实现见 [[2.01 Web 性能指标与前端监控]]。

---

## 1. 健康检查：让编排平台知道你活着

服务暴露一个轻量端点（`/healthz`），编排平台按周期探测：

| 探针 | 语义 | 失败后果 | 检查内容 |
|---|---|---|---|
| **liveness** 存活 | 进程是否卡死 | **重启容器** | 只查进程自身（最轻，别查依赖！） |
| **readiness** 就绪 | 能否接流量 | **摘出负载均衡**（不重启） | 依赖是否就绪：DB 连接、缓存、配置加载 |
| startup 启动 | 慢启动应用的宽限 | 延后其他探针 | 初始化是否完成 |

**最经典的配置事故**：liveness 里去查数据库——数据库抖动一下，**所有实例同时被判定「死亡」并重启**，把局部故障放大成全站雪崩。规则：**liveness 只证明「我还在跑」，依赖健康属于 readiness**。

Node 服务的配套（见 [[1.06 Node 部署与 Docker]]）：优雅退出——收到 SIGTERM 先让 readiness 返回失败（摘流量）、等在途请求处理完、再关连接退出；否则滚动更新时会出现连接被硬切断的报错。

## 2. 监控告警体系

**四个黄金信号**（服务侧通用口径）：延迟、流量、错误率、饱和度（资源使用）。前端侧对应：性能指标（LCP/INP/CLS）、PV/UV、JS 错误率与接口失败率、资源占用（内存增长）。

**告警分级**（面试重点，体现工程素养）：

| 级别 | 例子 | 通知方式 |
|---|---|---|
| P0 致命 | 服务不可用、核心链路错误率飙升 | 电话 / 立即响应 |
| P1 严重 | 关键接口失败率超阈值、内存持续增长 | 即时消息 + 值班 |
| P2 一般 | 非核心报错增多、性能劣化 | 工作时间处理 |

降噪四招：**阈值基于历史基线而非拍脑袋**；**持续 N 分钟才触发**（避免瞬时抖动）；**同类合并聚合**（一个 bug 上报十万次只告警一条）；**告警必须可行动**——收到后不知道该干什么的告警应该删掉或降级为看板指标。

**根因定位链路**：告警（指标异常）→ 看板下钻（按版本/地区/机型切分，见 [[1.06 分支部署与灰度发布]] 的版本标识）→ 错误详情（sourcemap 还原堆栈 + 用户行为面包屑）→ 链路追踪（traceId 串起前端请求与后端各服务）。**前端上报带 traceId 与后端日志关联**是打通全链路的关键一步。

---

## 3. 前端接入监控的实操清单

1. 引入 SDK（自研或 Sentry 类），初始化时配置：环境（生产/预览）、**版本号**（对应构建 hash，与灰度联动）、采样率、用户标识（脱敏后的 ID）；
2. 构建期上传 **sourcemap** 到监控平台并从产物中剥离（**绝不能把 sourcemap 发到公网**，会泄漏源码）；
3. 白名单/黑名单过滤：忽略浏览器扩展报错、跨域脚本的无堆栈错误、已知的第三方噪音；
4. 接口异常在请求层统一上报（见 [[1.03 前端 API 层架构设计]] 的 Request 层）；
5. 建看板与告警规则，发布后**盯着灰度期的错误率与性能指标**决定放量或回滚。

## 面试问答

### Q: liveness 和 readiness 探针有什么区别？配错会怎样？

满分答案：liveness 判断进程是否还活着，失败会重启容器，因此只应检查进程自身状态；readiness 判断是否能接流量，失败只是从负载均衡摘出去、不重启，可以检查数据库连接、缓存、配置等依赖。经典事故是把依赖检查写进 liveness——数据库抖动导致全部实例同时被判死并重启，局部故障被放大成全站不可用。配套要点：慢启动服务用 startup 探针给宽限期；收到 SIGTERM 先让 readiness 失败摘流量再优雅退出。

### Q: 你们的前端监控告警是怎么设计的？

满分答案：采集端上报性能（LCP/INP/CLS）、异常（JS 错误、Promise 拒绝、资源加载、接口失败）和行为面包屑，带上环境、版本号、用户标识维度。告警按 P0/P1/P2 分级对应不同通知渠道；降噪靠四点：阈值基于历史基线、持续一段时间才触发、同类错误聚合合并、每条告警必须可行动，否则降级为看板指标。定位链路是告警→按版本/地区下钻→sourcemap 还原堆栈加行为回放→traceId 关联后端链路。

### Q: 线上出了个只有部分用户复现的错误，你怎么排查？

满分答案：先用监控切维度定位共性——按版本（是否某次灰度引入）、机型/浏览器（兼容性）、地区/网络（资源加载或接口超时）、用户特征分组，看错误集中在哪一维；再看具体错误详情：sourcemap 还原的堆栈定位代码位置，行为面包屑还原用户操作路径，关联的 traceId 查后端该次请求的日志；必要时给灰度用户开更高采样率或加临时埋点补充信息。核心思路是「用维度切分把偶发变成规律」，而不是盯着单条堆栈猜。
