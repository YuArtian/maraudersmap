# Monorepo 落地实践

## TL;DR

**Monorepo 是「工程实践的放大器」——它同等放大好实践与坏实践，没有工具、流程、文化三方面准备就贸然合仓只会更乱**。落地四步：迁 pnpm workspace 建目录 → 配 Turbo 任务管线与缓存 → CI 按子项目拆分配置 → Changesets 管版本与 changelog。

> 概念与机制见 [[1.04 Monorepo 与工作区]]；构建缓存部分见 [[1.01 前端构建加速实践]]。

---

## 1. 背景：几个同源业务合仓

场景：同一业务线下有若干个前端项目（不同地区/不同渠道的同类应用），**代码高度相似却各自维护**——公共组件靠复制粘贴、依赖版本各自漂移、CI 配置重复维护、一个通用 bug 要改 N 遍。

目标不是「把代码堆一起」，而是**共享工程能力**：一套 lint/测试/CI 模板、一份依赖 lock、一处修复处处生效。

---

## 2. 落地四步

**① 迁移到 pnpm workspace**

```yaml
# pnpm-workspace.yaml
packages: ['packages/**']
```

```jsonc
// 根 package.json：锁定包管理器，防止有人 npm i 生成第二份 lock
"scripts": { "preinstall": "npx only-allow pnpm" }
```

目录结构（务实版）：

```text
repo/
├─ packages/          # 各子项目
│  ├─ app-a/
│  ├─ app-b/
│  └─ shared-ui/      # 抽出来的公共包
├─ .ci/               # 按子项目拆分的流水线配置 + 一份通用 mixin
├─ pnpm-workspace.yaml
├─ turbo.json
└─ package.json       # 根：公共 devDeps 与统一脚本
```

**② 配 Turbo 任务管线**：声明 `build` 依赖 `^build`（先构建上游）、精确列 inputs/outputs，开本地与远程缓存。

**③ CI 拆分**：每个子项目一份流水线配置 + 一份公共 mixin 复用（避免 N 份重复维护）；触发条件按路径过滤，改哪个包只跑哪条线；配合 Turbo 的受影响计算进一步剪枝。

**④ Changesets 管发版**（多包版本联动的标准解）：

```bash
pnpm add -Dw @changesets/cli && pnpm changeset init
# 开发者提交变更时：pnpm changeset → 选包、选 patch/minor/major、写变更说明
# 发版时：changeset version（自动升版本号 + 生成 changelog）→ changeset publish
```

价值：**版本推导自动化**——它会读依赖图，只升变更包及其下游依赖，changelog 由变更说明自动汇总（与约定式提交同属「让元信息驱动自动化」的思路，见 [[3.03 Git 钩子与工程规范]]）。配置里 `baseBranch` 决定 changed packages 的判定基准，`access` 控制私有/公开发布。

## 3. 挑战与反思（这部分才是面试亮点）

来自实践的三条判断：

1. **单仓是放大器不是银弹**：好实践（统一 lint、共享组件、原子提交）被放大，坏实践（混乱的依赖、无边界的耦合、随意的公共包改动）也被同等放大——**没有准备就迁移，只会让混乱指数级传播**；
2. **需要工具、流程、文化三件套**：工具（workspace + 任务编排 + 缓存 + 发版）只是入场券；流程（主干开发、code owner、公共包变更评审）和文化（对「改公共包会影响所有人」的敬畏）缺一不可；
3. **没有普适方案**：不同团队规模、基础设施、协作文化下，落地形态差别巨大——**方法论可迁移，配置不可照抄**。

具体的坑：仓库体积增长（用 sparse-checkout/浅克隆缓解）、权限粒度变粗（靠 code owner 补）、公共包改动的爆炸半径（靠测试覆盖与 changeset 评审兜底）、CI 不做增量就会退化成「改一行跑全量」。

## 面试问答

### Q: 你们为什么要做 Monorepo？怎么落地的？

满分答案：动因是同业务线多个相似项目各自维护——组件复制粘贴、依赖版本漂移、CI 配置重复、一处 bug 改多遍。落地四步：pnpm workspace 建工作区与目录规范（preinstall 锁包管理器防多份 lock）；Turbo 配任务依赖与本地/远程缓存，让构建只发生在受影响的包；CI 按子项目拆流水线并抽公共 mixin，按路径触发；Changesets 管版本——开发者随变更提交 changeset，发版时自动按依赖图升版本并生成 changelog。

### Q: Monorepo 有什么坑？什么情况下不建议用？

满分答案：核心判断是「它是工程实践的放大器」——好实践规模化生效，坏实践也同等放大，混乱的依赖边界和随意的公共包改动会指数级传播。具体坑：仓库体积与克隆时间（sparse-checkout 缓解）、权限粒度变粗（code owner 补位）、公共包改动的爆炸半径、CI 不做增量就退化为全量构建。不建议的情况：团队没有主干开发与评审流程的准备、项目之间本无共享诉求、缺人长期维护工具链——此时多仓 + 私有包发布反而更简单。

### Q: 多包项目的版本和发布怎么管？

满分答案：Changesets——开发者在 PR 里附带 changeset 文件声明「哪些包、什么级别（patch/minor/major）、变更说明」；发版时工具读依赖图自动升级变更包及其受影响的下游包版本、汇总生成各包 changelog、再统一 publish。相比手工改版本号：变更意图与代码同 PR 评审、版本推导可复现、changelog 不再靠人写。配置上注意 baseBranch 决定变更包判定、access 控制私有发布、internal 依赖的升级策略。
