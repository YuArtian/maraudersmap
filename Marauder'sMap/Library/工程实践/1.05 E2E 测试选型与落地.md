# E2E 测试选型与落地

## TL;DR

**前端测试金字塔在实践中更像「奖杯」：单测保核心逻辑、E2E 保关键链路**——因为前端行为依赖网络、后端、交互等多方因素，大量流程用单测**描述不出来或成本过高**。E2E 验证的是「所有层加起来能不能用」，是敏捷发布的信心来源：**没有 E2E，所谓的持续交付只是空谈**。

---

## 1. 为什么前端需要 E2E

前端是 GUI 软件，一次业务流程串起网络、后端服务、路由、组件状态、用户操作——单元测试只能覆盖「一个组件的一个函数」，**覆盖率再高也不能回答「用户能不能下单成功」**。

分工共识：

| 层级 | 覆盖对象 | 成本 | 定位 |
|---|---|---|---|
| 单元测试 | 纯函数、工具库、核心算法 | 低 | 保基础正确性、快速反馈 |
| 组件测试 | 单个组件的渲染与交互 | 中 | 组件库必备 |
| **E2E** | 真实浏览器里的完整业务链路 | 高 | **发版信心**：登录、下单、支付主流程 |

原则：**E2E 只覆盖关键路径**（写多了维护成本与不稳定性会吃掉收益），CI 里守住「主流程不挂」这条底线。

---

## 2. 选型考量

主流两家（Cypress / Playwright）的比较维度，答题时按维度讲而非背结论：

- **调试体验**：Cypress 的时间旅行调试器与自动等待极大降低编写门槛；
- **多浏览器与并行**：Playwright 原生支持 Chromium/Firefox/WebKit、多标签多上下文、并行执行更强；
- **组件测试**：两者都已支持组件级测试（可复用同一套工具跑组件与 E2E）；
- **生态与 CI**：录制回放、截图/录像、失败重试、报告集成。

结论口径：**新项目 Playwright 更全面；已在用 Cypress 且以 Chromium 为主的团队没必要迁移**——选型要基于团队现状而非「哪个更火」。

---

## 3. 落地规范（团队推广的关键）

**目录与配置标准化**——把测试目录结构、tsconfig、支持文件、mock 数据位置固定下来，抽成**预设包**（`@company/cypress-presets` 式的内部包）供各项目一行接入：不标准化就会每个项目一套写法，维护成本失控。

```text
package/
├─ e2e/（或 cypress/）
│  ├─ specs/            测试用例
│  ├─ fixtures/         mock 数据
│  ├─ support/          自定义命令与初始化（由预设包提供）
│  └─ tsconfig.json
└─ 配置文件（建议用 Vite 作为测试启动工具，与开发同构）
```

**选择器规范**（最容易被忽略却最影响稳定性）：**禁止用 CSS class 或 DOM 结构定位**——样式一改测试全红。统一用 `data-testid`（或语义化的 role/label 选择器），并与埋点规范共用一套元素标识约定（见 [[1.08 前端埋点与 SDK 设计]]），做到「一次标记、测试与埋点共用」。

**CI 集成**：PR 触发关键用例、夜间跑全量；失败自动保留截图与录像；不稳定（flaky）用例要**限期治理而不是简单重试**——长期重试会让 E2E 失去可信度。

---

## 4. 反思

真实经验里的三条：**E2E 的最大成本是维护而非编写**（UI 一变就要改）；**不稳定的测试比没有测试更糟**（狼来了效应，团队会习惯性忽略红灯）；**测试数据与环境是最大变量**（需要独立测试账号、可重置的数据种子、稳定的 mock 策略）。

## 面试问答

### Q: 前端为什么需要 E2E 测试？和单测怎么分工？

满分答案：前端行为依赖网络、后端、路由、交互等多方因素，大量业务流程用单测描述不出来或成本过高——单测覆盖率再高也无法回答「用户能不能走通下单」。分工：单测覆盖纯逻辑与工具函数（快、便宜、密集），组件测试覆盖组件渲染交互，E2E 在真实浏览器里覆盖登录、下单等关键链路，作为发版信心的最后一道关。原则是 E2E 只写关键路径，写多了维护成本和不稳定性会反噬。

### Q: Cypress 和 Playwright 怎么选？

满分答案：按维度比而非站队——调试体验 Cypress 的时间旅行与自动等待更友好、上手快；多浏览器支持、并行执行、多标签多上下文场景 Playwright 更强，且原生支持 WebKit；两者都已支持组件测试。结论：新项目倾向 Playwright（能力更全面），存量 Cypress 项目且只需 Chromium 的没必要迁移。选型应基于团队现状、CI 环境与维护成本，而不是流行度。

### Q: 团队推广 E2E 遇到过什么问题？

满分答案：三个真问题——维护成本：UI 一改用例就红，解法是把选择器统一到 data-testid 之类的稳定标识（并与埋点标识共用），禁止依赖 class 和 DOM 结构；不稳定用例：flaky 比没测试更糟，会让团队忽略红灯，必须限期治理而非无限重试；测试数据与环境：需要独立账号、可重置的数据种子和稳定 mock。此外把目录结构与配置抽成内部预设包，让各项目一行接入，是规模化推广的前提。
