# 前端构建加速实践

## TL;DR

**构建慢的三个层次，按投入产出比依次动手：① 开缓存（webpack 5 filesystem 持久化缓存，二次构建立竿见影）② 换更快的转译器（babel-loader → esbuild-loader/swc）③ 上任务级缓存（Monorepo 里 Turbo 的本地 + 远程缓存，未变更的包直接命中跳过）**。原则：先测量定位，再逐层加速。

> 通用原理与配置见 [[2.04 代码分割与构建优化实战]]；本篇是落地叙事与踩坑。

---

## 1. 背景与问题定位

某公司的前端项目群（十余个中后台与业务应用，vue-cli/webpack 技术栈），痛点是**本地开发冷启动数分钟、CI 构建排队严重**，发布节奏被构建拖住。

定位手段：`speed-measure-webpack-plugin` 量各 loader/plugin 耗时、CI 日志分段计时。结论集中在三块：**JS/TS 转译（babel-loader 占大头）**、**依赖重复解析（无缓存，每次从零开始）**、**CI 每次全量构建全部包**。

---

## 2. 第一层：持久化缓存（改动最小、收益最大）

webpack 5 内置文件系统缓存，把模块解析与转译结果落盘：

```js
// webpack / vue.config.js 的 configureWebpack
cache: {
  type: 'filesystem',
  buildDependencies: {
    // ★ 声明「构建配置本身」的依赖：配置或环境文件变了才让缓存失效
    config: [__filename, ...glob.sync('.env*', { cwd: __dirname, absolute: true })],
  },
}
```

踩坑记录：`buildDependencies.config` **要用绝对路径**，指定目录必须以 `/` 结尾——配置非法时缓存会**静默不生成**（现象是「配了没效果」，很难察觉）；CI 环境要把缓存目录（`node_modules/.cache`）纳入流水线缓存，否则容器每次全新、缓存等于没开。

效果口径：二次构建从分钟级降到十几秒（首次构建不变，因为要建缓存）。

---

## 3. 第二层：换转译器（esbuild / swc）

`esbuild-loader` 替换 babel-loader 做 TS/JS 转译与代码压缩（Go 编写、并行，见 [[2.06 Webpack、Vite 与 Rollup 对比选型]]）：

```js
// 转译：用 esbuild-loader 替换 babel-loader
{ test: /\.[jt]sx?$/, loader: 'esbuild-loader', options: { target: 'es2015' } }
// 压缩：用 ESBuildMinifyPlugin 替换 TerserPlugin
```

**代价与边界要说清楚**（否则不像真做过）：esbuild **不做语法降级到 ES5 以下、不处理 polyfill**——目标浏览器要求低时不能全量替换（保留 babel 处理 polyfill，或用 browserslist 收紧目标）；早期版本对装饰器、部分 TS 特性支持不全；**esbuild 不做类型检查**，类型校验必须由独立的 `tsc --noEmit` 承担（见 [[1.05 模块、配置与工程实践]]）。

结论：**开发环境全量用 esbuild 追求速度，生产构建按兼容性要求决定是否保留 babel 链路**。

---

## 4. 第三层：任务级缓存（Monorepo）

包多了之后，真正的浪费是「改一个包却构建全部」。Turborepo 的两把武器（配套见 [[1.02 Monorepo 落地实践]]）：

- **本地缓存**：以「任务输入（源码 + 依赖 + 配置 + 环境变量）哈希」为 key 缓存产物与日志，命中直接回放（秒级）；
- **远程缓存**：把缓存上传到共享存储，**CI 与同事之间共享**——同事拉取代码后本地构建可直接命中 CI 已构建过的结果；接入方式是配置远程缓存端点与 token（自建 Turbo 兼容服务或用官方托管）。

配置要点：`turbo.json` 里精确声明每个任务的 `inputs`/`outputs`/`dependsOn`——**声明不准会导致缓存该失效不失效（拿到旧产物）或该命中不命中**（白建缓存）；环境变量必须列进 `env`，否则不同环境共用缓存会出错。

---

## 5. 效果与反思（面试收尾）

分层收益：缓存让本地二次构建降到十几秒；esbuild 让全量构建时间显著下降；Turbo 让 CI 只构建受影响的包，流水线时长与改动范围成正比而非与仓库大小成正比。

反思三条：**先测量再优化**（凭感觉换工具常常收益为零）；**每层加速都有代价**（缓存的正确性风险、esbuild 的兼容性缺口、Turbo 的配置精度要求）；**长期解是换栈**——新项目直接上 Vite（见 [[2.05 Vite 原理]]）或 Rspack，比在 webpack 上层层打补丁更彻底。

## 面试问答

### Q: 你做过哪些构建优化？效果如何？

满分答案：按三层讲——先用 speed-measure 与 CI 分段计时定位瓶颈在转译与重复解析；第一层开 webpack 5 filesystem 持久化缓存并把缓存目录纳入 CI 缓存，二次构建从分钟级到十几秒；第二层把 babel-loader 换成 esbuild-loader、Terser 换成 esbuild 压缩，全量构建时间大幅下降，同时保留 tsc --noEmit 做类型检查、按 browserslist 决定是否保留 babel 处理 polyfill；第三层在 Monorepo 引入 Turbo 的本地与远程缓存，CI 只构建受影响的包。收尾给反思：先测量、每层都有代价、长期看换 Vite/Rspack 更彻底。

### Q: 用 esbuild 替换 babel 有什么风险？

满分答案：三点边界——esbuild 不支持降级到 ES5 以下且不注入 polyfill，兼容老浏览器的项目不能全量替换；它只做转译不做类型检查，类型安全必须由独立的 tsc --noEmit 保障（这也意味着 IDE/CI 必须补上这道关）；早期版本对装饰器等语法支持不完整。实践取舍：开发环境全量用它换速度，生产构建视目标浏览器保留 babel 链路，并用 browserslist 统一收敛目标降低转译量。

### Q: Monorepo 里怎么让 CI 不做无用构建？

满分答案：任务级缓存加受影响范围计算——Turbo/Nx 以任务输入哈希（源码、依赖、配置、声明的环境变量）为 key 缓存产物，命中即跳过；远程缓存让 CI 与本地共享命中结果；再配合按 git diff 计算 affected 包只跑相关任务。关键细节是 turbo.json 里 inputs/outputs/dependsOn/env 必须声明准确——声明不全会拿到脏缓存，声明过宽会永远不命中。
