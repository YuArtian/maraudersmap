# 前端埋点与 SDK 设计

## TL;DR

**埋点规范的核心是「元素标识约定」：用 `data-*` 属性声明式标记，测试与埋点共用一套标识**——一次标记，E2E 定位和行为采集都能用。**SDK 设计四原则**：接口易用（一行接入）、体验一致（内置 UI 但可定制）、平台差异内聚在适配层、版本与文档可维护。

---

## 1. 埋点方案的三种形态

| 方案 | 做法 | 优缺点 |
|---|---|---|
| 代码埋点 | 手动在业务代码里调 `track()` | 精确灵活，但侵入业务、易漏埋 |
| **声明式埋点** | 在模板上加 `data-*` 属性，统一委托采集 | **业务代码零侵入**、可被静态扫描、与测试标识复用 |
| 无埋点/全埋点 | 采集所有点击并事后圈选 | 免开发但数据噪音大、字段语义弱 |

**声明式埋点的规范**（可直接落地的约定）：

```html
<!-- 用符合 W3C dataset 规范的属性；框架里可封装成指令/组件简化书写 -->
<div data-t-key0>无值的标记</div>
<div data-t-custom-key="id_for_key">带值的标记</div>
```

命名约定三条：统一前缀（如 `data-t-`）便于扫描与过滤；**key 用 kebab-case、仅小写字母数字、字母开头**（dataset 语法要求）；**value 用 snake_case 字符串**。采集侧在根节点做**事件委托**（见 [[3.05 事件模型与事件委托]]），点击冒泡上来后用 `closest('[data-t-*]')` 找到最近的标记元素上报——**一个监听器覆盖全站**。

配套：Vue/React 里封装成指令或高阶组件（`v-test:key="value"`）让书写更自然；同一套标识直接作为 E2E 的选择器（见 [[1.05 E2E 测试选型与落地]]），**测试与埋点共用标识**是这套规范最大的工程红利。

## 2. 通用 SDK 的设计要点（以登录 SDK 为例）

**背景问题**：多个应用都要接入第三方登录、且要支持多个平台——每个应用各自对接一遍，成本高、体验不一致、代码难维护。**解法是把「协议对接 + 交互界面」沉淀成 SDK + UI 组件库**，形成统一的身份验证方案。

设计四原则：

1. **接口易用**：对外只暴露最小 API（`login()`/`logout()`/`getUser()`），复杂的平台差异（各平台的授权流程、回调参数格式）内聚在适配层——**使用方不需要理解 OAuth 细节**（协议本身见 [[1.08 登录方案：Session、JWT、SSO 与 OAuth]]）；
2. **体验一致但可定制**：内置默认登录界面保证各产品体验统一，同时开放主题/文案/布局定制与「只要能力不要 UI」的纯 SDK 模式；
3. **状态与安全**：token 存储策略（内存 + HttpOnly Cookie，见 [[2.05 浏览器存储：Cookie、Web Storage 与 IndexedDB]]）、静默续期、多标签页登录态同步、回调 URL 白名单与 state 防 CSRF；
4. **可维护性**：语义化版本与 changelog（见 [[1.02 Monorepo 落地实践]]）、TS 类型完备、文档与可运行 demo、破坏性变更的迁移指南——**SDK 的用户是开发者，DX 就是产品体验**。

通用 SDK 的架构范式（与 [[2.05 高频场景题集]] 的 SDK 设计原则一致）：**核心内核 + 插件/适配器 + UI 层三层分离**，让「加一个登录平台」只需加一个适配器而不动内核。

---

## 3. 数据链路与质量

埋点数据要能用，链路上还要解决：**上报可靠性**（sendBeacon/keepalive 保证页面卸载时不丢，批量合并减少请求）；**数据一致性**（前端埋点与后端日志用同一套事件命名与用户标识，才能拼出完整漏斗）；**埋点治理**（有元数据平台登记事件定义，避免同一行为多个命名各写各的）；**校验**（CI 里扫描 data-t 标识是否在事件字典中登记，防止「埋了没定义」和「定义了没埋」）。

## 面试问答

### Q: 你们的埋点方案是怎么做的？

满分答案：以声明式埋点为主——在模板元素上用统一前缀的 data-* 属性标记（key 用 kebab-case、value 用 snake_case，符合 dataset 规范），采集侧在根节点做事件委托，点击冒泡后用 closest 找最近的标记元素上报，一个监听器覆盖全站、业务代码零侵入。框架里封装成指令简化书写。最大红利是这套标识同时作为 E2E 测试的选择器——一次标记、测试与埋点共用，也避免了测试依赖 class 导致的脆弱。复杂业务事件再辅以代码埋点。

### Q: 设计一个通用登录 SDK 要考虑什么？

满分答案：先说清动因——多应用重复对接多个登录平台，成本高、体验不一致。设计上四点：对外 API 最小化，平台差异内聚在适配层，使用方不必理解各平台授权细节；提供默认 UI 保证体验一致同时支持主题定制和纯能力模式；安全与状态：token 存储策略、静默续期、多标签同步、回调白名单与 state 防 CSRF；可维护性：语义化版本、类型完备、文档 demo 与迁移指南。架构上内核 + 适配器 + UI 三层，新增平台只加适配器。

### Q: 埋点数据不准怎么办？

满分答案：分链路排查——采集端：上报是否在页面卸载时丢失（改用 sendBeacon/keepalive）、事件是否重复绑定或委托漏判、SPA 路由切换的 PV 是否补齐；定义端：前后端事件命名与用户标识是否统一，否则拼不出完整漏斗；治理端：是否有事件字典与元数据登记，CI 里扫描代码中的埋点标识与字典比对，找出「埋了没定义」和「定义了没埋」。核心观点是埋点是数据产品而非一次性代码，需要规范、校验与治理三件套。
