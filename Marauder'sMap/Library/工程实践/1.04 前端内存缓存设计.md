# 前端内存缓存设计

## TL;DR

**核心设计：缓存的值不是数据而是 Promise**——多个组件同时取未就绪的缓存时共享同一个 Promise，天然合并并发请求；**不提供手动更新，只提供纯函数 initializer**，过期后重新调用它取数；把存储位置抽象成可替换的 `state` 存取器，就能从内存扩展到状态库或持久化存储。

---

## 1. 问题

同一份「基础数据」（配置、字典、用户信息）被多个组件反复请求：浪费带宽、加重服务端、慢网下反复 loading。朴素缓存（`if (!cache) cache = await fetch()`）有三个漏洞：**并发穿透**（同时进入的多个调用各发一次请求）、**过期策略混乱**（谁负责刷新）、**存储位置写死**（想换成持久化就得重写）。

---

## 2. 三个设计决策

**① 缓存 Promise 而不是数据**（最精妙的一点）：

```ts
class CacheGetter<T> {
  private state: { promise: Promise<T> | null; updateTime: number } = { promise: null, updateTime: 0 };

  constructor(private initializer: () => Promise<T>, private ttl = 60_000) {}

  get(): Promise<T> {
    const expired = Date.now() - this.state.updateTime > this.ttl;
    if (!this.state.promise || expired) {
      this.state.promise = this.initializer();     // 只在此处发起
      this.state.updateTime = Date.now();
    }
    return this.state.promise;                     // ★ 并发调用拿到的是同一个 Promise
  }
}
```

收益：**并发合并**——十个组件同时 `get()`，只发一次请求，所有人 await 同一个 Promise 一起 resolve（Promise 一次 settle、多次 then 的特性，见 [[2.02 Promise 用法与手写实现]]）；接口天然异步统一，调用方无需区分「已缓存」和「首次加载」。

**② 只读接口 + 纯函数 initializer**：不开放手动 `set`——数据来源唯一（initializer 通常是接口请求），要求它是**纯函数**（同参同结果、无副作用），刷新即重新调用。这样缓存内容永远可复现，杜绝「谁偷偷改了缓存」的调试地狱。

**③ 惰性过期检查**：不用定时器主动刷新，而是**每次取用时判断是否过期**——省掉后台定时任务、无内存泄漏风险，代价是过期后的首次访问要等一次请求（可用 stale-while-revalidate 变体优化：先返旧值、后台刷新，同 [[1.04 HTTP 缓存策略]] 的同名指令）。

---

## 3. 可扩展性：把 state 抽成存取器

用 class 实现的关键理由是 `state` 可以被覆写成 getter/setter：

```ts
class CacheGetterWithStore<T> extends CacheGetter<T> {
  get state() { return store.cache[this.key]; }     // 读写转发到状态库/localStorage
  set state(v) { store.cache[this.key] = v; }
}
```

于是同一套逻辑可以落在：内存（默认）→ 状态库（让缓存参与响应式渲染）→ Storage（跨刷新持久化，见 [[2.05 浏览器存储：Cookie、Web Storage 与 IndexedDB]]）。**「策略可替换」是这个设计从 demo 走向生产的关键**。

---

## 4. 边界与现代替代

要主动说的取舍：内存缓存**刷新即失效**（要跨会话得配持久化）；**没有跨标签页同步**（BroadcastChannel 可补）；缓存一致性靠 TTL 而非事件驱动，强一致场景不适用（对照 [[2.02 MongoDB 与 Redis 概览]] 的缓存一致性讨论）。

现代生态里，**React Query / SWR / Vue Query 已经把这套做成标准品**——请求去重、stale-while-revalidate、失效重取、窗口聚焦刷新、乐观更新全都内建。自研的价值在于：非请求类数据（计算结果、跨框架共享）、需要嵌入既有架构、或者理解这些库到底解决了什么。

## 面试问答

### Q: 前端做数据缓存时，怎么避免同一份数据被并发请求多次？

满分答案：缓存里存的不是数据而是 Promise——第一个调用者创建请求并把 Promise 存入缓存，后续并发调用直接返回同一个 Promise，大家 await 同一次请求，一起 resolve。这利用了 Promise 一次 settle、多次 then 都能拿到结果的特性，比加锁或队列简单得多。同时接口统一为异步，调用方不需要区分首次加载与命中缓存。

### Q: 你设计的缓存怎么处理更新和过期？

满分答案：不提供手动 set，只在构造时传入一个纯函数 initializer 作为唯一数据来源，需要刷新就重新调用它——保证缓存内容始终可复现、来源唯一。过期采用惰性检查：每次 get 时比对时间戳，超过 TTL 就重新初始化，不用后台定时器（省资源、无泄漏）；对体验敏感的数据可以做 stale-while-revalidate 变体，先返回旧值再后台刷新。

### Q: 这类缓存怎么扩展到持久化或状态管理？

满分答案：把「存储位置」抽象出来——用 class 实现并把 state 定义为 getter/setter，子类覆写它即可把读写转发到 Vuex/Pinia（让缓存参与响应式渲染）或 localStorage/IndexedDB（跨刷新持久化），缓存的核心逻辑（Promise 合并、TTL 判断）完全复用。这是策略模式的应用。补充边界：内存缓存刷新即失效、无跨标签页同步（可用 BroadcastChannel 补）、一致性靠 TTL；生产上请求类缓存直接用 React Query/SWR 更划算。
