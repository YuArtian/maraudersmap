# 分支部署与灰度发布

## TL;DR

**分支部署（预览环境）：每个分支构建产物按唯一 hash 输出到独立目录并上传 CDN，配合动态 publicPath 与路由 base，让每个 PR 都有一个可点开的临时地址**。**灰度发布：按副本数（滚动比例）或按流量规则（网关/ingress 权重、Header/Cookie 定向）放量，配合监控与一键回滚**。

---

## 1. 分支部署：让每个 PR 都能点开

痛点：测试和产品只能等合并到测试环境才能验，多人排队互相覆盖。

实现要点（前端侧只需三处改动，都源自「产物要能在任意子路径下运行」）：

```js
// ① 构建产物路径：按分支 hash 隔离，便于 CDN 与清理
outputDir = process.env.DIST_HASH ? `dist/preview/${process.env.DIST_HASH}` : 'dist';

// ② 静态资源前缀：指向 CDN 上该分支的目录（否则资源 404，见工程化篇的 publicPath）
publicPath = process.env.PUBLIC_PATH;

// ③ 路由 base：history 模式下页面在子路径运行，base 必须同步
new Router({ mode: 'history', base: process.env.ROUTER_BASE_URL });
```

CI 侧：流水线里加一个 `build:preview` 任务，注入分支 hash 相关环境变量 → 构建 → 上传对象存储/CDN → 把预览地址回帖到 PR。配套：错误监控的 sourcemap 上传前缀也要跟着改（否则堆栈还原对不上，见 [[2.01 Web 性能指标与前端监控]]）；预览环境定期清理防止存储膨胀。

**关键认知**：这套方案的本质是「**前端产物与部署路径解耦**」——publicPath 与 router base 由环境变量驱动，同一份代码能部署到任意路径，预览环境只是它的一个应用。

---

## 2. 灰度发布的两种粒度

**① 基于副本数（滚动/金丝雀，容器编排层）**：新版本先起 1 个副本与旧版本共存，流量按副本比例自然分配；观察监控无异常再逐步扩大新版占比直至全量。优点：不依赖额外网关能力，编排平台原生支持；缺点：**流量分配不精确、无法定向到特定用户**。

**② 基于流量规则（网关/ingress 层）**：按权重（10% 到新版）或按请求特征（Header/Cookie/UID 尾号）路由——可以做到「内部员工先用新版」「特定地区灰度」。优点：精确可控、可做 A/B；缺点：需要网关支持与规则维护，前端要配合传递灰度标识。

前端侧的配套（这部分是前端面试的落点）：

- **静态资源必须版本共存**——带 hash 的文件名 + 长缓存（见 [[1.04 HTTP 缓存策略]]），保证灰度期间新旧版本的 JS 都能取到，否则用户拿着旧 HTML 却请求已删除的旧 chunk 会白屏（**发布后立刻清理旧产物是事故常见原因**）；
- **HTML 不缓存**，用户刷新即可拿到当前灰度指派的版本；
- **前端携带版本标识**（请求头/埋点字段），让监控能按版本切分指标——灰度期间对比新旧版的错误率与性能是决定是否放量的依据；
- **一键回滚**：产物在 CDN 上不删除，回滚只需把 HTML 指回旧版本（或切回旧副本），秒级生效。

---

## 3. 完整发布链路叙事

「代码合入 → CI 构建（缓存加速）→ 产物带 hash 上传 CDN → 部署新副本 → **健康检查通过**才接流量（见 [[1.07 监控告警与健康检查]]）→ 按比例灰度放量 → 观察错误率/性能/业务指标 → 全量或回滚 → 通知在线用户刷新（见 [[2.05 高频场景题集]] 的版本更新通知）」——这条链路能完整讲下来，等于覆盖了前端工程化的下半场。

## 面试问答

### Q: 什么是分支部署/预览环境？前端要做什么改造？

满分答案：让每个分支或 PR 都有独立可访问的临时环境，解决测试环境排队与互相覆盖。前端三处改造都围绕「产物与部署路径解耦」：构建输出目录按分支 hash 隔离；publicPath 指向该分支在 CDN 上的目录（否则异步 chunk 404）；history 路由的 base 同步为子路径。CI 里加 preview 构建任务注入这些环境变量、上传 CDN 并把地址回帖到 PR。配套注意 sourcemap 前缀同步与预览产物定期清理。

### Q: 灰度发布怎么做？前端要配合什么？

满分答案：两种粒度——基于副本数的金丝雀，新旧版本副本共存按比例分流，编排平台原生支持但无法定向；基于网关/ingress 的流量规则，按权重或 Header/Cookie/用户特征精确路由，可做定向灰度与 A/B。前端配合四件事：静态资源带 hash 且新旧版本共存（发布后别急着删旧产物，否则旧 HTML 取不到 chunk 白屏）、HTML 不缓存保证刷新拿到最新指派、请求与埋点携带版本标识以便监控按版本切分、保留产物实现秒级回滚。

### Q: 发布出问题怎么快速回滚？

满分答案：前提是产物不可变且共存——静态资源按内容 hash 命名长期保留在 CDN，回滚只需把入口 HTML（或部署指向）切回旧版本，秒级生效且无需重新构建；容器侧对应回滚到上一个镜像版本或调整副本。配套：发布前的健康检查与灰度观察窗口、监控按版本切分能第一时间发现异常、变更记录可追溯（谁在什么时候发了什么）。核心思想是「向前发布与向后回滚都是切换指针，不是重新构建」。
